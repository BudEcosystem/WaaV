# WaaV SDK Performance & Resilience Plan

> Governing design from research workflow whth7howg: gateway-internals review + Pipecat v1.4.0 brutal review + measured WaaV SDK baseline + SOTA survey (LiveKit/Daily/Vapi/WebRTC). Build-on-top, not invent.

## Baseline (measured)
MEASURED BASELINE (from /tmp/waav_bench/run_all.sh, 2-run stable, audio=false config-only on spare gw 3019 raised-limits / 3029 default; ollama-wired; verified against source at file:line):

CONNECT (connect()->ready): Py warm p50 1.92ms / p90 2.58ms / cold 2.74ms; TS warm p50 2.09ms / p90 2.80ms / cold 12.62ms (Node `ws`+ESM warmup). ctor("rate-limit/queue setup")=0.8us(Py)/0.5us(TS) — pure object alloc, NOT a bottleneck. => connect handshake is already fast; the real connect-tail is server-side PROVIDER_READY (audio=true, up to 30s for STT+TTS upstream, config_handler.rs:45) which this isolation deliberately excluded. Optimization must target cold/tail + provider construction, NOT the WS handshake.

RECONNECT (kill+restart gw mid-session): works e2e on BOTH — config IS re-sent (gw log 55->56 + fresh stream_id) and queued audio IS flushed (pending 0). But recovery is slow due to large first backoff: Py ~1652ms (attempt 4; 200+300+450+675), TS ~252ms (1 attempt). Py initialDelay=1000ms (session.py:37 reconnect_config), TS initialDelay=1000ms (reconnect.ts:28).

GAPS RANKED BY REAL-WORLD IMPACT:
1. [P0, CORRECTNESS] ZOMBIE/half-open undetected. SIGSTOP-frozen gw (TCP ESTABLISHED, no FIN/RST): Py reports connected=True for 30s (60/60 sends "succeed"), TS isConnected=true for 25s; neither reconnects. Py inherits websockets 20/20 ping but it did NOT trip; TS Node `ws` created with NO ping options (connection.ts:78). Browser path can't send native pings and gateway has NO JSON ping op (verified: zero `"ping"` arms in handlers/ws/) and does NOT proactively ping clients (handler.rs:683 auto-pong only). A real call silently hangs for minutes. THE #1 gap — all 4 reviews converge here.
2. [P0, UX] BROWSER PLAYER glitches + non-interruptible. player.ts:199 concatenates the ENTIRE queue into one AudioBuffer, :240 source.start() with NO scheduled `when` (back-to-back buffers race the audio clock -> gaps on underrun); clearBuffer()/stop() only empty the JS array (player.ts:319/334), never source.stop() the already-scheduled node -> barge-in does NOT cut the audio the user is hearing.
3. [P0, RESOURCE] MAIN-THREAD capture via deprecated ScriptProcessorNode in TS (recorder.ts:175, bufferSize 4096 = 85ms@48k/256ms@16k) AND widget (recorder.ts:56). Per-frame CPU trivial (~6us) but main-thread contention with React/GC/layout -> jank/underrun under load + a quarter-second fixed input-latency floor. TS has an UNUSED workletNode field (recorder.ts:65) and a "TODO: Upgrade to AudioWorklet" (recorder.ts:150). No worklet .js asset exists anywhere (verified: no addModule/audioWorklet refs).
4. [P0, RESILIENCE] No quick-failure circuit breaker in EITHER reconnect loop. TS reconnect.ts maxAttempts=Infinity (reconnect.ts:32), widget maxReconnectAttempts but no stable-duration tracking (websocket.ts:455), Py max_retries=10 treating every failure identically (session.py:967). An un-fixable error (bad key/config) keeps SUCCEEDING the handshake so backoff is futile -> reconnect-storm.
5. [P1, CORRECTNESS] WIDGET never reconnects after a post-ready drop. websocket.ts:300 onclose calls attemptReconnect ONLY when `!settled` (i.e. drop BEFORE ready); a drop AFTER ready leaves settled=true so it NEVER reconnects (unlike TS SDK which wires handleClose->scheduleReconnect->sendConfig+flush).
6. [P1, RESILIENCE] In-flight audio discarded on reconnect. Py session.py:496 _pending_audio.clear() after a single flush; no replay buffer across a reconnect that fires mid-utterance.
7. [P1, RESILIENCE] CONTROL-QUEUE asymmetry. TS buffers control+audio offline (session.ts queue.enqueue) and flushes on open; Py _send_json RAISES ConnectionError on a dead socket (session.py:739-744) so only send_audio buffers (_pending_audio). The ws/queue.py MessageQueue class (drop-oldest, bounded) EXISTS but is NOT wired into Py's JSON send path.
8. [P1, RESILIENCE] RATE-LIMIT storm. Default 60rps/burst10: raw 20-concurrent -> 3 OK/17x429; the SDK 2^attempt backoff (cap 15s) COMPOUNDS so a 20-concurrent SDK storm did NOT finish in 120s. No client-side connect coalescing / shared token bucket.
9. [P1, PERF] Naive resampling: processor.ts:95 stateless per-chunk linear interp (no anti-alias LPF, no cross-chunk history) -> aliasing on 48k->16k decimation + clicks at every buffer boundary. Py AudioProcessor pure-python no-numpy (0.77ms/4096-call, ~13x slower than TS) with per-call list+bytes() realloc -> GC pressure.
10. [P2, PERF] No jitter buffer / PLC on TTS playout (no file under */src/audio/). No opus on the wire (raw Int16 PCM ~256kbps mono@16k vs ~24kbps opus). No connect-time pre-warm (only a 10s connect timeout, connection.ts:78; no prepareConnection/prewarm anywhere — verified). No network-change (online/offline / navigator.connection) listeners.

CORRECTIONS TO THE INPUT REVIEWS (verified in source):
A. protocol_version is ALREADY ASSERTED in BOTH SDKs (Py session.py:793-803 stderr-warns on major mismatch; TS session.ts:333-342 emits a PROTOCOL_VERSION_MISMATCH error event). The gateway-internals review's "W-K1 left inert / only captures it" claim is STALE — this is DONE; drop it from the plan (keep only: extend Py warn -> typed event for parity, trivial).
B. TS connection.ts does NOT surface `on('pong')` (the `ws` instance is wrapped, pong is never plumbed up) — so the Node zombie watchdog needs connection.ts to ADD a pong listener + a ping() method, not merely "read the ws pong event."
C. TS already bounds its close handshake at 5s (connection.ts close()); only Py disconnect() awaits ws.close() UNBOUNDED (session.py:1024).
D. REST pooling: Py httpx.AsyncClient is created with default pool limits / no keepalive tuning (client.py:41 — no `limits=`); TS REST uses bare global `fetch` with NO keepAlive agent (client.ts:109). Both are real, concrete pooling gaps (Tier-2).

## Design philosophy + dimensions
DESIGN PHILOSOPHY: the gateway already owns ALL heavyweight server-side resilience (per-provider CircuitBreaker FATAL fast-trip, process-wide ReconnectGovernor storm cap, S2S conversation-replay + ResumptionHandle, ReconnectableStream) but NONE is surfaced on the client /ws or /realtime wire — verified zero resume/session_token matches on the client handlers. So the SDK MUST NOT mirror breaker/governor/replay client-side; on a client<->gw drop there is no server state to resume and the correct+sufficient behavior is the EXISTING reconnect->re-send-config->flush-queue. The SDK's job is the FOUR things only the client can do: (a) detect a dead-but-OPEN socket (the gateway never pings clients), (b) play TTS glitch-free + interruptibly, (c) capture off the main thread, (d) cooperate precisely with documented gateway limits/knobs. Adopt Pipecat's proven patterns; BEAT the weak ones (its WS client.py just gives up on reconnect — WaaV already beats it; its WS audio is raw PCM — WaaV's opus uplink will beat it).

=== D1. LIVENESS / ZOMBIE WATCHDOG (+ network-change) — Tier-1, #1 ROI ===
WHAT: app-level liveness on the SDK's OWN socket with a runtime-split mechanism, since the gateway auto-pongs but never initiates pings (handler.rs:683) and there is no JSON ping op.
- NODE (TS SDK, python SDK): native WS PING + pong-deadline. TS: in connection.ts ADD a `ping()` method (calls ws.ping()) and plumb `this.ws.on('pong', ...)` up to session.ts (currently not surfaced — correction B). Python: pass websockets.connect(ping_interval=5, ping_timeout=3) at session.py:410 (override the 20/20 default that did NOT trip) AND, belt-and-suspenders, run an app timer. Loop: send ping every ~5s (voice cadence; SOTA's 20-45s is for cost-sensitive long-idle, voice wants fast), expect pong within ~3s; on miss -> ws.terminate()/close + EXISTING reconnect path.
- BROWSER (widget + TS in browser): browsers CANNOT send raw WS pings and the gateway has no JSON ping (verified). Use a STALE-INBOUND-DATA timer instead: track lastInboundMonotonic on every frame (the gateway emits frequent transcripts/audio/keepalive during any active session); if NO inbound frame for a window WELL under the gateway's 300s idle-close (handler.rs:265, base_idle 300 +-30s jitter) — use ~10-15s during an active call — declare zombie, close, reconnect. Pair with D6 STT keepalive-silence so the line is never legitimately idle mid-call.
- NETWORK-CHANGE (browser): subscribe window 'online'/'offline' + navigator.connection 'change' + document 'visibilitychange'. On online/foreground -> fire an immediate liveness probe (Node: ping; browser: if no inbound in last 2s, proactively reconnect). On offline -> stop the storm (don't retry into a known-down NIC). Mirrors Twilio ICE-restart-on-network-change.
WHERE: TS connection.ts (add ping()/pong-plumbing + watchdog timers) + session.ts (wire miss->scheduleReconnect); python session.py (ping_interval/timeout + app watchdog in _receive_loop staleness); widget websocket.ts (stale-inbound timer + listeners). NEW small module ws/liveness (TS) / reuse inline (Py/widget).
GATEWAY LEVERAGE: relies on the gateway's existing auto-pong (handler.rs:683); cooperates with the 300s idle-close (handler.rs:518 sends {"type":"error","message":"Connection closed due to inactivity"} then Close) by healing FIRST. NO gateway change.
PIPECAT/SOTA ADOPTED: Pipecat smallwebrtc is_connected() (last-ping<3s) + WebsocketService._verify_connection() (ws.ping() AFTER reconnect to prove liveness, not merely OPEN) — adopt the verify-after-reconnect too. SOTA websocket.org heartbeat (pong-timeout 10s, treat missed pong as immediate-reconnect; immediate ping on visibilitychange).
TARGET: zombie detection < 3s in the SIGSTOP test (currently >30s/never); verify-after-reconnect proves the new socket carries data before declaring "reconnected".

=== D2. BROWSER PLAYER: 10-20ms scheduled playout + true barge-in cut — Tier-1, #2 ROI ===
WHAT: replace concatenate-and-start with a scheduled-chunk playout clock. Maintain playhead = max(ctx.currentTime, nextStartTime); for each ~20ms PCM chunk create a tiny AudioBuffer, source.start(nextStartTime), nextStartTime += chunk.duration; KEEP a list of future-scheduled sources. On clear()/barge-in: source.stop() EVERY scheduled source (cuts within ~20ms) AND empty the JS queue AND keep sending {type:'clear'} to the gateway. This fixes BOTH the underrun glitch AND the non-interruptible bug in one rewrite.
WHERE: typescript/src/audio/player.ts (rewrite processQueue:199 + clearBuffer:319 + stop:334) and widget/src/audio/player.ts.
GATEWAY LEVERAGE: set tts_config.audio_out_chunk_ms=20 (config.rs:533, E-G2 already implemented+validated) so the gateway re-frames egress into 20ms chunks -> a `clear` truncates within ONE chunk server-side, and the chunks arrive pre-sized for scheduled playout. Set tts_config.client_playback_rate to the AudioContext sink rate (e.g. 48000, config.rs:542, C-G5) so the GATEWAY resamples egress with continuous filter state -> the player does ZERO downlink resampling (removes a whole client-side resample stage + its clicks). This is faster + lower-jitter than a client jitter buffer for the common case and is the single biggest "leverage gateway not reinvent" win.
PIPECAT/SOTA ADOPTED: Pipecat base_output.py 10ms-chunk + PTS clock-task (audio_bytes_10ms, _clock_task_handler PriorityQueue PTS-vs-clock) + handle_interruptions drain/cancel; SOTA NetEq 10ms GetAudio granularity. WaaV BEATS Pipecat's clear by also killing locally-scheduled sources (Pipecat can't on Web Audio).
TARGET: zero underrun gaps at steady arrival; barge-in audible-cut < 30ms (currently never cuts already-scheduled audio).

=== D3. AUDIOWORKLET CAPTURE (off-main-thread, TS + widget) — Tier-1, #3 ROI ===
WHAT: ship an AudioWorkletProcessor that runs on the audio render thread, accumulates 128-sample render quanta into 20ms@16k = 320-sample frames, does resample + Float32->Int16 IN the worklet, and posts Int16 frames to main via TRANSFERABLE ArrayBuffers (zero-copy). Wire the already-present-but-unused workletNode (recorder.ts:65) via audioContext.audioWorklet.addModule(); KEEP ScriptProcessor ONLY behind a `typeof AudioWorkletNode === 'undefined'` capability fallback for legacy browsers.
WHERE: NEW typescript/src/audio/capture.worklet.ts (+ build step to emit a standalone .js — none exists today) and widget equivalent; rewrite recorder.ts:150-200 (delete the createScriptProcessor primary path) and widget recorder.ts:54-91. Bundler note: the worklet must be a SEPARATE entry (it has its own global scope) — add a Rollup/esbuild input or inline-blob-URL it.
GATEWAY LEVERAGE: declare stt_config.sample_rate accurately (config.rs:307 — it drives both STT and LiveKit ingress rate); chunk under MAX_AUDIO_FRAME_SIZE 5MB (audio_handler.rs:26) — trivially satisfied at 20ms frames (640B). No gateway change.
PIPECAT/SOTA ADOPTED: pipecat-client-web RTVIClient worklet (NOT the python repo) + SOTA realtime-audio-sdk (128-sample quantum -> 320-sample 20ms frames, postMessage transferable, "minimize allocations in process()" -> reuse a ring/pool, no per-frame Int16Array alloc — fixes the recorder.ts:191 fresh-alloc-per-callback).
TARGET: input cadence 20ms (from 256ms@16k); main thread freed (no jank under React/GC); zero per-frame main-thread allocation.

=== D4. RECONNECT HARDENING: quick-failure breaker + fast first-hop + widget post-ready fix + lossless replay — Tier-1 ===
WHAT (4 parts, all small):
(a) QUICK-FAILURE BREAKER in BOTH loops: record connection-survival duration; if a connection dies <5s after connecting, increment a counter; after 3 CONSECUTIVE quick failures STOP and surface a typed FATAL "likely-unrecoverable (check key/config)" error instead of looping. Port Pipecat websocket_service.py:31-36 (_MIN_STABLE_CONNECTION_DURATION=5.0, _MAX_CONSECUTIVE_QUICK_FAILURES=3), :166-189. This is the CLIENT-side analog of the gateway's per-provider CircuitBreaker FATAL fast-trip — NOT a duplicate (the gateway's is upstream-only); it stops the SDK retrying a doomed CONFIG.
(b) FAST FIRST-HOP: drop initialDelay 1000ms->~200ms with decorrelated-jitter backoff (sleep=min(cap, random(base, prev*3))) — NOT raw 2^attempt — to kill the compounding-storm finding; keep 30s ceiling + reset-after-stable. Brings Py ~1.65s recovery toward TS's ~250ms.
(c) WIDGET POST-READY FIX: wire websocket.ts onclose -> attemptReconnect -> re-send config UNCONDITIONALLY (not gated on `!settled`); reset reconnectAttempts on successful ready (websocket.ts:300-303 is the bug).
(d) LOSSLESS REPLAY: keep a BOUNDED ring of recently-sent audio + queued speak() calls; on reconnect (after config-restore) replay it; defer a reconnect that fires mid-utterance until the turn finishes where detectable. Port Pipecat stt_service.py:618-668. STOP Py's _pending_audio.clear() at session.py:496 from dropping in-flight audio.
WHERE: TS reconnect.ts (breaker state + decorrelated jitter) + session.ts (survival timer + replay ring); python session.py:962-1000 _reconnect (breaker + backoff + replay) + remove :496 clear; widget websocket.ts:300/454.
GATEWAY LEVERAGE: respect ONE-CONFIG-PER-SESSION (config_handler.rs:101 rejects a 2nd config on a live session) — reconnect-then-fresh-config is the ONLY correct reconfigure path; encode "change voice mid-call" as transparently-reconnect in the API. Treat /realtime error code:'connection_lost' + the following Close (realtime/handler.rs:738) and /ws "inactivity"/"shutting down" error texts as server-initiated -> immediate reconnect-with-config.
PIPECAT/SOTA: Pipecat quick-failure breaker + audio-loss-free replay + defer-until-UserStoppedSpeaking; SOTA decorrelated-jitter + Twilio 30s reconnect window.
TARGET: doomed-config stops in 3 quick failures (not 10/Infinity); first-hop recovery <300ms; widget reconnects after a post-ready drop (currently never); zero audio loss across a mid-call blip.

=== D5. CONTROL-QUEUE UNIFICATION + UPLINK BACKPRESSURE SHEDDING — Tier-1 ===
WHAT: wire the EXISTING ws/queue.py MessageQueue (drop-oldest, bounded — already written, just unused) into Python's JSON send path so control ops (speak/clear/send_message) buffer-and-flush like audio and like the TS SDK, instead of _send_json RAISING ConnectionError (session.py:739-744). Make Py == TS. Separately, mirror the gateway's drop-oldest egress discipline on the SDK UPLINK: bound the outbound audio queue and shed the OLDEST frame under backpressure (the gateway sheds stale DroppableAudio: messages.rs:458) so a slow gw never accumulates uplink latency; and on playback, drop late TTS frames (the gateway gives NO per-frame delivery guarantee for DroppableAudio — the player MUST be loss-tolerant).
WHERE: python session.py _send_json + the existing ws/queue.py; TS already correct (session.ts queue.enqueue).
GATEWAY LEVERAGE: matches the gateway's MessageClass policy exactly (DroppableAudio try_send-drop / Critical await). No gateway change.
TARGET: Py and TS behave identically offline (control buffers, not raises); uplink latency bounded under a slow-gw stall.

=== D6. CONNECT-TIME: prewarm + alias + correct timeouts — Tier-2 ===
WHAT: add a public prewarm()/prepareConnection() (mirror LiveKit Room.prepareConnection) callable at page-load: DNS+TLS warmup (a HEAD/preconnect to the gateway origin) + parallel auth/token prefetch + optionally a warm-spare WS so first user action attaches to an already-open socket. None exists today (verified no prewarm refs). Also: STT keepalive-silence (Pipecat stt_service.py:45 — 100ms zero-PCM every ~5s of no real audio, gated by a flag) so a conversational pause doesn't idle the upstream STT stream (note: the gateway's auto-pong keeps the SOCKET open but NOT the provider's STT stream warm).
WHERE: NEW prewarm() on the top-level client (bud.ts / client.py / widget); session connect path; send_audio idle-timer for keepalive.
GATEWAY LEVERAGE: the DOMINANT connect cost is server-side PROVIDER_READY (up to 30s, config_handler.rs:45) — so (i) the SDK connect timeout MUST be >30s (currently 10s, connection.ts:78 — this is a BUG for audio=true sessions; raise to ~35s), and (ii) prefer a server-side `alias` so ONE round-trip resolves the whole {stt,tts,llm} bundle (fastest perceived start); consider warming the gateway session before first user speech.
PIPECAT/SOTA: LiveKit prepareConnection (DNS/TLS + edge pick); OpenAI ephemeral-key prefetch off critical path; RFC8305 happy-eyeballs (250ms attempt-delay) is OPTIONAL for the single-URL WS (low value vs prewarm).
TARGET: shave cold DNS+TLS+token (100-400ms) off first-connect; connect timeout correctly bounds the 30s PROVIDER_READY; same-region health ping/pong 50-150ms.

=== D7. REST + WS CONNECTION POOLING — Tier-2 ===
WHAT: Python — pass httpx.Limits(max_keepalive_connections, max_connections, keepalive_expiry) to the AsyncClient (client.py:41 currently default/untuned) and KEEP the persistent client (it already memoizes one). TS — under Node, install a keepAlive Agent (undici/http.Agent with keepAlive:true) since it uses bare global fetch (client.ts:109, no agent) so REST calls reuse TCP/TLS; in browser, fetch keepalive is automatic. For WS: a small connect-concurrency cap + shared token-bucket client-side throttle (cooperating with the gateway's 60rps/burst10 governor, main.rs:273) so a burst of sessions doesn't self-DDoS into a multi-minute 429 storm (the measured failure). Honor the gateway's THREE connect-time rejections identically: per-IP 429 ("Too many connections", connection_limit.rs:71), global 503 ("Server at capacity") — back off, do NOT treat as fatal — and the tower_governor 429 + Retry-After (already handled by TS connection.ts:166; verify+extend to 503; verify Py's websockets upgrade captures the 429+Retry-After).
WHERE: python rest/client.py (httpx.Limits); TS rest/client.ts (Node keepAlive agent) + ws connect scheduler; connection.ts 429/503 handling.
GATEWAY LEVERAGE: cooperate with the documented governor + connection caps; no gateway change.
TARGET: REST calls reuse connections (no per-call TLS); a 20-concurrent SDK connect burst no longer storms >120s.

=== D8. OPUS/CODEC COMPRESSION (opt-in) — Tier-2 ===
WHAT: optional opus VOIP codec on the WS uplink (default KEEP raw PCM for back-compat), encode capture to opus 16-24kbps with DTX via a WASM encoder (opus-recorder / libopusjs) inside the worklet/Worker; decode opus TTS downlink on playout. Negotiate via the config flag echoed in the gateway `ready` ack so BOTH sides agree before any opus frame. This BEATS Pipecat (whose own WS path is raw PCM — opus only in its WebRTC transports).
WHERE: capture.worklet (encode) + player (decode) + config negotiation; gateway-side telephony opus/G.711 codec work already exists (infer/realtime notes) to build the gw decode/encode on.
GATEWAY LEVERAGE: reuse the existing gateway telephony codec path; gateway change LIKELY NEEDED to accept opus on the client /ws ingress + emit opus egress behind the negotiated flag (today STT ingress is raw PCM linear16, config.rs:290) — scope as a paired gw+SDK change, NOT SDK-only.
PIPECAT/SOTA: SOTA opus 20ms (~26.5ms delay) + DTX (1 frame/400ms during silence); ~10x egress cut (640B/20ms PCM -> ~60-80B opus).
TARGET: egress ~24kbps (from ~256kbps); near-silent cost during silence; adaptive drop to ~12kbps on bad networks.

=== D9. ADAPTIVE JITTER BUFFER + PLC — Tier-2 ===
WHAT: a NetEq-style adaptive playout buffer in the player: small initial buffer (~2-3 frames / 40-60ms), grow/shrink with measured inter-arrival jitter, reorder by timestamp, conceal late/lost frames by extrapolation, time-stretch WITHOUT pitch change to drain. Reference the pure-Rust `neteq` crate / WebRTC NetEq; 10ms GetAudio granularity. Size from observed variance, NOT a fixed delay.
WHERE: NEW typescript/src/audio/jitter-buffer.ts feeding the D2 scheduled player; widget equivalent. Build ON TOP of D2 (D2 is the prerequisite scheduling substrate).
GATEWAY LEVERAGE: note D2's client_playback_rate already smooths the rate-mismatch class of jitter server-side; the client jitter buffer handles NETWORK arrival variance D2 can't. Don't double-buffer.
PIPECAT/SOTA: WebRTC NetEq (adaptive buffer + PLC + time-stretch); Opus PLC.
TARGET: glitch-free up to moderate jitter with added latency <60ms.

=== D10. getUserMedia / DUPLEX-ECHO HARDENING — Tier-2 (small) ===
WHAT: keep echoCancellation/NS/AGC defaults true (already set, recorder.ts:127 — GOOD). WHERE: recorder.ts getUserMedia constraints + player output routing.

## Gateway leverage (do not reinvent)
LEVERAGE (don't reinvent) — the SDK COMPLEMENTS the gateway, never mirrors it:
1. tts_config.client_playback_rate (C-G5, config.rs:542, config_handler.rs:1511 EgressAudio resampler, valid 8000..=192000): set to the AudioContext sink rate -> gateway resamples downlink with CONTINUOUS filter state -> player does ZERO downlink resampling (kills a whole client resample stage + its boundary clicks). Highest-value leverage.
2. tts_config.audio_out_chunk_ms (E-G2, config.rs:533, WsEgressChunker): set ~20ms -> egress pre-framed into 20ms chunks so barge-in `clear` truncates within ONE chunk server-side AND chunks arrive pre-sized for D2 scheduled playout.
3. Server-side `alias` (one round-trip resolves {stt,tts,llm}) for fastest perceived connect; resolved_alias echoed on `ready` (config_handler.rs:463).
4. Gateway auto-pong (handler.rs:683) backs the Node native-ping watchdog; the SDK heals BEFORE the 300s idle-close (handler.rs:518) fires.
5. Gateway MessageClass drop-oldest discipline (messages.rs:458 DroppableAudio / Critical await): the SDK MIRRORS this on its uplink + tolerates dropped TTS frames (no per-frame delivery guarantee).
6. ONE-CONFIG-PER-SESSION (config_handler.rs:101): reconnect-then-fresh-config is the ONLY reconfigure path — encode in the API.
7. Gateway telephony opus/G.711 codecs (infer/realtime notes) back the D8 opus path.
DO NOT DUPLICATE (verified upstream-only — zero resume/session_token on the client wire): per-provider CircuitBreaker (circuit_breaker.rs FATAL fast-trip), process-wide ReconnectGovernor storm cap (reconnect_governor.rs), S2S conversation-replay (session.rs:426, 100 turns) + ResumptionHandle (session.rs:71, replayed into the PROVIDER's build_session_config, NEVER sent to client) + audio preroll (session.rs:805, 32KB). On a client<->gw drop there is NO server state to resume; existing reconnect->re-send-config->flush is correct + sufficient. Document this so nobody adds redundant client breakers. The SDK's D4 quick-failure breaker is the CLIENT analog (stops retrying a doomed CONFIG) — NOT a copy of the gateway's per-provider breaker.
ALREADY DONE (drop from plan): protocol_version is ALREADY asserted in BOTH SDKs (Py session.py:793-803, TS session.ts:333-342) — the W-K1 drift contract is LIVE, not inert.
GATEWAY CHANGES NEEDED: only D8 opus (accept opus on client /ws ingress + emit opus egress behind a negotiated config flag — today ingress is raw linear16, config.rs:290) — scope as a paired gw+SDK change. Everything in Tier-1 + the rest of Tier-2 is SDK-only.

## Appendix: research reports
### gateway-internals
I reviewed the WaaV gateway's client-facing wire protocol (/ws + /realtime), its server-side resilience stack (circuit breaker, reconnect governor, registry, ReconnectableStream, RealtimeSession supervisor), connection/rate limiting, and the audio/egress path, to determine exactly what the client SDK can RELY on, must COOPERATE with, and is leaving on the table.

THE CENTRAL FINDING: the gateway's heavyweight resilience — per-provider CircuitBreaker (FATAL fast-trip), process-wide ReconnectGovernor storm cap, conversation-replay, audio preroll, and the S2S ResumptionHandle — are ALL upstream-only (gateway↔provider, gateway/src/core/...). NONE of it is surfaced on the client-facing /ws or /realtime wire. There is NO resumption token, NO session-resume, NO connection-health signal, and NO in-band rate-limit/backpressure signal the SDK can consume. On a dropped client↔gateway socket the SDK starts a BRAND-NEW gateway session (server-side state is gone) and MUST re-send the full `config` message — exactly what the SDKs already do. So the SDK should NOT try to mirror breaker/governor/replay; instead it should (a) assert the one contract the gateway DOES expose — `protocol_version` on `ready` — which both SDKs currently capture but never assert; (b) cooperate precisely with the documented server limits/timeouts; (c) adopt the gateway's own server-side patterns (auto-pong, idle watchdog, drop-oldest egress, RAII teardown) for the SDK's own socket; and (d) LEVERAGE server-side audio knobs (`client_playback_rate`, `audio_out_chunk_ms`) instead of resampling/buffering client-side.

The gateway does NOT proactively send WS ping frames to clients on /ws or /realtime — axum only auto-pongs client pings (handler.rs:683). So the SDK cannot rely on server pings for liveness; an app-level zombie watchdog is genuinely needed and is the #1 gap.
RECOMMENDATIONS:
- ASSERT protocol_version on `ready` (do not just capture it). On `ready`, compare message.protocol_version against the SDK's bundled PROTOCOL_VERSION ('1.0'); on MAJOR mismatch emit a typed ProtocolVersionError / loud warning. This activates the W-K1 drift contract the gateway already built (messages.rs:38, :259) and is the cheapest, highest-leverage resilience win. Both SDKs currently leave it inert (TS session.ts:315, Python ws/session.py:238).
- ADD an app-level zombie/half-open watchdog on the SDK's own socket (Tier-1). The gateway does NOT ping clients (handler.rs:683), so a black-hole TCP path is invisible to native pong. Send a WS ping every ~15-20s, expect a pong within a deadline (Node `ws` pong event; browser native handles transparently — for browsers use a stale-inbound-data timer instead), and on miss terminate()+reconnect. Mirror the gateway's own auto-pong-and-keep-reading loop (scaffold/transport.rs:82). Also add a 'no inbound frame in N seconds' staleness timer well under the gateway's 300s idle close so the SDK proactively heals before the server kills it.
- TREAT /realtime error code:'connection_lost' (and the immediately-following Close) as a NON-recoverable upstream death — surface it distinctly and reconnect with a fresh config rather than silently streaming audio into a dead provider (realtime/handler.rs:738-761). On /ws, treat the 'Connection closed due to inactivity' and 'server shutting down' error texts as server-initiated closes that warrant immediate reconnect-with-config.
- DO NOT reimplement circuit-breaker / reconnect-governor / conversation-replay / resumption client-side — they are upstream-only and the gateway already owns them per-provider and process-wide (session.rs, circuit_breaker.rs, reconnect_governor.rs). On a client↔gateway drop the SDK has no server state to resume; the correct and sufficient behavior is the existing reconnect→re-send-config→re-flush-queue. Document this explicitly so nobody adds redundant client breakers.
- LEVERAGE the server-side audio knobs instead of doing the work in JS/Python: set tts_config.client_playback_rate to the client's fixed sink rate (e.g. 48000) so the gateway resamples egress with continuous filter state (config.rs:542-549) — removing client-side resampling; and set tts_config.audio_out_chunk_ms (e.g. 20) so barge-in `clear` truncates within one chunk (config.rs:533-540). This is faster + lower-jitter than an SDK-side jitter buffer for the common case.
- COOPERATE precisely with the three connect-time rejections: per-IP 429 ('Too many connections'), global 503 ('Server at capacity'), and the tower_governor token-bucket 429 (Retry-After/x-ratelimit-after). The TS path already does this for the upgrade 429 (connection.ts:160-174); extend the SAME handling to 503 (back off, do NOT treat as fatal) and ensure Python's WS connect path captures the upgrade-response 429+Retry-After identically (it has typed RateLimitError but verify the upgrade-status capture exists under websockets).
- RESPECT one-config-per-session: never send a 2nd `config` to live-reconfigure (the gateway rejects it, config_handler.rs:101). Any provider/voice/model change must open a NEW connection. Encode this in the SDK API so 'change voice mid-call' transparently reconnects.
- MIRROR the gateway's drop-oldest egress discipline on the SDK UPLINK and audio sink: bound the outbound audio queue and shed the OLDEST frame under backpressure (the gateway sheds stale audio: messages.rs:458-468), and on the playback side drop late TTS frames rather than letting latency accumulate — the gateway gives no per-frame delivery guarantee for DroppableAudio, so the player must be loss-tolerant.
- SURFACE config_warning to developers as a first-class typed event (both SDKs already do — keep it). It is the gateway's only channel for 'your setting was silently degraded' (alias_unknown, reasoning-on-voice-path, emotion-ignored, misnested keys). Recommend the SDK log these at WARN by default since they indicate likely-misconfigured sessions.
- OPTIMIZE connect-time (Tier-2) by pre-resolving DNS/TLS and reusing a warmed connection where possible, but note the dominant connect cost is server-side PROVIDER_READY (up to 30s for both STT+TTS to connect upstream, config_handler.rs:45) — so the SDK's connect timeout must be >30s, and for fastest perceived start prefer a server-side `alias` (one round-trip resolves the whole {stt,tts,llm} bundle) and consider warming the gateway session before first user speech.
- CLEAN UP protocol drift the assert would catch: remove the unreachable TS `case 'pong'`/handlePong/legacy pingInterval (gateway has no JSON ping/pong) and reconcile the `tts_audio` JSON handler with the reality that TTS audio arrives as raw BINARY frames (config_handler.rs:1498). Regenerate SDK message types from the committed docs/openapi.yaml so they stay in lock-step with PROTOCOL_VERSION.

Headline results: (1) CONNECT is fast and gateway overhead is NOT the bottleneck — warm connect()->ready p50 ~1.9ms (Py) / ~2.1ms (TS), cold 2.7ms (Py) / 12.6ms (TS, Node `ws` module warmup); the rate-limit/queue 'setup' is just object allocation at ~0.5-0.9 microseconds. (2) RECONNECT works end-to-end on BOTH SDKs: kill+restart recovers in ~1.65s (Py, attempt 4 of 200ms×1.5 backoff) and 252ms (TS, single 200ms backoff), config IS re-sent (proven by gateway log count 55->56 AND a fresh stream_id) and queued audio IS flushed (pending_audio 0). (3) ZOMBIE/half-open is the confirmed GAP: with the gateway SIGSTOP-frozen (TCP stays ESTABLISHED, no FIN/RST), Python reports connected=True for 30s (60/60 sends 'succeed', zero close/error/reconnect) and TS for 25s — neither detects the dead peer; Python's inherited websockets 20s ping_timeout did NOT fire and TS's Node `ws` has no ping configured at all. (4) RESOURCE: both TS and widget capture on the MAIN THREAD via deprecated ScriptProcessorNode; per-frame CPU is trivial (~6us) but the fixed input-latency floor is large (4096-buf = 85ms@48k, 256ms@16k); Python AudioProcessor is pure-Python (no numpy, 0.77ms per 4096-sample call) with per-call reallocation + bytes() copies. Bonus finding: a control-message queue ASYMMETRY — TS buffers both control+audio offline, but Python _send_json raises ConnectionClosedError on a dead socket (only audio buffers). Also: under default 60rps/burst10 limits a 20-concurrent connect burst yields only 3 OK / 17x429 and the SDK's 2^attempt backoff compounds into multi-minute storms.

RECOMMENDATIONS:
- KEEP this baseline harness as the regression gate: /tmp/waav_bench/run_all.sh is one command, key-free, on spare ports; re-run it after every Tier-1/Tier-2 change and diff the table. Snapshot binary at /tmp/waav-gw-snapshot makes the gateway side reproducible.
- Add an app-level LIVENESS/ZOMBIE watchdog to BOTH SDKs (the #1 gap): send a periodic app-level or WS ping and arm a pong-deadline (e.g. ping 5s / deadline 2-3s for voice); on deadline miss, force-close and trigger the EXISTING reconnect path. For TS, also pass `ws` ping options; for Python, set websockets ping_interval/ping_timeout far below the 20/20 default. After-metric: detection < ~3s in the SIGSTOP test (currently >30s / never).
- Cut reconnect first-hop latency for voice: drop the initial backoff to ~100-250ms with a fast first retry (and only then exponential), so the measured ~1.65s Python recovery approaches the ~250ms TS path. Voice tolerates an aggressive first reconnect.
- Move audio capture OFF the main thread to AudioWorklet in both the TS SDK (finish the already-stubbed workletNode at recorder.ts:65) and the widget, with a ScriptProcessor fallback only for old browsers. This removes main-thread contention jank; pair with a smaller worklet quantum (128 samples) to slash the 85-256ms fixed input-latency floor.
- Unify the offline message queue: wire ws/queue.py's MessageQueue into the Python session send path so control ops (speak/clear/send_message/config) buffer-and-flush like audio and like the TS SDK, instead of raising ConnectionClosedError on a dead socket. Make Python and TS behave identically.
- Add client-side connect coalescing / a shared token-bucket + jittered scheduling so a burst of sessions doesn't self-DDoS the gateway's 60rps/burst10 governor into multi-minute 429 storms; consider WS connection reuse/multiplexing or a small connect concurrency cap with full-jitter backoff (decorrelated jitter, not raw 2^attempt).
- Replace Python AudioProcessor internals with numpy (vectorized float32<->int16, resample, RMS) and avoid per-frame bytes() copies on the send path; ~13x per-frame speedup and far less GC pressure for high-frame-rate streaming.
- For super-realtime, adopt opus/codec compression on the wire (raw PCM today): a 20ms 16k mono frame is 640 bytes raw; opus at ~24-32kbps is ~60-80 bytes, ~8-10x less egress and lower jitter — gateway-side telephony codec work (opus/G.711/8-12kHz) already exists to pair with.
- Add a small adaptive jitter buffer on the TTS playback path (none today) so provider-side burst/gap variance doesn't cause underruns; size it from observed inter-arrival variance rather than a fixed delay.
- Benchmark the audio=true connect path next (provider construction is the real connect-tail cost the audio=false isolation deliberately excluded) once a key-free local STT/TTS or mock provider is wired, so the 'cold connect with providers' number is also tracked.

### sota-research
I surveyed the production-grade voice client SDKs (LiveKit JS/Android, Daily/Pipecat, Vapi, Retell, OpenAI Realtime, Twilio Voice.js) and the underlying WebRTC/WebSocket/Opus/NetEq standards, and cross-checked each against the audited WaaV SDK code and the WaaV gateway. The headline gap is that every mature SDK runs a WebRTC-grade audio + transport stack — off-main-thread AudioWorklet capture at 10-20ms frames, Opus on the wire (6-32kbps voice) with DTX, an adaptive NetEq-style jitter buffer + PLC on playout, ICE/region pre-warm at page load, and an app-level heartbeat that detects zombie/half-open sockets in seconds — whereas WaaV's WS-only SDKs still capture on the MAIN thread via the deprecated ScriptProcessorNode (TS recorder.ts:175 + widget recorder.ts:56), ship raw 16-bit PCM (~256kbps mono @16kHz), have NO jitter buffer / PLC, do NOT pre-warm the connection (only a 10s connect timeout, connection.ts:35), and — critically — have NO app-level liveness ping (TS deliberately removed JSON ping, session.ts:203-205; gateway only auto-replies to native pings, handler.rs:683-685), so a half-open socket where the OS never fires `close` is invisible until TCP times out (minutes). Reconnect also re-runs a full `connect()` with NO session-resume token (python session.py:962-1000; ts reconnect.ts), so every blip restarts the conversation. The good news: WaaV already has best-in-class backoff+jitter (30s cap / 10 retries, 1.5x), typed RateLimitError with Retry-After, a bounded drop-oldest queue, and config-restore+queue-flush on reconnect — and the gateway already owns the hard server-side resilience (circuit breaker, reconnect governor, S2S replay/resumption handles, telephony Opus/G.711 codecs). The SDK should COMPLEMENT that: the five concrete wins are (1) AudioWorklet capture at 20ms frames, (2) an app-level heartbeat/zombie watchdog, (3) connect-time pre-warm (DNS/TLS/token prefetch + warm-spare socket), (4) opt-in Opus encoding with DTX, (5) an adaptive playout jitter buffer + PLC. Target numbers below are drawn from the SOTA sources (OpenAI: first-audio 200-350ms, ping/pong 50-150ms same-region; Twilio: 30s signaling-reconnect window, ICE-restart after 15s gather-fail; RFC8305: 250ms happy-eyeballs delay; NetEq: 10ms GetAudio granularity; Opus: 20ms frame ~26.5ms delay, DTX 1 frame/400ms).
RECOMMENDATIONS:
- TIER-1 #1 (highest ROI): App-level heartbeat + zombie/half-open watchdog. In all three SDKs, add a client ping loop (default interval ~20s, configurable to 75% of the deployment's proxy idle timeout) that expects a pong within ~10s; on a missed pong, force-close and trigger the existing reconnect path immediately instead of waiting for TCP timeout. Use the gateway's native WS ping frames where the runtime allows sending them (Node ws / python websockets do; browsers cannot send raw pings, so add a tiny JSON {type:'ping'} op to the gateway and reply {type:'pong'} — the gateway already has a 'pong' handler stub the Python SDK listens for at session.py:900). Also send an immediate ping on document 'visibilitychange'/foreground. This is the cheapest fix and closes the worst correctness gap.
- TIER-1 #2: AudioWorklet capture at 20ms frames (replace ScriptProcessorNode). Ship an AudioWorkletProcessor that runs on the audio render thread, accumulates 128-sample render quanta into 320-sample (20ms@16kHz) frames, and posts them to the main thread via transferable ArrayBuffers (zero-copy). Wire the already-present-but-unused `workletNode` field (recorder.ts:65) and delete the ScriptProcessor path; keep ScriptProcessor only as a legacy fallback behind a capability check. Do the same in the widget. Target: 20ms input cadence (down from ~256ms) and main-thread freed for UI/decode.
- TIER-1 #3: Connect-time pre-warm. Add a public `prewarm()`/`prepareConnection()` (mirroring LiveKit) that, on page load / SDK init, does DNS+TLS warmup (a HEAD/preconnect to the gateway origin) and pre-fetches any auth/ephemeral token in parallel, optionally opening a warm-spare WS so the first user action attaches to an already-open socket. Keep the 10s timeout as the failure bound. Target: shave the cold DNS+TLS+token RTTs (typically 100-400ms) off first-connect; aim for same-region ping/pong 50-150ms as the health check.
- TIER-1 #4: Reconnect-with-session-resume. Have the SDK persist the gateway-issued stream_id/resumption handle (the gateway's S2S scaffold already exposes 'resumption handles' + 'conversation replay' per core/realtime/scaffold/session.rs) and pass it on reconnect (query param or first config msg) so the gateway re-attaches the existing conversation + replays missed events, instead of the current full restart (python session.py:962-1000 re-runs connect()). Carry a last-received-sequence so the server can replay only the gap. This turns a blip from 'conversation lost' into 'seamless resume'.
- TIER-2 #5: Opt-in Opus encoding with DTX on the wire. Add a codec option (default keep PCM for back-compat) that encodes capture to Opus VOIP at 16-24kbps with DTX via a WASM encoder (opus-recorder/libopusjs) in the worklet/Web Worker, and decodes TTS Opus on playout. Gate it on a config flag echoed in the gateway 'ready' ack so both sides agree; the gateway already has Opus/G.711 telephony codecs to build the decode/encode path on. Target: ~10-30x egress bandwidth cut (256kbps PCM → ~24kbps), near-silent cost during silence via DTX, and adaptive bitrate (drop to ~12kbps) on detected bad networks.
- TIER-2 #6: Adaptive jitter buffer + PLC on playout. Add a NetEq-style adaptive playout buffer in the audio player: target a small initial buffer (~2-3 frames / 40-60ms), grow/shrink with measured jitter, reorder by timestamp, conceal late/lost frames via extrapolation, and time-stretch without pitch change to drain. Reference the pure-Rust `neteq` crate / WebRTC NetEq design; pull 10ms per GetAudio. Target: glitch-free playout up to moderate jitter while keeping added latency under ~60ms.
- TIER-2 #7: Network-change-driven proactive reconnect. Subscribe to window 'online'/'offline' and navigator.connection 'change' (effectiveType/type) in the browser SDKs and to OS network-change signals where available; on a change, proactively re-validate the socket (immediate heartbeat) and reconnect/resume rather than waiting for the next failure. Mirror Twilio's 'ICE restart after 15s gather-fail / 30s signaling reconnect window' bounds for the WS-resume timeout.
- TIER-2 #8: Duplex echo hardening for agent audio. Document and mitigate the browser-AEC blind spot: route TTS playback through a path the AEC can observe (or expose a flag to do so), offer voiceIsolation on iOS as an opt-in getUserMedia constraint, and keep echoCancellation/NS/AGC defaults (already true). This prevents the agent hearing itself when TTS is scheduled via raw AudioContext buffers.
- TRANSPORT (strategic, beyond Tier-1/2): Plan an optional WebRTC transport (smallwebrtc/LiveKit-style) as the long-term ceiling — it gives Opus, NetEq, ICE restart, congestion control, and native AEC visibility for free and is what every low-latency SOTA client uses for browsers. The four Tier-1/2 audio+resilience ports above are the pragmatic 80% that work on the existing WS transport now; WebRTC is the follow-on once they ship.
- Adopt explicit target SLOs from the SOTA sources so the optimization is measurable: time-to-first-connect (warm) < ~300ms; first-audio (TTS TTFB) 200-350ms; same-region health ping/pong 50-150ms; input frame cadence 20ms; added playout latency from jitter buffer < 60ms; zombie-socket detection < ~30s (vs minutes today); egress bandwidth ~24kbps with Opus (vs ~256kbps PCM). Wire these into the existing MetricsCollector (python session.py:70+, ts metrics/collector.ts) which already tracks ws_connect_ms / tts_ttfb / e2e_latency.
