# Interaction Mode

Interaction mode is an opt-in behaviour for `/ws` voice sessions, including those whose caller is in a LiveKit room or on a phone line, for voice-agent sessions on `/v1/realtime` (see [OpenAI Realtime Clients](#openai-realtime-clients)), and for speech-to-speech sessions on `/realtime` and the `/v1/realtime` relay, where the provider keeps its own voice (see [Speech-to-Speech Providers](#speech-to-speech-providers)). A fast "front" keeps the conversation alive: it acknowledges what the caller said, asks for confirmations and handles interruptions. A slower background (an LLM, a voice agent, or a backend of the operator's) does the actual request as a "task", and its answer is relayed to the caller word for word, sentence by sentence. A session that does not ask for the mode is never touched by it.

## Overview

A session runs interaction mode when all of the following hold:

- **The server switch is on** - `interaction.enabled` in the server config file, off by default.
- **The session asks for it** - its `config` message carries `"interaction": true` or an object of settings, or its alias definition has an `interaction` block, or the server has an `interaction.default` block.
- **There is a background** - the session's `conversation_config`, or else `interaction.tasks.llm` in the same shape, or a backend of the operator's that the block names (see [Operator Backends](#operator-backends)), or the session's Bud voice agent (see [Voice-Agent Sessions](#voice-agent-sessions)), or the session's DAG when it ends in text (see [DAG Sessions](#dag-sessions)).
- **It is an audio session** - audio is on. The caller's audio comes over the socket or, with a `livekit` block, from a room (see [LiveKit Rooms and Phone Calls](#livekit-rooms-and-phone-calls)).
- **Its speech-to-text can end one utterance and keep listening** - a provider that returns one transcript per connection is refused.
- **Its language has a pack** - `stt_config.language` is empty or starts with `en` (the built-in English pack), or its primary subtag is the language of a pack the operator loaded (see [Language Packs](#language-packs)).

A session that asked and cannot have the mode runs exactly as it would have without the value, and one `config_warning` message says why:

| `code` | `detail` | When |
|--------|----------|------|
| `interaction_disabled_by_server` | `path: "interaction"` | The server switch is off. |
| `interaction_value_ignored` | `path: "interaction"` | The value is neither `true`, `false` nor an object. |
| `interaction_needs_background` | `surface: "ws"`, `reason: "no_background"` | There is no `conversation_config`, no usable `interaction.tasks.llm` and no named backend. |
| `interaction_dag_audio_output` | `surface: "ws"`, `reason: "dag_audio_output"` | The session's DAG produces audio itself: it has an `audio_output`, a `tts_provider` or a `realtime_provider` node. |
| `interaction_dag_no_text_output` | `surface: "ws"`, `reason: "dag_no_text_output"` | The session's DAG has no `text_output` node. |
| `interaction_surface_unavailable` | `surface: "ws"`, `reason` | `reason` is `agent` (a voice agent that answers in text only or takes manual turns), `dag_config` (the DAG could not be read; an `error` says why), `audio_disabled`, `stt_file_only` (the speech-to-text cannot keep listening, or its model transcribes files only: Deepgram's `whisper-*`), `language_unsupported` (no pack speaks the session language) or `background_unavailable` (the background LLM or the voice agent could not be set up). |
| `interaction_override_refused` | `path: "interaction"` | A voice-agent session sent its own `interaction` value and the agent does not allow that. |
| `truth_ack_required`, `interaction_needs_background`, `interaction_unsupported` and the other codes of [Speech-to-Speech Providers](#speech-to-speech-providers) | `surface: "realtime"`, `provider`, `verbs` | A `/realtime` session that cannot run the mode (sent as `warning`). |
| `interaction_language_step_down` | `surface: "ws"`, `pack: "en"` | Sent during the call: the caller kept speaking another language (see [Another Language](#another-language)). |
| `caller_identity_rejected` | `path: "interaction.front.caller.identity_token"` | The identity token is not valid for this tenant now: the call runs without caller memory. |
| `caller_memory_unavailable` | `path: "interaction.front.caller.identity_token"` | The server keeps no caller memory. |

A session that only received the server's `default` or `agent_default` block did not ask, so it gets no warning.

## Enabling Interaction Mode

### Server Settings

The settings live under the `interaction` key of the YAML file given with `--config`. Each environment variable overrides its YAML key. A problem in the block is logged at startup and never stops the server. A YAML block that does not parse, for example one with an unknown key, is ignored as a whole; the environment variables still apply.

| YAML key | Environment variable | Default | Meaning |
|----------|----------------------|---------|---------|
| `interaction.enabled` | `WAAV_INTERACTION_ENABLED` | `false` | The server switch. |
| `interaction.default` | `WAAV_INTERACTION_DEFAULT` (JSON) | none | `true` or an object: the block of a session that sends none, and the base of every session's own block. With it set, every `/ws` session that fits runs the mode. |
| `interaction.agent_default` | `WAAV_INTERACTION_AGENT_DEFAULT` (JSON) | none | `true` or an object: the block of a Bud voice-agent session whose agent entry carries none. |
| `interaction.front_model.url` | `WAAV_INTERACTION_FRONT_URL` | none | The llama-server of the front model, which decides every caller turn in context and words the front's lines. Interaction mode needs it: without a ready front model a session that asks for the mode gets `config_warning` `interaction_refused` (reason `front_unavailable`) and runs without it (see [Conversation Controls](#conversation-controls)). |
| `interaction.front_model.model` | `WAAV_INTERACTION_FRONT_MODEL` | none | The model name sent to that server. It needs the URL. |
| `interaction.front_model.api_key` | none | none | A key for that server. |
| `interaction.front_model.command` | `WAAV_INTERACTION_FRONT_COMMAND` (space-separated) | none | The gateway runs that server itself with this command (the program, then its arguments; it must listen at `front_model.url`) and restarts it (see [The Front Model's Server](#the-front-models-server)). It needs the URL. |
| `interaction.front_model.licence` | `WAAV_FRONT_LICENCE` | none | `lfm_open_eligible` or `liquid_commercial`: the operator states that it may run LFM weights. Another value is dropped with a line in the log. |
| `interaction.tool_secret` | `WAAV_INTERACTION_TOOL_SECRET` | none | Signs the HTTP calls of the operator's tools (see [Tools](#tools)). |
| `interaction.allow_client_tools` | `WAAV_INTERACTION_ALLOW_CLIENT_TOOLS` | `false` | Accept `interaction.tasks.tools` from a session. It is never accepted under the Bud control plane. |
| `interaction.task_redis_url` | `WAAV_TASK_REDIS_URL` | none | A Redis that the gateway processes of one deployment share for their tasks (see [Several Gateway Processes](#several-gateway-processes)). Without it tasks are kept in each process. It is not `WAAV_REDIS_URL`, which belongs to the Bud control plane. |
| `interaction.task_backends` | `WAAV_INTERACTION_TASK_BACKENDS` (JSON list) | `[]` | The operator's backends: a webhook, an A2A agent, an MCP task tool or an OpenAI Responses model (see [Operator Backends](#operator-backends)). An entry that cannot work is dropped with a line in the log. |
| `interaction.allow_client_backends` | `WAAV_INTERACTION_ALLOW_CLIENT_BACKENDS` | `false` | Let a session name one of those backends itself. It is never accepted under the Bud control plane. |
| `interaction.allow_resume_key` | `WAAV_INTERACTION_ALLOW_RESUME_KEY` | `false` | Let a session bring `tasks.resume_key` (see [Coming Back](#coming-back)). |
| `interaction.allow_client_push` | `WAAV_INTERACTION_ALLOW_CLIENT_PUSH` | `false` | Let a session name its own `tasks.push_url`, signed with its own `tasks.push_secret` (see [The Push](#the-push)). Never under the Bud control plane. |
| `interaction.tenant_personas` | `WAAV_INTERACTION_TENANT_PERSONAS` | `false` | Tenants register their own personas, and their sessions select them by id (see [Personas](#personas)). |
| `interaction.caller_memory_key` | `WAAV_INTERACTION_CALLER_MEMORY_KEY` | none | Caller memory: the key the operator signs caller identity tokens with (see [Caller Memory](#caller-memory)). Without it the gateway keeps nothing about callers. |
| `interaction.truth_ack` | `WAAV_INTERACTION_TRUTH_ACK` (comma-separated) | `[]` | The speech-to-speech providers, as `provider` or `provider:model`, whose own speech the operator accepts as monitored rather than enforced. Interaction mode runs on a speech-to-speech provider only when it is listed (see [Speech-to-Speech Providers](#speech-to-speech-providers)). |
| `interaction.realtime_default` | `WAAV_INTERACTION_REALTIME_DEFAULT` (JSON) | none | `true` or an object: the block of every `/v1/realtime` relay session (a Bud realtime deployment whose vendor speaks OpenAI Realtime; not a standalone alias's `realtime` block). |
| `interaction.packs_dir` | `WAAV_INTERACTION_PACKS_DIR` | none | A directory of language packs, read once when the first session needs a pack (see [Language Packs](#language-packs)). |
| `interaction.clips_dir` | `WAAV_INTERACTION_CLIPS_DIR` | none | Recorded listening sounds per provider, voice and language, which replace the rendered ones (see [Listening Sounds](#listening-sounds)); also the recorded and the cached lines said when a service fails (see [When Services Fail](#when-services-fail)). |
| `interaction.failure_voice` | `WAAV_INTERACTION_FAILURE_VOICE` (JSON) | none | The server's default voice, in the shape of `tts_config` with PCM audio: the lines said when a service fails are made in it once at server start, for sessions whose own voice cannot give them (see [When Services Fail](#when-services-fail)). |
| `interaction.realtime_legacy_wire` | `WAAV_REALTIME_LEGACY_WIRE` (comma-separated) | `[]` | Escape flags of the speech-to-speech provider wire fixes (see [Provider Fixes](#provider-fixes)). An unknown name is dropped with a line in the log. |
| `interaction.provider_fixes` | `WAAV_PROVIDER_FIXES` (comma-separated) | `[]` | Provider wire fixes and default moves to turn on before their vendor's live probe (see [Provider Fixes](#provider-fixes)). Each is off unless listed, but `deepgram_user_text`, whose probe passed. An unknown name is dropped with a line in the log. |
| `interaction.provider_fixes_per_session` | `WAAV_PROVIDER_FIXES_PER_SESSION` | `false` | A `/realtime` session's config may also turn a fix on (it may always turn one off; see [Provider Fixes](#provider-fixes)). |

An alias definition (the `aliases:` section of the same file) may carry an `interaction` block. It stands in for a session that names the alias and sends no block of its own; the session's own value, including `false`, wins.

### Session Config

Send `interaction` in the `config` message. `true` takes the defaults:

```json
{
  "type": "config",
  "stt_config": { "provider": "openai", "model": "whisper-1", "language": "en", "sample_rate": 16000, "channels": 1, "punctuation": true, "encoding": "linear16" },
  "tts_config": { "provider": "openai", "model": "tts-1", "voice_id": "your-voice-id", "audio_format": "pcm", "sample_rate": 24000 },
  "conversation_config": { "base_url": "http://127.0.0.1:18742/v1", "model": "qwen3b-q4_k_m", "api_key": "local-dummy" },
  "interaction": true
}
```

An object sets individual keys. This one declares a tool that the caller must confirm before it runs (the server needs `allow_client_tools`):

```json
{
  "interaction": {
    "front": { "persona": "northwind-travel-ava" },
    "tasks": {
      "tools": [{
        "name": "book_table",
        "description": "Book a table",
        "parameters": { "type": "object", "properties": { "party": { "type": "integer" } }, "required": ["party"] },
        "url": "https://tools.example.com/book",
        "side_effects": true,
        "confirm_phrase": "book a table",
        "progress_phrase": "Booking the table"
      }]
    },
    "policy": { "hitl_answer_timeout_ms": 30000 }
  }
}
```

### Voice-Agent Sessions

A session whose `config` carries an `agent` block is served by a Bud voice agent. It runs interaction mode when a block is set for the agent. The block is taken from the first of these that exists:

1. **The session's own `interaction` value** - only when the agent's `session_overrides` list contains `interaction`. Otherwise the value is ignored with warning `interaction_override_refused`, also when it is `false`.
2. **The agent entry's `interaction` field** - published with the agent (`true` or an object).
3. **The server's `interaction.agent_default`** - the operator's block for agents whose entry has none.

The server's `interaction.default` is never the block of a voice-agent session, but it is still the base that the chosen block is laid over. `stt_config`, `tts_config` and the `agent` block are sent as on any voice-agent session:

```json
{
  "type": "config",
  "agent": { "id": "support" }
}
```

In this mode each request of the caller becomes one run of the agent, and the front speaks while the run works. The differences from a session with a `conversation_config` are:

- **One run at a time** - the agent's conversation takes one run at a time. A request made while a run works is queued, and a correction restarts the run after the earlier one was cancelled. No run is started before the caller's turn is settled: `tasks.speculative_start` is always `off` (an explicit `on` gives `interaction_value_ignored`).
- **When the answer is spoken** - the gateway cannot tell an agent's draft from its answer until the run completes. By default the text the agent wrote after its last tool call is spoken when the run completes. When `background.answer_marker` is set, the text after that line is spoken sentence by sentence while the agent writes it; an agent that leaves the marker out is spoken when its run completes.
- **Tools** - the agent runs its own tools. `tasks.tools` and `tasks.llm` are ignored, so there is no confirmation by voice and no `ask_caller`. A task's `effects` lists the agent's tool calls: `used <tool>` for one that ran, `tried <tool>` for one that failed and `started <tool>` for one that was running when the task was cancelled. A cancelled task says "It's stopped." only when no tool call was seen. A task's `kind` is `action` unless the agent has no tools.
- **Approval** - when the Bud gateway holds a run for a person's approval, the task fails with a `summary` that starts with `approval_required` and the caller hears "That needs someone's approval first, so I haven't done it."
- **Interruptions** - a caller who talks over an answer stops the speech, not the run. The agent's next run is told how much of the answer the caller heard, as the plain voice-agent path does. An agent with `interruption.enabled: false` starts with `duplex.barge_in: false`.
- **Greeting and limits** - the agent's static greeting is spoken after `ready`, and its `limits.max_session_seconds` still ends the session.
- **Structured output** - for an agent with a `speak_field`, that field is spoken.
- **Another language** - a stepped-down session (see [Another Language](#another-language)) keeps the agent's conversation and its history.

These parts of a voice-agent session do not apply in interaction mode: the agent's filler messages (the front speaks instead), `idle.end_after_silence_ms`, `interruption.min_words` and `interruption.ignore_phrases`, the `truncate` message, and the `agent_response_started`, `agent_response_created`, `agent_tool`, `agent_output`, `agent_response_done`, `agent_truncated` and `agent_error` messages (the task events take their place).

### DAG Sessions

A session with a `dag_config` runs interaction mode when its graph ends in text: it has a `text_output` node and no node that produces audio. The graph is then the background.

```json
{
  "type": "config",
  "stt_config": { "provider": "deepgram", "model": "nova-3", "language": "en", "sample_rate": 16000, "channels": 1, "punctuation": true, "encoding": "linear16" },
  "tts_config": { "provider": "openai", "model": "tts-1", "voice_id": "your-voice-id", "audio_format": "pcm", "sample_rate": 24000 },
  "dag_config": { "template": "support-text" },
  "interaction": true
}
```

- **One run per task** - the graph runs once for each request of the caller, from the node after its `stt_provider` node, with the request as the transcript. Without the mode it runs once per spoken turn. A correction runs it again with the request and a line `Correction: ...`.
- **The answer** - every text a `text_output` node emits is spoken, sentence by sentence, in the session's own voice (`tts_config`). It is not sent as a `message` with topic `dag_output`. An `llm_endpoint` node with `streaming: true` gives its sentences as they are written.
- **One run at a time** - a request made while a run works is queued. `tasks.speculative_start` is always `off` (an explicit `on` gives `interaction_value_ignored`), and `tasks.tools`, `tasks.llm` and a `conversation_config` are ignored: the graph's own nodes do the work. There is no confirmation by voice and no `ask_caller`.
- **Tasks** - a task's `background` is `dag` and its `kind` is `lookup`, unless the graph has an endpoint node (`http_endpoint`, `grpc_endpoint`, `web_socket_endpoint`, `ipc_endpoint`, `live_kit_endpoint`) or a `webhook_output` node: then it is `action`, and a repeated request is asked about (see [Repeated Requests](#repeated-requests)).
- **Another language** - there is no plain conversation to step down to: the agent keeps asking the caller to repeat.
- **A graph that speaks itself** - a graph with an `audio_output`, a `tts_provider` or a `realtime_provider` node is refused with `interaction_dag_audio_output` and runs as a plain DAG session.

### Operator Backends

A session's tasks can run outside the gateway: on a webhook, on an Agent2Agent (A2A) agent, on a tool of a Model Context Protocol (MCP) server, or on a model behind the OpenAI Responses API. The operator lists these backends in the server config file; a block names one with `tasks.default_backend`. The address and the secret never leave the server.

```yaml
interaction:
  enabled: true
  allow_client_backends: true
  task_backends:
    - name: "crm"
      type: "webhook"
      url: "https://crm.example.com/waav/tasks"
      secret_env: "CRM_WEBHOOK_SECRET"
```

A session with speech-to-text and text-to-speech only then needs no LLM of its own:

```json
{
  "type": "config",
  "stt_config": { "provider": "deepgram", "model": "nova-3", "language": "en", "sample_rate": 16000, "channels": 1, "punctuation": true, "encoding": "linear16" },
  "tts_config": { "provider": "openai", "model": "tts-1", "voice_id": "your-voice-id", "audio_format": "pcm", "sample_rate": 24000 },
  "interaction": { "tasks": { "default_backend": "crm" } }
}
```

| Key of an entry | Used by | Meaning |
|-----------------|---------|---------|
| `name` | all | What a block calls it: 1 to 64 lower-case letters, digits, `_` or `-`. Required. |
| `type` | all | `webhook`, `a2a`, `mcp` or `openai_responses`. Required. |
| `url` | all | An `http://` or `https://` address. Required. For `openai_responses` it is the API base (`https://api.openai.com/v1`). |
| `secret_env` | all | The environment variable that holds the secret: the signing secret of a webhook (without it the server's `tool_secret` signs), the bearer token of the others. Also accepted as `bearer_env` and `api_key_env`. |
| `side_effects` | `webhook`, `a2a`, `mcp` | `possible` (the default) or `none`. With `none` a task's `kind` is `lookup` and a cancel is confirmed at once. |
| `tool`, `argument` | `mcp` | The tool that does the task (required unless the entry has `tools`), and the name of its argument that carries the caller's request (`request` when not set). |
| `tools` | `mcp` | For an orchestrator (see [Agents That Describe Themselves](#agents-that-describe-themselves)): the server's tools it may call, each as a tool of its own: `["*"]` for every tool the server lists, or up to 32 names. An entry with `tools` and no `tool` runs only as an orchestrator's agent. |
| `catalog_ttl_s` | `a2a`, `mcp` | How long the Agent Card or the tool list a session's start read serves later sessions of the gateway process. 300 when not set. |
| `confirm` | all | Whether an orchestrator's call of the entry is confirmed with the caller before it is sent, over what `side_effects` and an MCP tool's annotations say: `true` or `false` for every call, or an object of MCP tool names (`{"archive_note": false}`); a tool it does not name is decided as without it. |
| `model` | `openai_responses` | The model the requests name. Required. |
| `mode` | `openai_responses` | `poll` reads each response until it is done. Without it the response is streamed. |
| `description` | all | One sentence an orchestrator reads to choose the entry, for example `Operates websites in a browser: bookings, forms, purchases.` (see [Many Agents](#many-agents)). |
| `max_concurrent` | all | How many tasks of one session run on the entry at once; more wait in a queue. No limit when not set. |
| `timeout_s` | `webhook`, `a2a`, `mcp` | How long a task may take before it fails. 600 when not set. |
| `question_deadline_ms` | all | How long the caller has to answer a question of the entry's: at most the session's `policy.hitl_answer_timeout_ms`. A question's own `expires_in_ms` wins. Either is the job's deadline: it is never moved, and a question that cannot wait for the end of the agent's answer breaks into it (see [Questions With a Deadline](#questions-with-a-deadline)). |
| `fallback` | all | The name of another entry that takes an orchestrator's new tasks while this one's breaker is open. An entry the list does not have is dropped from it, with a finding at startup. |
| `oauth` | `mcp`, `a2a` | An OAuth 2.0 client whose access token the gateway fetches and renews (see [MCP Task Tool](#mcp-task-tool)): `token_url`, `client_id`, `client_secret_env` (the environment variable of its secret), optional `scope` and `resource`. Not with `secret_env`. An A2A entry may leave `token_url` out: its card names it (see [A2A Agent](#a2a-agent)). |
| `push_base_url` | `a2a` | The gateway's own address as the agent reaches it, for the agent's push notifications (see [A2A Agent](#a2a-agent)). |

- **Who may name a backend** - the server's `default` and `agent_default` blocks and an alias definition always. A session's own block only with `allow_client_backends`; otherwise the key gives `interaction_override_refused`. A name the list does not have gives `interaction_value_ignored`.
- **Which background wins** - a named backend does the tasks even when the session also has a `conversation_config`. A voice-agent session and a DAG session ignore the name.
- **Several backends** - `tasks.backends` lists the entries the session's tasks may run on, chosen per request. With `tasks.orchestrator` they join its agents and it chooses. Without one, a single entry (counting a `default_backend`) does every task; several are chosen among by the session's own LLM (its `conversation_config` model, else `tasks.llm`) as their orchestrator, from each entry's `description` or card (see [Many Agents](#many-agents)); a session with no LLM has the first listed do every task, with `interaction_value_ignored`. A speech-to-speech session has its named backend, else the first listed, do its tasks (the others: `interaction_value_ignored`). A voice-agent or DAG session ignores the list.
- **A webhook, an A2A agent and an MCP tool run the task themselves** - several tasks at once (at most `max_concurrent`; more wait in a queue). `tasks.tools`, `tasks.llm` and `ask_caller` do not apply, and `tasks.speculative_start` is always `off`. The answer is spoken when the backend returns it, sentence by sentence, after the same checks as any answer (see [What Is Never Spoken](#what-is-never-spoken)).
- **Progress** - what the backend says it is doing is the `text` of a `task_progress` event, and is spoken like a tool's `progress_phrase`.
- **Questions** - a question of the backend's is a `task_question`, asked and answered like one of `ask_caller` (see [Confirmation](#confirmation)); the answer goes back to the backend.
- **Effects** - a webhook reports what it changed, and that is the task's `effects`. An A2A agent and an MCP task tool do not: with `side_effects: possible` the `effects` of their tasks are `"unknown"` from the moment the backend has the task (an orchestrator's call of an MCP server's tool says it ran, see [MCP Task Tool](#mcp-task-tool)).
- **Cancelling** - the backend is told. With `side_effects: possible` the task is `cancelled` only when the backend confirmed (within 8 seconds), with the effects it reported. A backend that does not confirm leaves a cancelled task with `effects: "unknown"`, and the caller hears "I've stopped it, but I can't confirm whether it had already gone through."
- **A backend that gives no result** - a task ends `failed` after `timeout_s` (10 minutes), or after three reads in a row that failed. A task on an entry with `side_effects: none` that could not reach the backend, or got nothing back in time, is tried once more.
- **An entry that keeps failing** - each entry has a breaker, shared by the sessions of the gateway process: after 3 of its last tasks (at least half) could not reach it or got nothing in time, it gets no task for 30 seconds, then one task tries it. A task started meanwhile fails at once and the caller hears "Sorry, I couldn't get that done just now."; an orchestrator's new task goes to the entry's `fallback`. No other entry is affected.
- **Another language** - there is no plain conversation to step down to: the agent keeps asking the caller to repeat.

#### Webhook

Every message of the gateway is a `POST` to the entry's `url`, signed like a tool call (see [Tools](#tools)) with the entry's secret. `Idempotency-Key` is `<task_id>:<revision>:<type>`, and for an answer also `:<request_id>`.

| Message | Body | When |
|---------|------|------|
| `task` | `type`, `task_id`, `revision`, `request` (the caller's request; a correction follows on a line that starts `Correction:`), `history` (up to 12 earlier turns as `role` and `content`), `callback` (`/v1/tasks/<task_id>/callback`), and for a follow-up `follows` (the `task_id` of the finished task it continues) | A task starts, or the caller corrected it (a new `revision`). |
| `answer` | `type`, `task_id`, `revision`, `request_id`, `outcome` (`accept`, `decline`, `timeout`, `cancel`), `value` (a choice or a value), `operation_id` (a confirmed action) | The caller answered the webhook's question, or did not. |
| `cancel` | `type`, `task_id`, `revision` | The task was cancelled or replaced. The reply should end with `cancelled`. |

The reply to each message is one event or a list of events; an empty reply means "taken". The webhook can send the same events later, signed the same way, to the gateway's callback route:

```text
POST /v1/tasks/<task_id>/callback
X-WaaV-Timestamp: <unix seconds>
X-WaaV-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>" keyed with the entry's secret>

{"type": "result", "text": "Order A 17 ships on Friday."}
```

| Event | Fields | Meaning |
|-------|--------|---------|
| `progress` | `text` | What is being done. |
| `effect` | `label` | Something was changed. The label completes "it had already ...", for example `booked a table for 2`. |
| `question` | `request_id`, `kind`, and `action` with `arguments` (kind `confirm`), `prompt` with `options` (kind `choose` or `value`), `prompt` with `schema` (kind `form`) or `prompt` with `url` (kind `auth_url`); `sensitive`; `expires_in_ms` (optional: the answer is needed within this time) | Ask the caller. A `confirm` is read back like a tool call and needs a clear "yes". A `form` and an `auth_url` are answered on the client's screen. |
| `result` | `text` | The answer: the task is `completed`. |
| `failed` | `error` | The task is `failed`. |
| `cancelled` | none | The task stopped. |
| `control` | `kind`, `value`, `request_id` | A conversation control (see [Conversation Controls](#conversation-controls)). The gateway posts a `control_applied` message back (the `control_applied` event's fields and the `request_id`); its reply is read like any other. |

The callback route answers `202` when the events were taken, `401` for a missing or wrong signature, a timestamp more than five minutes off, or a backend with no secret, `404` when no run of this gateway process waits for the task, `409` when an event's `revision` is not the task's current one, and `400` for a body that is not an event or a list of events. The route takes no API key: the signature is its authentication.

#### A2A Agent

The gateway speaks A2A 1.0 (`A2A-Version: 1.0`, and `Authorization: Bearer` with the entry's secret) on the binding the agent's card names: JSON-RPC (the default, and without a card), HTTP+JSON or gRPC. A task is one `SendMessage` with `returnImmediately`; the gateway then reads it with `GetTask` twice a second.

- **Bindings** - the card's interfaces (1.0 `supportedInterfaces[].protocolBinding`, 0.3 `preferredTransport`/`additionalInterfaces[].transport`) on the entry's own origin are used, JSON-RPC first, then HTTP+JSON, then gRPC; a gRPC interface may be on another port of the entry's host. HTTP+JSON is `POST <url>/message:send` (and `/message:stream`, whose server-sent events are the results themselves), `GET <url>/tasks/{id}`, `POST <url>/tasks/{id}:cancel` and `GET <url>/extendedAgentCard`, with the JSON-RPC binding's bodies. gRPC is `lf.a2a.v1.A2AService` (`SendMessage`, `GetTask`, `CancelTask`, `SendStreamingMessage` and `GetExtendedAgentCard`, the credential in the call's metadata): when the card says it streams, a task is one `SendStreamingMessage` whose events (a task, a message, `statusUpdate`, `artifactUpdate`) are read as they come, as on the other bindings; the extended card is asked for there too, and its name, description, interfaces, capabilities, security schemes and skills are read. Every connection of the gRPC channel, the first and each one made again after the agent went away, resolves the agent's host anew and dials only an address the SSRF rules allow (a name that now resolves to a private address is refused).
- **OAuth from the card** - an entry with `oauth` (a `client_id` and `client_secret_env`, optional `scope` and `resource`) is reached with an access token of the client credentials grant, fetched and renewed as for MCP below. Without `token_url` in the entry, the token endpoint is the one of the card's OAuth 2.0 scheme with a client-credentials flow (1.0 `oauth2SecurityScheme.flows.clientCredentials.tokenUrl`, 0.3 `type: oauth2`), when it is on https or on the entry's own origin: the client secret goes nowhere else. A card that names none fails the task before anything is sent. The token is sent as `Authorization: Bearer` on every binding, also to ask for the extended card.

- **The Agent Card** - for an orchestrator's agent (see [Agents That Describe Themselves](#agents-that-describe-themselves)) the gateway reads `<url>/.well-known/agent-card.json` at the session's start. When the card says `capabilities.streaming`, a task is one `SendStreamingMessage` instead, and its progress, its questions and its result are read from the reply's server-sent events as they come (a task, a message, `statusUpdate` and `artifactUpdate`, or the 0.3 `kind`s `task`, `message`, `status-update` and `artifact-update`); a stream that ends while the task waits for an answer, or early, is read with `GetTask` from then on, and the answer is sent as a new streamed message. The card's security scheme decides how the secret is sent: in the named header of an `apiKey` scheme in a header (`apiKeySecurityScheme` in 1.0), else as `Authorization: Bearer`. The card's JSON-RPC interface address is used when it is on the entry's own origin (scheme, host and port); otherwise the entry's `url` is, so a card never sends the secret elsewhere. A card that cannot be read leaves the entry as configured.

- **States** - a status message of a working task is its progress; `TASK_STATE_INPUT_REQUIRED` makes its status message a `value` question (with a deadline when the message's `metadata` has `expires_in_ms`: A2A has no standard field for it), and the caller's answer is sent as a message to the same task; the text of the artifacts of a completed task (or its status message) is the answer. The state names of A2A 0.3 are read too.
- **Sign-in** - `TASK_STATE_AUTH_REQUIRED` with a link in its status message (a part's `url`, a data part's `url`, or the first `http://` or `https://` address in its text) is a sign-in link on the client's screen (see [Questions on the Client's Screen](#questions-on-the-clients-screen)). When the client answers with `accept`, the message `Signed in.` goes to the same task and the agent goes on; a decline or a timeout is sent as for any question. Without a link the task fails: a sign-in cannot be given by voice.
- **Context** - the `contextId` of the session's first task is sent with each later one; a follow-up sends the `contextId` of the task it follows (see [Follow-ups](#follow-ups)).
- **Cancelling** - `CancelTask`.
- **Push notifications** - with `push_base_url` on the entry (the gateway's own address as the agent reaches it) and a card that says `capabilities.pushNotifications` and does not stream, a task's first `SendMessage` carries `configuration.pushNotificationConfig`: `url` `<push_base_url>/v1/tasks/<task_id>/callback` and a `token` of 64 hex digits made for that task. The agent posts each change of the task there (a task, a message, or a `statusUpdate` or `artifactUpdate`, as on a stream, or the 0.3 task object) with the token in `X-A2A-Notification-Token`; each is read as a streamed event is, so progress, questions and the result come as they happen. Meanwhile the task is read with `GetTask` only every 5 seconds, in case a push was lost. A push with another token, or none, is answered 401; one for a task no process runs, 404; with a task Redis a push that reaches another gateway process is handed to the one that runs the task (see [Several Gateway Processes](#several-gateway-processes)). The card of a session's own A2A backend (`tasks.default_backend`) is read at the session's start, as an orchestrator's agents' cards are: its binding, its credential's scheme, its token endpoint and whether it streams or pushes apply to the session's tasks.
- **The extended card** - when the public card says the agent has an authenticated extended card (`capabilities.extendedAgentCard`, `supportsExtendedAgentCard`, or 0.3 `supportsAuthenticatedExtendedCard`) and the entry has a secret, the gateway asks for it at once with the entry's credential (1.0 `GetExtendedAgentCard`, 0.3 `agent/getAuthenticatedExtendedCard`, at the card's JSON-RPC address) and uses it in place of the public card: its description and skills describe the agent, its security scheme decides the credential's header. An extended card that cannot be read leaves the public card.

#### MCP Task Tool

The gateway calls the entry's `tool` with `tools/call` as MCP 2026-07-28 defines it for HTTP (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, the request metadata in `_meta`) and declares the Tasks extension `io.modelcontextprotocol/tasks`. A server that answers with a task is read with `tasks/get` at the interval it asks for (250 ms to 5 s); one that answers at once has answered the task.

- **The handshake** - before its first `tools/list` or `tools/call` to a server, the gateway process sends `initialize` (`protocolVersion` 2026-07-28, `capabilities` with `elicitation` and the Tasks extension, `clientInfo`), then `notifications/initialized`. Every later request carries the version the server answered (`MCP-Protocol-Version`) and its `Mcp-Session-Id`, when it gave one. The handshake is the entry's (two entries of one server, with their own credentials, make their own) and serves the process's sessions for the entry's `catalog_ttl_s` (300 s); a server that answers 404 to a request with the session is initialized again by the next request. A server that refuses `initialize` (an error or a 4xx) is used without a session, each request standing alone as before.
- **OAuth** - an entry with `oauth` (`token_url`, `client_id`, `client_secret_env`, optional `scope` and `resource`) is reached with an access token: the gateway fetches it from `token_url` with the client credentials grant (HTTP Basic client authentication) and sends it as `Authorization: Bearer` with every request. A token is renewed a minute before it expires (half way through a token that lives under two minutes; five minutes when the server gives no `expires_in`), and fetched again after the server answered 401. A token is kept per `token_url`, `client_id`, `scope` and `resource`. The token and the client secret are never logged or echoed; a failed fetch is logged with the endpoint's `error` code only. `oauth` takes the place of `secret_env`.
- **Input asked outside a task** - a request of the server's written on the reply of a call that is no MCP task (a JSON-RPC request in its server-sent events, such as `elicitation/create`) belongs to the session that made the call: an elicitation is asked of that session's caller as below, and the answer goes back as the JSON-RPC response with the request's `id` (`{"action": "accept", "content": {...}}`, or `decline` or `cancel`). An elicitation the caller cannot answer is declined; any other request gets the error `-32601`. A request written on a reply no session waits on (`initialize`, the `tools/list` an orchestrator's start reads) has nobody to ask: it is refused with the JSON-RPC error `-32601`, and the reply is read on.

- **The GET stream** - once `initialize` has made the handshake, the gateway opens the server's GET stream (MCP Streamable HTTP: `GET <url>` with `Accept: text/event-stream`, the session and the credential) and reads it while the handshake serves; a stream that ends is opened again a second later, and a server that offers none (405, or any refusal) is not asked again for that handshake. A message on it about a call of a session goes to that call: one that names the call's task (`_meta["io.modelcontextprotocol/related-task"].taskId`, or the `taskId` of `notifications/tasks/status`) or carries its `progressToken`. An elicitation about a task is asked of that session's caller as below, and the answer goes back as the JSON-RPC response of its `id`; a status notification has the task read at once rather than at its next poll; progress is a `task_progress`. A request that is about no call of a session is refused with `-32601` (a `ping` is answered), and `notifications/tools/list_changed` has the next session read the tool list again.
- **Conversation controls** - a server asks for a control (see [Conversation Controls](#conversation-controls)) with the notification `notifications/io.waav/control` (`params`: `kind`, `value`, `request_id`) on a call's reply or on the GET stream, or in a tool's or a task's result as `_meta["io.waav/control"]` (one, or a list; applied before the result is read). How it went goes back as the notification `notifications/io.waav/control_applied` (the `control_applied` event's fields, the `request_id`, and the task in `_meta`).
- **Result** - the text content of the tool's result is the answer; `isError` fails the task.
- **Questions** - a form elicitation in `inputRequests` with one field is asked by voice with its `message`: as a choice when the field has an `enum` or is a boolean ("yes" or "no"), else as a value. One with several fields is a form on the client's screen, with the elicitation's `requestedSchema` as its `schema`; the client's object is sent back as `{"action": "accept", "content": {...}}` (a value that is not an object is a decline). The answer is sent with `tasks/update`. An elicitation that opens a URL is a sign-in link on the client's screen (see [Questions on the Client's Screen](#questions-on-the-clients-screen)); the client's accept is sent back as `{"action": "accept"}`. Any other input request is declined.
- **Cancelling** - `tasks/cancel`, then the task is read until it has ended.
- **Deadlines and follow-ups** - an elicitation whose `_meta` has `expires_in_ms` is a question with that deadline. A follow-up's `tools/call` carries the task id of the task it follows as `_meta["io.waav/follows"]`.
- **Progress on the reply** - every `tools/call` has a `_meta.progressToken`. A server that answers with server-sent events may send `notifications/progress` before its result: each one's `message` (or, without one, how far it is: `40% done.`) is a `task_progress` as it arrives.
- **An orchestrator's server** - with `tools` the server's tools are the orchestrator's own tools (see [Agents That Describe Themselves](#agents-that-describe-themselves)): each call is `tools/call` of that tool with the arguments the orchestrator gave, as a task when the server makes it one. A call of a tool that is not read-only and ends without an error has the effect `ran <tool>` (`ran delete note` for `delete_note`).

#### OpenAI Responses

A Responses model is prompted by the gateway like the session's own LLM: the persona's preamble and the `system_prompt` of the session's `conversation_config`, the heard conversation as `input`, `tasks.tools` and `ask_caller` as function tools, and the answer marker (see [Tools](#tools)). Three tasks may run at once. `tasks.speculative_start` is always `off`: a run that is started and dropped is still billed.

- **Requests** - each round is `POST <url>/responses` with `background: true` and `store: true`. A streamed response is spoken sentence by sentence as it is written; a stream that breaks is picked up with `GET <url>/responses/<id>?stream=true&starting_after=<n>`, and where that is not served the response is read with `GET <url>/responses/<id>` twice a second, as it is with `mode: poll`.
- **Tools** - a `function_call` item is run by the gateway under the rules of [Tools](#tools), and its result goes back as a `function_call_output` item with the model's own output items. A task gets at most 8 such rounds.
- **Cancelling** - `POST <url>/responses/<id>/cancel`.
- **Follow-ups** - a follow-up sends `previous_response_id` (the last response of the task it follows) and only the new request as `input`.
- **Servers without background mode** - a server that answers the request with the finished response, or with the stream (llama-server does), works the same way.

### Many Agents

With `tasks.orchestrator` a session's requests go to an orchestrator: a model on the LLM tier, normally a large one, whose tools are the catalog entries the session lists in `tasks.agents` (each with its `description`) as well as the session's own `tasks.tools`. The small front keeps acknowledging at once while the orchestrator plans.

```json
"interaction": {
  "tasks": {
    "orchestrator": "gpt-oss-20b",
    "agents": ["browser", "coder"]
  }
}
```

- **Which model** - a model name runs on the session's own LLM (its `conversation_config` or `tasks.llm`, with that model); an object of the `tasks.llm` shape (`base_url`, `model`, `api_key`, ...) is an LLM of its own. Without a `system_prompt` of its own it has the session's. Its answers may use 4096 tokens unless the object sets `max_tokens` (a model that reasons before it calls a tool does not fit the 256-token voice cap). Say in its `system_prompt` what the agents know and that they ask the caller for what they need: without that, gpt-oss-20b asked the caller for every detail (a departure city, a repository) before it gave any agent the task. A reasoning model plans faster with `reasoning_effort: "low"`: on a loaded machine gpt-oss-20b's first agent call came 17 to 44 seconds after the request at its default effort, and 3.5 to 10 seconds after it at low.
- **Calling an agent does not wait** - the call starts a child task on the agent and returns at once with the child's `task_ref`. The orchestrator may call several agents in one round. A child hears only the request the orchestrator wrote (no history, no persona, no tools of the session). An orchestrator whose only tools are agents has no `ask_caller` (its agents ask the caller for what they need): with it, the 3B background asked the caller for a flight's date instead of calling the travel agent (live PR10).
- **Agents are not asked about their tasks** - the gateway's rules tell the orchestrator that a task's update reaches it by itself, never to call an agent to check on a task, and to give an agent the details the caller gave without asking the caller for them again (live MA1: `gpt-oss-20b` called the browser agent to "check the status of task t5", the coder's task, then asked the caller which repository held the test the request had named). A call of an agent whose request names a task the same run started together with the word "task" or "status" (`Check task t5 status`; "a cab to Heathrow T5" is a request) is not made: the orchestrator gets `task_ref` and a note that the task's update reaches it by itself (live MA1, 21 October: gpt-oss-20b asked the coder about its own child t5 despite the rule, and the child's "I don't have information on task t5" was said to the caller).
- **Results come back as messages** - when a child ends, its result (or that it failed or was stopped) is added to the orchestrator's history as a message that begins `Task update`, and its run goes on: it may start the next step. The orchestrator's task ends when it has answered and none of its children is left. Neither a child's own answer nor what the orchestrator writes after its first answer is spoken: once it waits for its children its answer is over, and each child's result reaches the caller as an update (see [Task Updates](#task-updates)). The request's `task_result` `summary` still holds all the orchestrator wrote.
- **One request, one orchestrator task** - a caller's request still makes one task; the orchestrator splits a request with several parts into children. General questions it answers itself. Each request's run sees the call so far without the caller's other requests that are still running (they have runs of their own); a finished request and what was said about it stay in.
- **The task tree on the wire** - every task event carries `parent_id` (`null` for a caller's request), `agent` (the entry's name, `null` on the session's own LLM, agent or DAG) and `trace_id` (32 hex digits, one per caller's request, shared by its children). Each request to an agent or a tool carries the task's trace in a W3C `traceparent` header (`00-<trace_id>-<span>-01`).
- **Questions and failures** - a child's question waits for a slot of the conversation like an update, unless its deadline cannot wait (see [Questions With a Deadline](#questions-with-a-deadline)). A child that fails is said like any failed task ("Sorry, I couldn't get that done just now."); the orchestrator is told that the caller already heard it.
- **Stopping** - cancelling or correcting a request stops its live children (they end `cancelled` by `parent`, which is not said aloud when nothing was done); a correction starts the orchestrator again on the corrected request.
- **"What are you working on?"** - with more than one live request, the caller hears the three most recent by title and how many more ("Right now I'm working on A, B, C, and 2 more.").
- **"Tell me as soon as it's done"** - see [Task Updates](#task-updates): the caller's own word on how a task's result reaches them.
- **Agents describe themselves** - an A2A agent's card and an MCP server's tool list describe them to the orchestrator; a call that may change things is confirmed with the caller first (see [Agents That Describe Themselves](#agents-that-describe-themselves)).
- **Who may name agents** - as for `tasks.default_backend`: the server's blocks, an alias and an agent entry; a session only with `allow_client_backends`. A voice-agent or DAG session ignores the orchestrator, a named `default_backend` gives way to it, and `tasks.agents` without an orchestrator is ignored, each with `interaction_value_ignored`. Speech-to-speech sessions ignore it too.

#### Agents That Describe Themselves

The orchestrator is the gateway's own agent: it needs nothing from the agents' authors but A2A or MCP. A Bud agent, or any other, takes part the same way when it exposes either one; the signed webhook stays for operators who have neither.

```yaml
task_backends:
  - name: "trips"          # an A2A agent: its card describes it
    type: "a2a"
    url: "https://trips.example.com/a2a"
    secret_env: "TRIPS_KEY"
  - name: "notes"          # an MCP server: every tool it lists is a tool of the orchestrator
    type: "mcp"
    url: "https://notes.example.com/mcp"
    tools: ["*"]
    secret_env: "NOTES_TOKEN"
```

- **Read at the session's start** - before an orchestrator session starts, the gateway reads the Agent Card of each A2A agent in `tasks.agents` and runs `tools/list` on each MCP entry with `tools` (all pages, at most five), all at once and for at most 3 seconds. What was read serves the process's later sessions for `catalog_ttl_s` (300 s); what could not be read is tried again by the next session, and the entry works as configured meanwhile (an MCP entry with `tools` then has no tools). An MCP server is initialized first (see [MCP Task Tool](#mcp-task-tool)); every request also carries its version and capabilities in `_meta`.
- **An A2A agent** - one tool, named after the entry, whose description is the entry's `description`, else the card's `description` followed by its skills (`Skills: <name>: <description>; ...`, at most 1,000 characters), else "The <name> agent.". It takes one `request` in words.
- **An MCP server** - one tool per tool it lists that `tools` allows (up to 32), with the server's name (characters other than letters, digits, `_` and `-` become `_`; a name another agent has gets the entry's name and `_` in front), its `description` (else its `title`) and its `inputSchema` as the tool's parameters. The call's arguments go to the server as they are. On the wire, the child task's `agent` is that tool's name and its `background` is `mcp:<entry>`; the entry's `max_concurrent` counts per tool, its breaker per server.
- **Confirmations come from the gateway** - a call is confirmed with the caller when the entry may change things (`side_effects: possible`, the default) and, for an MCP tool, its annotations do not say `readOnlyHint: true` or `destructiveHint: false` (MCP's defaults: a tool that is not read-only may destroy). The entry's `confirm` overrides both. A confirmed call goes through the gate of [Confirmation](#confirmation) before anything is sent: the caller hears it read back from its exact arguments ("To confirm: delete note, old list. Do you want me to do that?"), a no or a correction refuses it (the orchestrator is told it was declined or stale), and the same call under the same revision is neither asked nor started twice. A read-only MCP tool's task has `side_effects: false` and nothing to confirm.
- **Every call is a child task** - on any protocol, with the request's `trace_id`, its own state, question, effects and `task_output`. The front model is not shown a child while the request that started it is under way: the request stands for it (with both listed, the 2B front read a new request as `wait` and a question as a follow-up of a child that had just ended). A finished child of a finished request is what a follow-up names.
- **Follow-ups** - a follow-up of a call of an MCP server's tool, or of an agent whose calls are confirmed, is not run on that agent with the caller's words (the tool takes arguments, and the gate would be passed by): it is an ordinary request to the orchestrator, which calls the tool again through the gate.

### Task Updates

What an orchestrator's children come to reaches the caller in two independent ways: it is published the moment it exists, and it is spoken only when it fits the conversation.

- **Published at once** - when a task completes, `task_output` carries its whole result: `text` (the answer as the background wrote it), `data` (a backend's structured result: a webhook result's `data`, the A2A task's data parts, an MCP tool's `structuredContent`; else `null`), `artifacts` (a webhook result's `artifacts`, the A2A task's file and link parts, the MCP result's content that is not text), `effects`, and `parent_id`, `agent` and `trace_id`. It goes to the socket and a room's data topic before anything is said of the task, and to the readers of `GET /v1/tasks/events` (see [Listing Tasks](#listing-tasks)). Every completed task has one, a caller's request too; `task_result` keeps its meaning.
- **Spoken at a slot** - a child's result, and its failure, wait in the session's update inbox (failures first, then the tasks the caller asked to hear about, then by age) until a slot: nothing of the agent's is queued or playing, the caller's latest request has its answer (its run's first answer is over, or the task ended), no question or offer is open, and the caller is not speaking. An update never cuts an answer and never starts over the caller. At the slot:
  - **Idle** - nobody has spoken for 4 seconds: the update is said.
  - **Going on** (the slot right after an answer) - `tasks.announce` decides. `ask` (the default) says one short offer: "I've got the answer on your request to book the flight. Want it now?", or for several at once "By the way, 2 updates are in: ... Want them now?". A yes (the persona's accept words) says them, as the reply to that turn; a no ("Okay.") or no answer within `policy.answer_window_ms` after the offer was heard keeps them for the next idle moment; an offer is made once. `tell` says the update itself. `screen` never says it.
  - **A failure** is said at the slot in its usual words ("Sorry, I couldn't get that done just now."), except with `screen`.
- **The caller's own word** - when the caller says how to hear about a running task ("let me know the moment the test is fixed", "don't tell me about that one"), the model front answers with the task's status and adds `notify`: `tell` (said at the next slot, before the other updates) or `screen` (never said). It applies to the task and to its children. The front model decides this from the call.
- **The narrator** - the front words each result: the model front gets the last two lines of the call, the task's title and its result, and writes one sentence of at most 20 words within the front's budget (`front.total_budget_ms`, 1.5 seconds by default, as for a follow-up question), told to keep every time, date, number and code the result gives (live MA1: "The morning flight from Mumbai to Delhi has been booked for you." for a result with its flight number and departure time). The line is said only when every number in it is in the result (or the title, or the caller's last words), every name (a capitalised word that does not start the sentence) is too, it holds no link and no prompt label, and it is one sentence of at most 20 words. There is no template to fall back to: an update without such a line waits for its next slot (at most three tries; the client has the result in `task_output` and `task_result` whatever is said of it), and while the front model is unavailable updates wait for it to be back. Live on a loaded shared GB10 with Qwen3.5-2B the narrator took 505 to 991 ms for the lines it wrote in time at first; with a budget of its own of 1.2 s, 24 of the 53 narrations of the 20 October runs ran out and their updates went unsaid (alone a line took 0.5 to 1.1 s, and it waited up to 0.4 s for the slot it shares with the interims' priming), so it has the front's budget. With a screen attached (`hitl.channels` holds `client` and the caller is not on a phone line) the sentence is followed by "The details are on your screen." The push's `update` (see [The Push](#the-push)) is the narrator's line when it has one in its budget, else absent: the summary alone. Update lines and offers are `assistant_transcript` and `audio_segment` with `kind: "update"`.
- **"Tell me more"** - a child's whole result is kept in the call's history (a note "Result of an earlier task ...", not the caller's words), so a later request relays it as an answer is relayed, and its numbers may be said.
- **`task_seen`** - a client that showed the result sends `task_seen` with the `task_id`: an update of it that is still to be said is dropped.
- **Progress** - a progress line (chapter 4's spacing) is said only while nothing else of the agent's plays and the caller is not speaking.

### Questions With a Deadline

A question of an orchestrator's child waits in the inbox and is asked at the next slot (the agent's answer is over, nothing is queued, the caller is not speaking). It is on the client's screen at once: `task_question` is sent when the job asks, with `expires_at_ms` (its deadline on the session's clock; `expires_at_ms - t_ms` is the time left). It may be answered there before it is asked aloud.

- **The deadline** - `expires_in_ms` of the webhook's `question` event, the A2A status message's `metadata.expires_in_ms`, the MCP elicitation's `_meta.expires_in_ms`, or the entry's `question_deadline_ms`; at most `policy.hitl_answer_timeout_ms`. A question with no deadline of its own has the session's timeout, which starts again when it is heard; a deadline of the job's own is never moved.
- **When it cannot wait** - when the deadline comes sooner than the end of the agent's speech still to be heard plus 2.5 seconds, the question breaks in (an orchestrator's session synthesises its lead-in and "Anyway," at the start, with the warm-up lines). While the agent speaks, the relayed answer is cut at its next clause boundary (a comma, a semicolon, a colon or a sentence end within 400 ms at the measured speaking rate, else the end of the word being spoken) and the question is said first, after "Quick question." (a persona may reword the template `question.interrupt`) when 6 seconds or more are left before its deadline; with less, the question is said on its own (live MA2, 5 s: the question took 1.2 to 1.3 s, the caller began 0.75 s after it and spoke 1.3 s, the recogniser's final and the reply's reading took 0.6 to 1.0 s more, and with the 1.2 s lead-in every answer came 5.38 to 5.39 s after the agent asked). While it waits for the cut (and the answer's sentences already synthesised, nothing else with the voice's provider) the question's words, and its lead-in's, are synthesised into the speech cache: the cut keeps that synthesis going (only the agent's audio stops) and the question is said from the cut with the same words, its audio from the cache once its synthesis is done; a cut for anything else (the caller's barge-in) clears it and the question is synthesised afresh. Why: live MA2 on 23 and 24 October missed its 5 s by 0.01 to 0.33 s, and the question's synthesis (0.55 to 0.9 s on Piper under load) began only at the cut, 0.06 to 0.41 s after the question came. The caller's answer ends at its first pause that Smart Turn has judged, unless Smart Turn is sure they have not finished (any open question: a short answer needs no 1.5 s silence). While the caller speaks it waits for their first pause of at least 250 ms and never starts over them; a reply to the caller waits for the end of their turn as before.
- **The answer resumes** - after the caller answered (or the question ended), the interrupted answer goes on from the sentence that was cut, which the caller did not hear in full, introduced by "Anyway," (`question.resume`).
- **A very short deadline** - the lead-in, the question and the caller's answer take their time: on the reference stack (a local voice of about 14 characters a second, a request-response recogniser) the caller's answer reached the agent 7 seconds after it asked, so a 5 second deadline expired; a synthesis already under way when the question breaks in is finished first (up to about 2 seconds, seen live).
- **When it expires** - the job gets `timeout`, and the caller hears at the next slot: "A question about your request to ... could not wait for your answer, so it went on without it."
- A caller's own request keeps the rules of [Confirmation](#confirmation): its question is asked at once.

### Follow-ups

A finished task of a catalog agent (a child, or a request on a named `default_backend`) stays addressable for `tasks.follow_up_ttl_s` (30 minutes by default), with its result and its continuation handle: the A2A task's `contextId`, the webhook's `task_id`, the MCP task id, or the Responses response id. A turn is a follow-up when the model front names the act `follow_up` with the task, or when it names a finished task by a word of its title ("can you book the return flight too?"), or points back ("when does it land?", "can it be a window seat?") within two minutes of hearing that task's update. "Tell me more" is not a follow-up: the background relays the whole result as before.

- **A question the result answers** - the front model answers it from the stored result in one sentence (within the front's `total_budget_ms`), with the checks of an update: every number and name in the answer must be in the result, the title or the question. No task is made. Without a model front, or without an answer that passes, it becomes a task as below.
- **Anything else** - a new request on the same agent, which hears only the request and continues the old task with its handle (`follows` on the wire and in `GET /v1/tasks`, `parent_id` null). Its answer is said like the answer to any request. A follow-up of a call of an MCP server's tool, or of an agent whose calls are confirmed, is an ordinary request to the orchestrator instead (see [Agents That Describe Themselves](#agents-that-describe-themselves)).
- **Cancelling something done** - "cancel the flight" about a finished task that may have changed something asks "Your request to ... is already done. Do you want me to ask for it to be undone?"; a yes sends the caller's words to the same agent as a follow-up, a no leaves it.
- **After `tasks.follow_up_ttl_s`** - the handle is not used: the new task's request ends with a line of the old result (`(Earlier, "<title>" came to: <its first sentence>)`).
- A task of the session's own LLM, Bud agent or DAG has no handle: a request about it is an ordinary request, with the call's history as its context.

### A Hesitant Request

Words that go on with the caller's latest request ("I need a pet-friendly apartment in Miami" ... "and my budget is about 1500 a month") are part of it, not a request of their own, when the caller began them at most 1.5 seconds after the turn of the request ended, nothing of the request's answer has been heard, its task is still running, and the request ended on an unfinished word or the new words start with one that joins them ("and", "but", "with", "for", "um", ...). The task is revised with its words joined into one request (one task, a new `revision`), and no second acknowledgement is said.

### OpenAI Realtime Clients

`/v1/realtime?model=prompt:<agent>` serves a Bud voice agent over the OpenAI Realtime protocol. Such a session runs interaction mode under the rules of [Voice-Agent Sessions](#voice-agent-sessions): the agent entry's `interaction` field, or the server's `interaction.agent_default`. A client cannot send a block of its own on this endpoint.

The session object and the audio are those of any voice-agent session on this endpoint. What the mode adds:

| On `/ws` | On `/v1/realtime` |
|----------|-------------------|
| `ready.interaction` | `bud.interaction.state` with the same object under `interaction`, sent once the session has started |
| `task_created`, `task_progress`, `task_question`, `task_answer_received`, `task_output`, `task_result`, `task_cancelled` | `bud.task.created`, `bud.task.progress`, `bud.task.question`, `bud.task.answer_received`, `bud.task.output`, `bud.task.result`, `bud.task.cancelled` |
| `floor_state`, `agent_audio_stopped`, `interaction_updated` | `bud.floor.state`, `bud.audio.stopped`, `bud.interaction.updated` |
| `config_warning` about the block | `bud.warning` with `code`, `message` and `detail` |
| `error` with a `code` | `error` with the code in `error.code` |
| `assistant_transcript` | one response per line of the agent (below) |
| `task_answer`, `task_cancel` | `bud.task.answer`, `bud.task.cancel`, with the same fields |
| `interaction_update` with `patch` | `bud.interaction.update` with the patch under `interaction` |

Every `bud.*` event has the body of its `/ws` event, plus `event_id`.

- **Agent speech** - each line the agent says is one response: `response.created`, the transcript and audio deltas, `response.done`. Its `metadata` carries what the line is: `bud_utterance_id`, `bud_source`, `bud_kind`, `bud_verbatim`, and where they apply `bud_act`, `bud_task_id` and `bud_sentence`. A line that was heard to its end has status `completed`. A line that was cut has status `cancelled`, after `bud.audio.stopped` and a `conversation.item.truncated` whose `audio_end_ms` is the line's `delivered_ms`.
- **Caller speech** - `input_audio_buffer.speech_started` and `speech_stopped` follow the floor (they need `events.floor`, which is on by default). The caller's item is completed, with the transcript of the turn, when the agent's first line after that turn starts.
- **Client events** - a typed message followed by `response.create` is a caller turn. `response.cancel` cuts the agent's audio. `conversation.item.truncate` changes nothing: the gateway measures what the caller heard.
- **Settings** - `bud.interaction.update` applies only the paths the agent's `session_overrides` list: `interaction` for the whole block, or a path such as `interaction.policy` or `interaction.events.floor`. Every other path is answered at once with `bud.interaction.updated` and reason `not_allowed`.
- **Without the mode** - `bud.task.answer`, `bud.task.cancel` and `bud.interaction.update` get an `error` with code `interaction_not_enabled`.

#### A Session's Own Tools and Instructions

A voice agent's instructions and tools are its own. Where the agent's `session_overrides` list `instructions` or `tools`, a `/v1/realtime` session may add its own, as an OpenAI Realtime client does with a speech-to-speech model. They apply to a session that does not run interaction mode; one that does ignores them.

| `session_overrides` | What the session may send | What the gateway does |
|---------------------|---------------------------|-----------------------|
| `instructions` | `session.instructions` | Sent with every run of the agent. |
| `instructions` | `response.create` with `response.instructions` | Starts a run with these instructions in place of the session's, with no words of the caller. This is how a client has a text spoken. |
| `instructions` | `conversation.item.create` with a `system` message | Kept as context for the next run. Nothing is said until then. |
| `tools` | `session.tools` with tools of type `function` | Sent with every run. A call to one of them is a `function_call` item in the response, with `response.function_call_arguments.done`. |
| `tools` | `conversation.item.create` with a `function_call_output` item, then `response.create` | The output goes to the agent with the run that `response.create` starts. |

- **Without the entry in `session_overrides`** - the event is answered with an `error` (`event_not_allowed`), as before, and `session.updated` shows no instructions and no tools.
- **Metadata** - the `metadata` of a `response.create` that starts a run is returned in that response's `metadata`, next to `bud_agent` and `bud_turn`.
- **Turns** - with `audio.input.turn_detection` set to `null`, the client ends the caller's turn with `input_audio_buffer.commit`. The session's own turn detection needs a speech-to-text deployment that streams its results.
- **What the agent receives** - the Bud gateway's `/v1/responses` request carries `tools`, `instructions` and input items as the OpenAI Responses API defines them.

## Speech-to-Speech Providers

On `/realtime` (any provider) and on the `/v1/realtime` relay (Bud realtime deployments whose vendor speaks OpenAI Realtime), the provider keeps its voice and its own turn-taking. Interaction mode then makes WaaV its background: the provider hands requests to the gateway, the gateway runs them as tasks with the same tools, confirmations, backends and task events as the cascade, and it decides the words that bind.

**Which regime.** The gateway's regime resolver decides per session from the provider's capabilities (the plan's capability file), the surface, the session's `regime` and `speech.*` keys and the date. Two regimes run here:

| Regime | Providers by default | Who speaks | What the gateway says itself |
|--------|----------------------|------------|------------------------------|
| `provider_speech` (B) | OpenAI, Azure OpenAI, Yandex, Grok, Inworld, Deepgram Voice Agent, Ultravox, ElevenLabs | The provider, steered by the gateway | Confirmations, every task's result, corrections, and an acknowledgement when `filler_owner` resolves to `gateway` |
| `delegating` (C) | Gemini Live, Nova 2 Sonic; any provider with `regime: delegating` that can delegate | The provider: it is the front | Confirmations, the result of a task that committed something, corrections |

The mode runs only when the operator lists the provider in `interaction.truth_ack` (the gateway monitors, and cannot prevent, what such a provider says), the block gives a background (`tasks.llm` or `tasks.default_backend`), the server switch is on, and the provider and model are not retired. Otherwise the session runs as without the field and one `warning` (on `/realtime`; logged on the relay) names the reason: `truth_ack_required` (with `path` and `alternative`), `interaction_needs_background`, `interaction_unsupported`, `truth_enforcement_unavailable`, `model_retired`, `provider_retired`, `unsupported_vendor`, or `interaction_surface_unavailable` (`reason: half_cascade` for `speech.voice_owner: gateway`, or `background_unavailable`). `regime_downgraded`, `<kind>_owner_overridden`, `voice_owner_unavailable`, `model_family_unknown` and `model_retiring` are warnings the session runs with.

**On `/realtime`.** Send `interaction` in the `config` message:

```json
{"type": "config", "provider": "openai", "instructions": "You are the Olive Garden's phone assistant.",
 "interaction": {"tasks": {"llm": {"base_url": "https://llm.example.com/v1", "model": "my-model", "api_key": "..."}}}}
```

`session_created` then carries `interaction`: the settings echo with `regime` (`provider_speech` or `delegating`) and `speech` (`provider`, `verbs` this build can send it, `truth`, `filler_owner`, `confirm_irreversible`, `confirm_reversible`, `claim_policy`, `delegate_tool`, `voice_owner`). The task events, `unverified_claim` and `error` arrive with their `/ws` bodies, and the session takes `task_answer`, `task_cancel`, `task_seen` and `interaction_update` (`{"type": "interaction_update", "patch": {...}}`) as on `/ws`.

**In a LiveKit room or on a SIP call.** A `/ws` session with a `livekit` block whose own `interaction` block has `speech.realtime` has no speech-to-text, text-to-speech or conversation loop: its voice is the speech-to-speech provider. The room's caller (the first participant heard, as in [LiveKit Rooms and Phone Calls](#livekit-rooms-and-phone-calls)) is heard by the provider at the provider's input rate, and the provider's audio is published in the room at its output rate. `speech.realtime` takes the keys of the `/realtime` `config` (`provider`, default `openai`, `model`, `voice`, `instructions`, `turn_detection`, `temperature` and the rest) except `tools`, `alias` and `interaction`, which are not read: a call of a function nobody answers would hold the provider. `stt_config` and `tts_config` are not needed and are not read; a `conversation_config` is the background when the block names no `tasks.llm`.

```json
{"type": "config", "livekit": {"room_name": "support-call-1042"},
 "interaction": {"speech": {"realtime": {"provider": "openai", "voice": "verse",
                                         "instructions": "You are the Olive Garden's phone assistant."}},
                 "tasks": {"llm": {"base_url": "https://llm.example.com/v1", "model": "my-model", "api_key": "..."}}}}
```

- **Ready** - `ready` has `protocol_version` `1.1`, the room's details and `interaction`: the echo of `/realtime`'s `session_created.interaction` (with `regime` and `speech`). The events go to the socket and, as the same JSON, to the room's `waav.interaction` data topic. The socket takes `task_answer` and `task_cancel`.
- **Refused** - a session that cannot run the mode gets each reason as a `config_warning` (the codes above), then one `error` with code `interaction_realtime_unavailable`, and no `ready`: the voice runs only with the mode. A provider this gateway does not serve gives `invalid_provider`; a retired one `model_retired` or `provider_retired`; no credential `missing_api_key`.
- **Turns** - the provider's own turn detection ends the caller's turns, and when the provider reports that the caller started speaking, the room drops what it still holds of the provider's audio (`agent_audio_stopped` with `reason: barge_in`). With `turn_detection: {"mode": "manual"}` the gateway's analyser (Silero, as on the cascade) hears the caller: it commits the caller's turn to the provider at 700 ms of silence after at least 250 ms of speech, and when the caller has talked over audible provider audio for `duplex.pause_after_ms` (400 ms by default; never with `duplex.barge_in: false`) it stops the provider (`stop_output`), drops what the room holds and the rest of that response, and sends `agent_audio_stopped`. The analyser's echo gate reads the provider's audio as it was sent to the room. A commit is all the gateway sends: a provider that also needs `response.create` after a manual commit does not answer.
- **Phone lines** - a SIP participant turns the echo canceller on as for the cascade (only with manual turns, where the analyser runs). Keypad answers (`hitl.channels: dtmf`): 1 accepts the open confirmation and 2 declines it, from when it is asked; another question takes digits, `*` clears them and `#` sends them (`task_answer_received` with `by: dtmf`). The question is said with the keypad hint, as on the cascade ("You can also press 1 for yes, or 2 for no."; for a choice "You can also press 1 for 7 pm, or 2 for 8 pm.", key n picking option n at once); `task_question.prompt` holds the question alone.
- **Words** - the caller's final words go to the socket as `stt_result`, the provider's as `assistant_transcript` `{turn_index, delta, source: "provider"}` (`turn_index` counts the caller's turns).
- **Messages** - the socket takes `task_answer`, `task_cancel`, `task_seen`, `interaction_update` and `control`; the room's `waav.interaction` topic takes `control` and `task_seen`, as a cascade room session's does, and the answer (`control_applied`) is published there too. A `stop` or `hold` control stops the provider's speech and the gateway's and drops what the room holds (`control_applied` `applied`, `agent_audio_stopped` `reason: client_clear`); every other control is `unsupported`: the provider runs the conversation.
- **Not here** - a Bud-mode gateway (`speech.realtime.deployment`, Bud realtime deployments, needs budapp to name them) and a voice-agent session: `speech.realtime` is ignored with `interaction_surface_unavailable` (`reason: bud_mode` or `agent`) and the session is configured as any `/ws` session. Without a `livekit` block, and on `/realtime` and the relay, it is ignored with `interaction_value_ignored`.

**On the `/v1/realtime` relay.** The operator's `interaction.realtime_default` is every relay session's block (Bud publishes none per deployment yet). After `session.created` the client gets `bud.interaction.state`; the events have their `bud.*` names (`bud.task.created` ... `bud.claim.unverified`), and the client may send `bud.task.answer` and `bud.task.cancel`.

**What the provider gets.** One function, `waav_delegate` (`{"request": "<the caller's words>"}`), added to the session's tools and kept in every session update, and a few lines after the session's instructions: call it for anything to look up or do, never say something was done unless its result says so. The provider's input transcription is turned on. A call to `waav_delegate` never reaches the client.

**A delegated request.** Each call is a task (`task_created` with `origin: "provider_tool"`) run by the session's background. The task's result goes back as the call's output (`status`, `result`, `effects`). Where the exact words matter, the gateway says them itself and the output tells the provider not to repeat them: in regime B every result, in regime C a result that committed something. A call made while a gateway line plays is not a request (the output says `ignored`). A call whose words answer the open confirmation is that answer, and one whose words cancel the running task cancels it.

**A gateway line.** `say_exact` where the provider has a wire for it (Deepgram, Ultravox `forced_agent_message`, Inworld `response.speak`, Grok `conversation.item.create` with a `force_message` item), else guided speech (`response.create` with the words and `tool_choice: none` on OpenAI; on Grok under `grok_session` xAI's `response.create` with `instructions`, which takes no `tool_choice`). Each line waits for the one before it, for a response of the provider's own (its words or a function call) to end, and for the provider's audio to play out. When the response ends, its transcript is checked against the line: word for word after `say_exact`; after guided speech every number must match and every content word of the read-back be said. A line that fails gives `unverified_claim` with `rule: ExactWords`.

**Confirmations.** The resolver names the path per provider: `native_exact` and `say_guided_exact_words_checked` are spoken (`task_question.spoken: true`); `client_ui` (an irreversible action on a provider without exact speech) asks on the client's screen only, and the provider is told to send the caller there. A spoken answer counts only once the question was said and passed its check; when the check fails the question is said once more, and after a second failure only the client can answer. `gateway_clip_same_voice` and `gateway_clip_different_voice` are said in the gateway's own voice when the session has one ([Gateway clips](#gateway-clips)); without one those paths ask on the screen. With no channel at all the action is declined.

**What the provider says on its own.** Each finished response is read sentence by sentence. A claim that something was done that no task of the session supports (a committed task backs any claim, a confirmed cancel backs a cancel, a finished lookup backs "done"), a promise (an action, a time or a channel) while no task runs, and a number nobody gave (not in the caller's words, the instructions, a result or a gateway line; of a long call the newest 512 numbers are kept besides the instructions' own) each give one `unverified_claim`. A negated claim ("it couldn't be processed") is none. With `speech.claim_policy: correct` the provider is then made to say the correction template ("Just to be clear, that isn't finished yet. I'll tell you when it is."), once per response, and `corrected` is `true`. `output_stopped` is always `false`: the words are judged after they were said.

**When the provider's connection drops.** The verbs and results that could not be sent wait, in order (at most 32), and go out when the provider is back. A result for a call made on the lost connection goes in as context, followed by a request to reply. A provider that cannot cancel its output has its audio held for up to 8 seconds when the gateway must stop it.

**When the provider fails.** Its errors, a caller's turn it does not answer and a connection lost for good get the lines of [When Services Fail](#when-services-fail), from the server's default set, played into the session's output audio; the session ends with `session_failed` and the socket is closed. On the relay a line is a response of the gateway's own (`response.created`, `response.output_audio.delta`, `response.output_audio.done`, `response.done`, with `metadata.bud_source: "gateway"` and `bud_kind: "failure"`), the end is `bud.session.failed`, after which the relay closes with code 1011; the caller's turns there are the vendor's `input_audio_buffer.speech_started`, `speech_stopped` and `committed`, and its `error` events count as errors (a vendor connection that drops still ends the relay at once). A turn that asks nothing of the provider is not waited on: when the session's front model reads the caller's words as asking nothing ("uh-huh", "okay", "right": its `wait`, a continuer or nothing new), and the provider's last words were not a question, a provider that leaves them unanswered gets no stall line. That holds before the provider has said anything too: the front's prompt names "uh-huh" as a continuer and shows a bare one, with no earlier lines, as a `wait` (r15, owner 25 October: Qwen3.5-2B read a first-turn "Uh-huh." as `social`, a greeting, 10 of 10 and the caller heard a stall line; now a `wait` 10 of 10, while "Hello?", "Are you there?" and a question keep their acts, 70 of 70). A first-turn "Yeah." is still read as `social`. The session puts the persona's prompt into its front's cache (the decisions' slot) as it starts, as a cascade session does, so that first reading is not made cold (live SS2, r15: read cold, a first-turn "Uh-huh." 1.4 s into the call took past its 1.5 s budget and a stall line played; warmed, 346 to 556 ms).

**The caller's words.** What the caller meant is read by the server's front model, as on the cascade (owner, 24 October: no word list reads the caller's meaning): an answer to the gateway's spoken question with the labels of [How an Answer Is Read](#how-an-answer-is-read), a cancel of the running task (its `abort`) and a continuer (its `wait`), each on the provider's transcript of the caller's turn, and a `waav_delegate` call that passes on an answer to the open (or just answered) confirmation or a cancel is read the same way before it is taken as a request (`answer_received`, `cancelling`). The session uses the front's own client, its lane's slots and its supervisor's gate. A speech-to-speech session therefore needs the front too: on a server without `interaction.front_model`, or whose own front is not ready, it runs without the mode with `interaction_surface_unavailable` (`reason: front_unavailable`). While the front is down nothing is taken from the caller's words (the keypad and the client's `task_answer` still answer); there is no word-list fallback.

#### The Half-Cascade

`speech.voice_owner: gateway` (or `speech.truth: enforced`) on an OpenAI-family provider (OpenAI, Azure OpenAI, Yandex), on `/realtime`, in a room or on the `/v1/realtime` relay: the provider listens, transcribes the caller and writes its replies as text (its session asks for `output_modalities: ["text"]`); the gateway says them in its own voice. The echo has `regime: provider_speech`, `speech.truth: enforced` and `speech.voice_owner: gateway`.

- **Every sentence is judged before it is said** - a sentence of the provider's that claims something no task supports, or names a number nobody gave, is not said: the correction template is said in its place (once per response), and `unverified_claim` has `corrected: true` and `output_stopped: true`. The rest is said as written.
- **The gateway's lines** - the acknowledgement, confirmations (`task_question.spoken: true`) and every result are said in the same voice; a spoken answer binds once its question played to its end.
- **The voice** - `speech.voice` (a `tts_config` object, its key from the server's configuration as for `/speak`), else the operator's `interaction.failure_voice`; PCM only. Without one the session runs without the mode (`interaction_surface_unavailable`, `reason: gateway_voice_unavailable`).
- **On the relay** - with `speech.voice_owner: gateway` in the operator's `interaction.realtime_default`, every `session.update` the vendor gets asks `output_modalities: ["text"]` (whatever the client sent), as does a client `response.create` that names them; the vendor's `response.output_audio.delta` never reaches the client. Each line of the gateway's voice is a response of the gateway's own (`response.created`, `response.output_audio.delta`, `response.output_audio.done`, `response.done`, `metadata.bud_source: "gateway"`, `bud_kind: "voice"`; a failure line's is `failure`), with its `bud.audio.segment`. The vendor's `response.output_text.*` events still reach the client. Gateway clips outside the half-cascade are not played on the relay (their questions are on the client's screen).
- **Talking over it** - the provider's speech-started event (or the room's analyser with manual turns) stops the voice: `agent_audio_stopped` with `reason: barge_in` and the cut lines' ids. A question cut so is said again after the caller; the provider's sentences still to come of that reply are dropped. A `/realtime` client drops the audio it holds at the provider's `speech_started`, as it does for the provider's own audio; a room drops what it holds. Any audio the provider sends never reaches the caller.

#### Gateway Clips

Where the resolver's confirmation path is `gateway_clip_same_voice` or `gateway_clip_different_voice`, the question is said in the gateway's voice (as in the half-cascade) once the provider is quiet, and the provider's audio is held while it plays (at most 8 s). Without a gateway voice the question is on the client's screen. A `gateway_clip_different_voice` question (a provider whose voice the gateway cannot speak in, `speech.voice_mismatch` allowing it) begins with the introduction "Here are the details from our system:", and the provider is told that the system read the details in another voice and not to repeat or contradict them. No provider session makes listening sounds: the capability data resolves `backchannel_owner` to `provider` or `none` for every provider, and to `none` for the half-cascade.

#### A Claim Caught as It Is Said

With `speech.claim_policy: correct` in regimes B and C the provider's words are read as they come (its output transcript leads its audio). The first finished sentence that claims what no task supports, or names a number nobody gave, stops the provider (`stop_output`: its response is cancelled, or its audio held where it cannot cancel), the client gets `agent_audio_stopped` with `reason: policy` (a room drops what it holds), the correction is said, and `unverified_claim` has `output_stopped: true`. What had already played was heard. With `report` the words are judged when the response ends, as before.

#### Provider Speculation

A Gemini session whose withdrawn calls reach the gateway (provider fix `gemini_tool_call_cancellation`) takes each `waav_delegate` call as provisional: its run starts at once and nothing goes to the client. It is adopted when the provider's turn ends (`turnComplete`), when the provider makes another call, 300 ms after the provider stopped its turn for the caller (`interrupted`) unless it withdrew the call by then (on `/realtime`; a room reads no withdrawal), or 10 s after the call (the capability data's `adopt_by_ms`): then `task_created` with `speculative: true` goes out, and what the run did meanwhile follows. A call withdrawn before that is dropped unseen: no task event and no result. A backend that runs its own tools (a voice agent, a webhook, A2A, MCP) starts nothing before the adoption. Deepgram's eager calls are not provisional here: the gateway reads no withdrawal on Deepgram's wire until the plan's probe of it.

#### Delivery Scheduling (Gemini)

With the provider fix `gemini_response_scheduling` each delegate result carries Gemini's `scheduling`: `SILENT` for a result the gateway says itself or the caller read on the screen (and for a call that was not a request), `INTERRUPT` for one that committed something or failed, `WHEN_IDLE` otherwise.

#### Changing Settings Mid-Session

`interaction_update` on `/realtime` and in a room applies what a `/ws` session may change mid-session (`policy`, `duplex` but its echo defence, `events`, parts of `front`, `tasks.announce`), refuses the rest with its reason, and answers `interaction_updated`. The provider's own settings are not changed by it. On the relay `bud.interaction.update` changes nothing (the block is the operator's): each key is refused with `reason: not_allowed`.

#### Audio Segments

In a room and on the relay (`bud.audio.segment`) each gateway line has an `audio_segment` `start` and `end` (`lane: main`): a line the provider says (`utterance_id` `g_<n>`, from when it is sent until its response ends), a line in the gateway's voice (`v_<n>`) and a failure line (`f_<t>`, `kind: failure`). `/realtime` has none (plan chapter 6).

**Not built.** GPT-Live and Bud realtime deployments as a room's voice (they need budapp to name them, sign-off 27), Deepgram's provisional calls (its probe first). A task of a provider session ends with the session.

## Conversation Controls

Callers also steer the conversation itself: "stop talking", "say that again", "what was the number?", "slower please", "louder", "keep it short", "hold on a second", "go on", "talk to me in Spanish". Each is one **control** of a closed list, the same whoever asks:

- **the caller** - the front model decides in context whether an utterance is a control (its `control` act). No phrase list decides: "stop talking" while the agent speaks is a stop, a recogniser's near miss of it ("top talking") is too, and "stop by the store on the way" is a request. While the agent speaks the front is also asked on the recogniser's interim results, so a stop does not wait for the end of the caller's turn; meanwhile the agent's voice is ducked the moment the caller starts speaking (a reaction to sound, not to words). An interim takes the floor only on a sure reading: a `control` once its kind is read, a `stop` at once (also the near miss "top talking") and a `hold` once the turn's next interim reads it too; any other act once the turn's next interim names it too; other kinds never. No stop-cue list makes or hurries a cut (owner, 24 October: the pack's `stop_talking_cues` are examples in the front's prompt, nothing more). Measured live (S1, streaming, 24 October, three runs each, alternating): with the cue list the cut came 86 to 228 ms after the cue's words (one at 1 ms) and every "Wait a second." was cut (543 to 610 ms after its first voiced frame); with the front's readings alone 108 to 575 ms after the words, and 3 of 6 "Wait a second." cues were not cut at all (the 2B front reads its one interim over the agent as a `hold` and the turn's final as a `wait`), the others at 939 to 972 ms. S1 failed every run either way. A turn's own decision while the agent still speaks (the caller's words did not cut it) is shown to the front as said over the agent, as an interim's are (`USER (interrupting you)`; typed words excepted): offline (r15, ten seeds, no earlier turns) the 2B front read "Wait a second." in that decision as a `hold` 10 of 10 (0 of 10 without the mark: `wait`) with the r15 prompt; on the prompt as shipped since r15-verify (its `wait` line no longer says "also before you spoke", which with the first-turn continuer example made live R1's hold cue a second task) it was a `hold` 2 of 10. Words said over the agent are now shown without the recogniser's closing full stop, as its interims and the prompt's examples of them are (r15-fix, 26 October): "Wait a second." in that decision is a `hold` 8 to 10 of 10 ("Wait a second" as its interim reads it), its interim still 10 of 10, while "Can you stop by the pharmacy on the way?", "mm-hm" and "Okay." over the agent keep their acts and "Wait, what time is it?" is never a hold or a stop (0 of 20); the 13 decisions over the agent in the gate sets read as before (ten seeds), and "Wait, wait." is still a continuer. Live (S1, streaming, 26 October, three runs at a load average of 4 to 7): all 6 "Wait a second." cues were cut, 941 to 957 ms after the first voiced frame, by the overlap's barge-in; the front read the cue's one interim as a `hold` about 240 ms after the caller's onset, but the local stand-in gave one interim a cue and a hold takes the floor only when a second agrees, and the turn's decision came after the cut (no longer over the agent: `wait`). The stops were cut at 302 to 870 ms. S1 failed 3 of 3 on its 900 ms limit. Before (25 October, load 20 to 25): 4 of 6 "Wait a second." cues were cut (989 to 2,344 ms after the first voiced frame: three by the decision's hold, one by the overlap's barge-in); the decision shown the mark read a `hold` in 3 of 5 (the other two `wait`, with the session's earlier turns in the prompt); the stops were cut at 957 to 2,651 ms. S1 failed every run (its limit is 900 ms). Otherwise the turn's final decides, or the barge-in's own deadline (`duplex.decide_by_ms`: a caller still speaking then takes the floor): a `stop` or `hold` read at the end of a turn whose interims did not cut cuts the line that plays on (one whose interims did cut leaves alone what the agent began to say since); the turn's own `stop` cuts at its kind, which the gateway takes as soon as it is streamed, a `hold` once its line is read. An interim whose act is known and did not cut gives way to newer words at once (live S1: "stop talking" had waited behind the kind of the `control` named for "zob", Whisper's first hearing of "Stop-"). A `control` read on to its kind is read only that far: the kind is taken as soon as it is streamed, not at the end of the line (the line's last four tokens; on an own front server the kind came a median 147 ms after the act alone, 177 ms beside Whisper and 241 ms beside a generating gpt-oss-20b, the end of the line 225, 271 and 379 ms, r8, 23 October). An interim still out when its turn ends is kept until the turn's decision has its act: a stop it names (its kind, as above) cuts the line first, once, unless the turn already cut the agent (its barge-in's deadline, say: a line the agent began since is left alone; live S1, r8-verify: the cue's interim, back 1.3 s after it was asked, had cut the client's next line before its cue); the decision still runs and settles the turn whatever it reads, its own stop does not cut again, and its act drops the interim (live S1, r7-verify: the cue's interim was dropped at the end of the turn and the cut waited about 0.7 s for the decision's act). Live L6 is why a `control` cuts only as a `stop`: the interim "aha" of an "uh-huh" over the agent was named `control` and cut it; on the gate set the 2B front names "mm-hm", "aha" and "Uh-huh." over the agent a `hold` in some runs.
- **the orchestrator** - the tool `conversation_control` (`kind`, `value`, `asked_by`) of an orchestrator run (`tasks.orchestrator`); its result is the `control_applied` event. `asked_by` (required) is the words of the operator's prompt or of the caller that ask for the change: a control is applied only when they are words of the operator's prompt or of the caller's words in this call (the same words in the same order within one sentence, case and punctuation aside, at most three other words of the sentence between two of them; see below), since a control the operator and the caller did not ask for is never applied. A call of the run's own rounds whose `asked_by` quotes no one waits for the run's control round (below) and gets what that round applied for the same `kind` and `value`, else the answer that nothing was changed (offline the model wrote `asked_by: "user"` there for a caller's "Could you speak a bit slower, please?", 10 of 10; live MA7 on 22 October it called `updates` `tell` on "Find me a hotel in Goa for two nights.", which nobody had asked for). The tool applies only the call's `rate`, `volume`, `verbosity` and `language` (what its description names); any other kind is answered "Not applied: this tool changes only the call's language, rate, volume or verbosity" (live MA7, 22 October: after starting the planner the model's own round called `updates` `ask` and `tell` with a quote of real words). Every control gets a `control_applied` event (`outcome` `applied`, `partial`, `unsupported` or `refused`, with a `detail`), a note in the history, and an `interaction_updated` with the new **conversation state** (`version`, `language`, `rate`, `volume_db`, `verbosity`, `voice`, `backchannels`, `updates`, `held`, `controls`: the last 16). A control that is not applied in full is said in the persona's words ("Sorry, I can't change my speed on this line."); the agent never pretends.

**Language.** A switch is applied only when the operator lists the language (`controls.languages`), the recogniser hears it (a multilingual model such as Deepgram `language: "multi"`, or a provider whose language table has the language: then a second recogniser on the session's own settings is opened in it before the switch is applied, and hears the caller from their next pause, the first one closing after it (a recogniser opened for a switch that a later switch replaced, or that the session ended before, is disconnected, for every provider); none of the providers here changes the language of an open stream, so the second recogniser is the way for all of them; one that does not open within 10 seconds makes the switch `unsupported`), the voice provider lists a voice for it (the provider's voice list, the gender of the session's voice first; the list is read once per provider and key and shared by every session of the process for 10 minutes, by a gateway whose operator block lists `controls.languages` already at its start for the providers it holds a key for (Deepgram, ElevenLabs; log `voice list read at start`), else at session start; a switch asked for before the list came (the caller's, the client's or an orchestrator's, whose `conversation_control` gets the switch's `control_applied` when it is applied) waits for it, at most 30 seconds, and the gateway logs `interaction voice list not read` when it did not come), and there is a reviewed language pack. **The history** the background gets is what the caller heard: a line the caller cut off is kept up to its last heard word and marked `[cut off by the caller]`, a line never heard is left out, and each control leaves a note (`[the caller asked to speak slower; rate 0.85]`, `[language switched to es (partly)]`). #### A Person on the Webhook

The operator's endpoint at `controls.human.url` gets the signed `human_requested` body with `task_id` (`human_<32 hex digits>`) and `callback` (`/v1/tasks/<task_id>/callback`). It answers in its reply, or later on that route signed like a webhook backend's callback (`X-WaaV-Timestamp`, `X-WaaV-Signature` with `interaction.tool_secret`; see [Webhook](#webhook)), with `{"type": "human_connected"}` once a person takes the call or `{"type": "human_unavailable"}`; other events on the route are taken (202) and ignored. The client gets `human_answered` (`outcome` `connected`, `unavailable` or `no_answer`, `t_ms`). A request that is refused or not delivered counts as `unavailable`. Without `interaction.tool_secret` a callback is refused (401), so only the reply can answer. With a task Redis the answer may reach any gateway process: it is handed to the one that waits for it (see [Several Gateway Processes](#several-gateway-processes)).

## Protocol

When the mode is on, `ready` reports `"protocol_version": "1.1"` and carries an `interaction` object: the resolved settings (`enabled`, `protocol_version`, `regime` (always `cascade`), `front`, `tasks` with tool names only, `orchestrator` (whether there is one), `agents`, `limits`, `backend` (`llm`, `agent:<name>` on a voice-agent session, `dag`, or `<type>:<name>` for an operator backend, for example `webhook:crm`), `reconnect_grace_s`, `push` (whether a push address is set; the address itself is not shown), `session_end` and `orphan_max_s`, `announce`, `follow_up_ttl_s`, `resume` (whether a resume key is set; the key itself is not shown), `policy`, `duplex`, `events`, `hitl` (`channels`), `failure` (`stall_after_ms`, `max_wait_s`, `follow_up`: whether the exit line promises to get back, and `lines`: which failure lines are loaded, see [When Services Fail](#when-services-fail)), `degraded`). `front` echoes the persona's id and the caller's `preferred_name`, `verbosity` and `pace`; never the identity token or the caller's memory. Otherwise `ready` reports `1.0` and has no `interaction` key. Tool addresses and LLM keys are never echoed.

### Events (Server → Client)

`task_id` is `task_` plus 32 hex digits and `task_ref` is a short name (`t1`, `t2`). Every `task_*` event also carries `parent_id`, `agent` and `trace_id` (see [Many Agents](#many-agents)). `state` is one of `submitted`, `working`, `input_required`, `completed`, `failed`, `cancelled`, `rejected`, `unknown`. `effects` is `"none_committed"`, a list of labels of what was done, or `"unknown"`. `t_ms` is milliseconds since the session started.

## Tools

A tool is an HTTP address. When the background LLM calls it, the gateway sends:

```text
POST <url>
Content-Type: application/json
X-WaaV-Timestamp: <unix seconds>
X-WaaV-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>" keyed with tool_secret>
Idempotency-Key: <operation id>

{"tool": "<name>", "arguments": {...}, "operation_id": "<operation id>"}
```

- **Signature** - `X-WaaV-Signature` is present only when the server has a `tool_secret` and the tool comes from the server's `default` block or from an alias definition. A session's own tools need `allow_client_tools` and are never signed, even when one repeats an operator tool's name and address.
- **Idempotency key** - a side-effecting call carries an operation id of the form `op_<task_id>_<revision>_<n>`, both as `Idempotency-Key` and as `operation_id`. For other tools the header is absent and `operation_id` is `null`.
- **Response** - a 2xx body is the result (JSON or text; the first 16,384 bytes are read). Its string field `effect`, when present, labels what was done. A 4xx means the tool refused and nothing happened. A 5xx, a timeout (30 seconds) or a broken connection on a side-effecting call is recorded as an unconfirmed effect, and the LLM is told not to retry.
- **Answer marker** - with tools configured, the LLM is told to begin its final answer with a line that says only `ANSWER:`. Text before that line is never spoken.

### Confirmation

A tool with `side_effects` is held before its request is sent. The gateway emits `task_question` with kind `confirm` and reads the call back to the caller: the `confirm_phrase` and the arguments, in the order of the schema's `required` list. The caller answers by voice, or the client sends `task_answer`. On `accept` the request goes out; on `decline`, `cancel` or `timeout` it does not, and the LLM is told so. A spoken "yes" counts only when it began after the read-back was heard and is clearly the caller's; for an `irreversible` tool a weak accept such as "okay" makes the gateway ask once more. One question is open per session at a time, and the same call under one revision is asked once.

The background LLM also has a built-in tool, `ask_caller`, to ask the caller for a choice or a value (not an orchestrator of agents alone, see [Many Agents](#many-agents)). The answer binds like a "yes": only when the caller began to speak after the question, which names the options, was heard in full. An answer said over the question is not taken; the question is asked once more. With `kind: "form"` and `fields` (1 to 8 different names of at most 40 characters, such as `["street", "city"]`) it asks for several details at once on the client's screen: the form's `schema` has one required string field per name, and the client's object is the tool's answer. A form with no usable fields is refused to the model and nobody is asked.

A tool with a `confirm_template` is read back in its author's words, with the arguments that will run in its slots: "To confirm: Book a table for 4 at Rosa's. Do you want me to do that?". The re-asks keep using the `confirm_phrase`.

### Questions on the Client's Screen

Some questions are never answered by voice: a form with several fields, a link to sign in, and a value of a sensitive category (see [Sensitive Values](#sensitive-values)). With `client` in `hitl.channels` (the default) they are asked on the client's screen: `task_question` carries `channels: ["client"]`, the client shows the question and answers with `task_answer`, and the caller hears one line that says where to look.

| Question | Where it comes from | `task_question` | What the caller hears |
|----------|---------------------|-----------------|-----------------------|
| A form | a webhook's `question` with `kind: "form"`, a `prompt` and a JSON Schema `schema`; an MCP form elicitation of several fields; `ask_caller` with `kind: "form"` | `kind: "form"`, `schema` | "I'm putting a secure form on your screen for the details." |
| A sign-in link | a webhook's `question` with `kind: "auth_url"`, a `prompt` and a `url`; an MCP elicitation in URL mode; an A2A task in `TASK_STATE_AUTH_REQUIRED` that sends a link | `kind: "auth_url"`, `url`, `sensitive: true` | "To do that I need you to sign in. I'm sending a secure link to your screen.", then "I've sent it." |
| A sensitive value | an `ask_caller` or webhook question that names a sensitive category | `kind: "value"`, `sensitive: true` | "I'm putting a secure form on your screen for your card number." |

- **The answer** - `task_answer` with `outcome: "accept"` and `value`: the form's fields as an object, the value, or anything for a link (the caller signed in). The value goes to the background only. For a sensitive question `task_answer_received` carries `value: null` and `value_redacted: true`.
- **"I've sent it."** - a sign-in link's second line is said once its `task_question` is on the client's connection (the gateway handed it to the session's socket, and to the room's data topic in a LiveKit session), after the first line. A question that closes before it plays drops it. A connection that is gone gets neither the link nor the line.
- **No voice answer** - words the caller says are not taken as the answer, and the question is not asked again by voice. A caller who says a sensitive value while one is open hears "Please don't say that out loud. Use your screen instead."
- **The recogniser hears nothing of it** - while a sensitive value (or a sign-in link) is asked on the screen or the keypad, the speech-to-text gets silence of the same length in place of the caller's audio, and the client gets no `stt_result`: a value said anyway never reaches a transcript, the vendor, the background or the billing span. The voice activity detection still runs: a caller who speaks during that time (250 ms or more) hears the line above once per question. Spoken words, a "cancel" included, are not heard until the question is answered on the screen or keypad, cancelled by the client, or times out.
- **Without a screen** - with `hitl.channels: ["voice"]` such a question is declined at once (`task_answer_received` with `outcome: "decline"` and `by: "policy"`), and the caller hears "I can't take ... on this call for security reasons."
- **Timeout** - `policy.hitl_answer_timeout_ms`, as for any question.

## What the Front Decides on Its Own

These rules apply before a request reaches the background LLM. Each one settles the caller's turn with a fixed line from the persona's pack. What the caller meant (a request, a cancel, a stop, a repeat, a status question, a continuer, an amendment, side talk, a follow-up, a hesitant request going on) is never decided by a phrase list: the front model decides it in context (see [Conversation Controls](#conversation-controls)). The checks below are about the words' form (confidence, the recogniser's language field, digits), not their meaning; that the caller speaks another language is the front's reading too. The answer to something the agent asked (a confirmation, a choice, a value, the choice offer, the undo and update offers, "change it, or a second one?") and whether a new request repeats a task are read by the front model too (see [How an Answer Is Read](#how-an-answer-is-read)).

### Unclear Turns

When the speech-to-text reports a confidence below 0.5 for a turn, the caller is asked to say it again ("Sorry, could you say that again?") and nothing the turn seems to say is acted on: no task starts, an open question is not answered, and a "cancel that" does not cancel. A continuer such as "uh-huh" is still only a continuer.

This needs a speech-to-text provider that reports its own confidence for the words:

| Provider | Confidence used |
|----------|-----------------|
| `deepgram`, `gladia`, `revai`, `phonexia`, `tinkoff`, `gnani`, `aws-transcribe`, `ibm-watson`, `speechmatics` | Yes. The values 0.0 and 1.0 mean "not sent" and are ignored. |
| `google`, `microsoft-azure` | Yes, when the vendor sent one (final results; Azure's detailed output format). |
| Every other provider | No. The field holds a constant (1.0, 0.95, 0.9, 0.5 or 0.0) or a figure derived from log-probabilities, so no turn is ever unclear. |

### Repeated Requests

On a session with at least one `side_effects` tool, or with a voice agent that has tools, a request that nearly repeats a task that is running, or one that completed in the last 30 seconds and committed something (or may have: its effects are unknown), does not silently start a second task. A finished task that committed nothing was a lookup, and a request like it (a question about its answer: "And which one is the largest?" after "Tell me about the planets") simply runs. The agent asks "Do you want me to change it, or is this a second one?" and holds the request:

- **A second one** ("another one", "both") - the held request becomes a new task.
- **Change it** ("change the first one", "instead") - a running task is revised with the held request. A task that is already over cannot be revised, so the request becomes a new task.
- **Neither** ("no", "never mind") - nothing starts, and the agent says "Okay, I'll leave it."
- **Anything else** - the held request is dropped and the new words are handled as a turn of their own. If they repeat the request, it starts without a second question.
- **No answer for `policy.hitl_answer_timeout_ms`** - nothing starts, and the agent says "No problem, I'll hold off for now."

Whether a request repeats a task is the front model's reading (see [How an Answer Is Read](#how-an-answer-is-read)): it is shown the titles of those tasks and the new request, and names the task asked for again or `new`. "A table for four" after "a table for two" is the same table; "a taxi as well" is not. A session whose tools only look things up runs a repeated request again without asking. The quoted words above and below are examples of what the front reads as each answer, not a list the gateway matches.

### How an Answer Is Read

When the caller's turn may answer something the agent asked, the gateway asks the front model what it means, with the agent's question, the caller's words and the possible readings, and acts on the one it names (`assistant_transcript` and the task events are as before):

| Asked | Readings |
|-------|----------|
| A confirmation ("Shall I book ...?") | `yes`, `okay` (a weak yes: an irreversible action is asked again), `no`, `change` (the caller's words revise the task), `cancel`, `other` |
| A choice | one of the options, `any` (no preference: the caller's words go to the agent, which picks), `none`, `cancel`, `other` |
| A value | `answer` (the caller's words are the value), `cancel` |
| A question on the screen | `yes` or `no` (the caller is pointed at the screen again), `other` |
| The choice offer, the undo offer, the offer of updates, "change it, or a second one?" | as in their sections, or `other` |
| A request on a session with `side_effects` tools while such a task runs or just finished | the task it repeats, or `new` |
| A follow-up the front named of a finished task an agent did | `1` (it is about that task: its result, a detail, a change, more of the same work by that agent), `new` (something else, or work another kind of agent would do: a new request for the session's background) or `thanks` (it only thanks or says goodbye: the persona's thanks line, nothing answered from the result); the reading is shown what that agent does (its description) and five examples; without a reading in time the follow-up stands. Words that name another agent of the session (its name, or a word of six letters or more that only its description has, and the finished task's agent and title do not) are not read apart: they are a new request, the orchestrator's to place (live, launch demo take 23: "Great. Can you also get the download numbers in the terminal?" after the browser's release check went to the browser agent when the reading had no label in its 1.5 s on the loaded GPU). Live rehearsal 1 (28 October): after the browser's release check the 2B front named every later turn a follow-up of it, thanks too; offline the finished-task gate set of its turns settles 130 of 130 right with the reading, 60 before. Live MA7: Qwen3.5-2B named `follow_up` of a hotel search for "Do I have a note about the dentist?" whatever the prompt said, and read apart it is `new`. A task that was one MCP tool call is not followed up at all (it has no conversation to go on with): what the caller says after it is a new request, the orchestrator's to place ("Delete my note called ..." after a notes search). |
| A request the front delegated while the caller's latest task started less than 10 seconds before (any session; the repeat reading above comes first) | `1` (it is about that request: the same thing asked again in other words, a detail of it, a change to it; the running task takes the words, as for an `update`, and the decision's line is its acknowledgement) or `new` (a task of its own); without a reading in time the delegate stands. The task is the one that was running when the caller's turn ended (what the front was shown): one that completes after that, before the reading is back, is still read against, and `1` about it is a `wait` (its answer, on its way, answers the words; no second task). Live PR2 and PR8: Qwen3.5-2B delegated "Can you check its delivery status?" right after "Where is my parcel?" in every run, a second task, and no wording or example of the decision's own prompt changed that without costing a gate case; read apart, with six examples of its own, it is `1` (offline 10 of 10, eight held-out follow-ons 10 of 10, twelve new requests right after a task started `new` 10 of 10, about 30 to 50 ms). |
| A repeat of the number or the code the front named while the agent's last line holds a number | `number` (only the number is said again) or `line` (the whole line, a repeat with no value); without a reading in time the front's value stands. Live CT1: Qwen3.5-2B named the number for "Sorry, can you say that again?" after "Your confirmation code is 4 4 1 7." in every run; read apart it is `line` (offline 10 of 10), and "What was the number again?" stays `number`. The repeat waits for the reading (about 30 to 50 ms). |

A reading is one short request to the front's server (about 0.1 s on Qwen3.5-2B), made after the turn ends and before anything is started for it. The last two are asked only in their situation, so every other turn is as the front decided; their examples are shown to the model as earlier turns of the reading, and they are the model's reading, not a list of words the gateway matches. `other` makes the turn an ordinary one: the front decides it as any other. Without a reading in `front.total_budget_ms` (the front is down or slow) a question is asked again and an offer is not taken; nothing is guessed. A speech-to-speech session reads the caller's answer to its spoken question with the same labels on the server's front (see [Speech-to-Speech Providers](#speech-to-speech-providers)); no lexicon reads an answer anywhere (owner, 24 October).

### Sensitive Values

A card number, a PIN, a password, a one-time code and the like are never taken by voice. The categories are those of the pack plus the persona's own.

- **The caller says one** - a turn that names a category (also in the plural: live P1 had Whisper hear "my card number is 4111 ..." as "my card numbers 4111 ...") and carries at least three digits is not passed on: no task starts, the words are kept out of every later background run, and the agent says "I can't take your card number on this call for security reasons." A password spoken as words carries no digits and is not caught by this rule.
- **The background asks for one** - an `ask_caller` question that names a category is asked on the client's screen (see [Questions on the Client's Screen](#questions-on-the-clients-screen)). Without a screen (`hitl.channels: ["voice"]`) it is not asked: the client gets `task_question` (its `prompt` is the decline line) and at once `task_answer_received` with `outcome: "decline"` and `by: "policy"`; the caller hears the decline line and the LLM is told that the value is never taken by voice.
- **The background asks for one in its answer** - a sentence that names a category and asks for it ("Please tell me your current password.", or the bare "Your current password, please.": live P1, 26 October) is not spoken; the caller hears the decline line in its place, once per task. After a decline, a sentence of the same task that asks again without the name ("Please share it with me now.") is not spoken either. These sentences stay in the task's `summary`.

When the caller says a value with no question open, the transcript of the turn still goes to the client as `stt_result`, and the speech-to-text vendor has heard the audio. While the value is asked on the screen or the keypad it is not (see [Questions on the Client's Screen](#questions-on-the-clients-screen)).

### Another Language

A turn in another language never starts a task and never answers a question. The language is taken from the speech-to-text result when the provider names one (the same value `stt_result` carries as `detected_language`: a multilingual Deepgram model with `language: "multi"`, OpenAI's Whisper), and otherwise read by the front model from the words: once a turn's decision has named its act, the front's server is asked, in a short reading of its own (on the lane's readings slot, at temperature 0), the language the caller's words are in: the front copies the caller's first word and then writes the language's English name (the gateway maps it to its code); a `wait`, a `control` (a wish to talk in another language, said in English, is the decision's `language` control) or a decision that failed needs none. Until it is back the act waits (a `stop` excepted, which cuts at once), and a code other than the pack's makes the turn one in another language. It is asked at the act, not beside the decision: two requests read together on the server read the same prompt differently (live PR10, r14: "Also, fix the failing test ..." was `progress` beside the reading, `delegate` alone). A turn whose language the recogniser named (its `detected_language`, as Whisper and a multilingual Deepgram model give it) is not read again: the recogniser's reading decides. The reading costs every other request a turn makes (a typed turn, a recogniser that names no language) one more short front request and its time (live, on the loaded GPU, 0.2 to 1.2 s after the decision's act, r14; asked on every request it put the first acknowledgement 0.6 s later, live L1, r14-verify). A newer caller turn that supersedes the turn stops its reading with its decision, so it holds no slot of the server beside the newer turn's decision. No word list or script check decides it (owner, 24 October: the function-word lists and the script check were removed; the copy spans no longer depend on the words' language). The reading is made only while the conversation is in its pack's language: after a switch to another language the caller's turns in it are the conversation's own. The reading's prompt carries sixteen short examples as earlier turns (sentences in English, Spanish, French, German, Italian and Portuguese, most of them naming a language, a country, a city or a dish of another language): told only in words, the 2B front named the language a sentence mentions, and live (r14, the first build) it read "What is the capital of France?" as `fr` in every session that asked it, so the turn was asked again. The model writes the language's name, not its code (r15, 25 October): with codes, on a Spanish pack the 2B front read "¿Cuál es la capital de Francia?" and "What is the capital of France?" as `fr` 10 of 10 each; with names, the reworded instruction (the language of the sentence itself, never that of a place, a person, a dish or a language it names) and examples that are not all English, a held-out set went from 26 to 37 of 44 right (Spanish pack 10 to 19 of 22), the Spanish pack's probe cases from 60 to 80 of 80 and the English pack's from 380 to 400 of 400 (ten seeds each). The front copies the caller's first word before the name (r15-fix, 26 October): live LP1 on a Spanish pack still read "¿Cuál es la capital de Francia?" as French, because the reading was a coin toss (Spanish 0.40, French 0.39 on Qwen3.5-2B) that the decision generating beside it on the server tipped; with the first word written first, offline a development set went from 35 to 41 of 41 right, a held-out set written before the change from 21 to 26 of 26 (Spanish sentences naming Lisbon, Canada, Chicago or Brazil among them), and under a generation running beside it 0 of 670 readings were wrong against 100 of 670, at about 40 ms more a reading (median 92 against 54 ms on an own server). Live LP1 then passed 3 of 3 on request and 1 of 1 on streaming. A sentence that starts with a foreign place's name ("París es muy bonita, ¿verdad?", "Londres, ¿qué hora es allí?") is still read as that place's language, before and after: a limit of the 2B front. Measured offline with the examples (r14, 24 October, Qwen3.5-2B on an own server, a set the examples are not from): 13 of 13 turns in Spanish, French, German, Italian, Portuguese and Hindi read as another language, and 32 of 38 English turns that name a language, a country, a city, a dish or a person read as English (without the examples 29 of 38); the misses are "Can you speak Spanish with me?", "Can you talk to me in Chinese?" and "Say it in Spanish, please." (wishes the decision reads as its `language` control, which keeps the turn English), "Can you check flights to São Paulo next week?" `pt`, "Do you have any Korean barbecue sauce?" `ko` and "Can you find a German speaking doctor?" `de` (asked again: a limit of the 2B front, recorded). The same reading asked in the decision's own prompt (a `wait` reason `foreign` with an example) was never chosen (0 of 80) and cost the control gate set 9 of its 53 cases, and two labels (the pack's code or `other`) were read as English every time, so neither is used. A speculative run the gateway starts on a turn's words before the front's act (as for any turn) is discarded unseen when the turn is read as another language.

- **One such turn** - the agent says "Sorry, I didn't catch that. Could you say it again?".
- **Two in a row, on a session with a `conversation_config`** - the agent says the persona's notice ("Sorry, I can only help in English on this line.") and the session steps down: `config_warning` with code `interaction_language_step_down` is sent, and from then on every caller turn goes straight to the background LLM with an empty history. The front, the acknowledgements, the holding lines, the confirmations and the tools are off for the rest of the call; the answers are still relayed sentence by sentence, the caller can still interrupt, and the task events are still sent.
- **Two in a row, on a session whose only LLM is `interaction.tasks.llm`** - there is no plain conversation to step down to: the agent keeps asking the caller to repeat.

### What Is Never Spoken

Each sentence of a background answer is checked before it is spoken. A sentence is dropped, and is not part of the task's `summary`, when it is or contains:

- **A link** - `http://`, `https://`, `www.` or a name under a common top-level domain such as `.com` or `.org`.
- **A long number the caller did not give** - seven or more digits in a row (spaces, dashes, dots and brackets between them allowed), unless the caller said those digits earlier in the call. Prices, times, dates and short references pass.
- **Prompt scaffolding** - a label of the model's own prompt followed by a colon, such as `HEARD:`, `FRONT:` or `USER:`. A label at the very start of a sentence is stripped and the rest is spoken: a speaker label (`Front: ...`), any word of three or more capitals (`ORDER: ...`), or `Answer:` in any case (live MA1 and MA7, r8-verify: gpt-oss-20b wrote the answer marker in title case, "Answer: Your note ... is being deleted.", not the `ANSWER:` line the answer gate looks for, so its round was released whole at its end and the label was said). A sentence that starts with `HEARD:` is dropped whole.
- **The background's own instructions** - on a background the gateway prompts (the LLM tier and an OpenAI Responses entry), a sentence that says again who its prompt tells it it is: the first sentence of the persona's preamble ("You are the backend for ...") or of the operator's prompt. It does when a run of at least three of its words, in order, is also in that line and covers 60 percent of both the sentence and the line (the transcript echo filter's measure). Quoted text and what follows a colon in that line are the operator's to say, and pass (live P1, r15-verify: qwen2.5-3b said "You are the help desk for customer accounts.", its prompt's first line, to the caller). The rest of the prompt is not compared, since it also holds what the caller is to be told: the operator's facts ("The store opens at nine in the morning.") and the preamble's line for a forbidden topic ("Say it is not something this line can help with.") are spoken when the answer repeats them. A paraphrase, such as "You are part of the system now.", is not caught.

When every sentence of an answer is dropped, the task fails and the caller hears "Sorry, I couldn't get that done just now."

## Pauses in the Caller's Turn

The caller's turn ends when the speech-to-text ends its segment (its speech-final result), sooner when the gateway's turn-end model (Smart Turn, asked 200 ms into each pause of the caller) is sure that the caller has finished, and at the latest after 1.5 seconds of silence. A turn whose next words come before it is decided, beginning within 1.5 seconds of its end, was not over: the next turn carries its words (live, launch demo take 22: "Great. Can you also get" ended at a pause, and "the download numbers in the terminal?" read alone went to the finished browser task as a follow-up). A pause in which the caller is still thinking is held, not answered:

- **Held** - a speech-final result does not end the turn when the words end on one that leaves the sentence open ("and", "to", "the", ...), whatever the turn-end model says (it hears sound, not words: live, launch demo take 24, it was sure at a 200 ms gap the voice activity detection heard inside "... the download numbers in the terminal?", the turn ended at "the", and "terminal?" became a turn of its own), and such words are not claimed early either (only the silence ceiling claims them); and, in a turn the caller began while the agent was silent, when the model is sure that the caller has not finished (a probability under 0.05), when its verdict on the pause is not in yet, or when the caller has already started to speak again. Nothing is said and no task starts. The turn ends 800 ms after that result, at once when a verdict comes that would not have held it, and not at all when the caller goes on: their words join the same turn, and each later pause is judged again. The same holds when the gateway had already asked the speech-to-text for the end of the segment (a sure verdict) and the caller speaks again before that final comes: its words are kept and the turn goes on (live TP1: the final came 300 ms after the caller had gone on, and the rest of the story became a second task). A merely unsure verdict (0.05 to 0.7) on words that do not dangle does not hold the turn: in measured calls most such pauses were the caller's end, and holding them made every such answer 800 ms later. Once a pause of the turn was held and the caller went on, an unsure verdict holds the next pause too: the caller is telling a story (live TP1: the story's second pause, after "... where the kids can swim and play.", was judged 0.57 three runs of three and ended the turn there).
- **Late words** - words the speech-to-text brings after the gateway closed the caller's sound as a turn with no words (at the silence ceiling), within 3 seconds, are that sound's: the turn has its onset, so a "yes" to a confirmation binds (live, take 24: Deepgram's "Yes. Go ahead." came 2.6 s after the caller stopped, the turn had no onset, and the yes was asked again, "Just to be sure: ...").
- **Not held** - for a thinking pause, in a turn that began over the agent's speech (an interruption, a continuer, side talk: it wants its answer now); at all, while an answer to the agent's question is expected (a "yes" binds at once), on a request-response speech-to-text (its final follows an upload that the turn-end model or the silence asked for), on a speech-to-text with its own turn model (Deepgram Flux), and for words the gateway's voice activity detection did not hear.
- **The acknowledgement waits** - when the caller speaks again after the end of a turn, its acknowledgement is not said while they speak, and the next turn that ends takes its place.
- **Nothing unheard starts over a caller who goes on** - when the caller speaks again within 1.5 seconds of the end of their turn (the turn was not over: the turn-end model took a pause for the end) and none of the agent's line with the text-to-speech has been heard yet (the synthesis can take a second or two), the line is taken back: an answer, a relayed answer or a client's `speak` line waits and is said whole once their turn has ended and been settled; an acknowledgement or a holding line is dropped. The client gets `agent_audio_stopped` (reason `policy`). Later than 1.5 seconds the caller's speech is a new turn and the line plays as usual (over the caller it is a barge-in, judged as one); only an urgent question may start while the caller speaks, as before.

## Waiting

While a task runs and nobody speaks, the agent keeps the caller informed: a progress line on a real change of the task (none in the first `policy.progress_min_wait_ms`, at least `policy.progress_min_gap_ms` apart, at most `policy.updates_max_per_wait` in a wait), a holding line after `policy.hold_after_silence_ms` of silence, and as long again later one offer of a choice: "It's still going. Do you want to keep waiting, or should I stop it?" (`assistant_transcript` kind `choice_offer`). Its answer counts for 10 seconds; unanswered, it is an agreed wait, and it no longer holds a finished task's update back (live, take 24: the caller's "Keep going." was taken for the agent's echo, the offer stayed open for 3.5 minutes, and two finished results waited all that time).

- **Keep waiting** ("keep going", "no rush", "sure") - the agent says "Okay." and the wait goes on.
- **Stop** ("stop it", "forget it") - the running task is cancelled, as with "cancel that".
- **No answer within 10 seconds, or other words** - it is an agreed wait: a check-in every `policy.quiet_checkin_ms` until the wait is `policy.agreed_wait_max_ms` old. Other words are a turn of their own.

## Listening Sounds

While the caller tells a long story the agent makes short listening sounds ("mhm", "okay", "I see"), as a person on the line does. The words are the language pack's (its `backchannel` group); they are made once at session start in the session's voice (after the session's warm-up lines, the acknowledgements among them, so the first turn's acknowledgement is ready; then the lines said when a service fails), played 3 dB quieter than speech and on their own lane: they are not lines of the agent (no `assistant_transcript`, nothing in the conversation history), and the client sees them as `audio_segment` with `lane: "backchannel"`. A listening sound wanted before they are made (a long turn at the start of a session, while the voice still makes the warm-up lines) has them made in that turn, in its pauses; the turn's later pauses can then have one (live BC2: the first session of a gateway got none in its first long turn).

A listening sound plays at a pause of the caller when all of these hold:

- **The turn goes on** - the turn-end model says the caller has not finished, after enough of the caller's speech in the turn (below). It is asked 200 ms into the pause and answers in about 100 ms, before the caller goes on: it keeps the spectrogram of the last 8 s as the audio comes, and on a CPU whose cores differ in speed (big.LITTLE) it runs on the fast ones (on a slow core it took 590 ms, too late for most pauses).
- **Nothing else is said** - the agent is silent and no answer to a question or a confirmation is expected.
- **Not too often** - long enough after the last one and after the agent's last line, not more than the turn allows, and some such pauses pass without one (below).
- **Nothing private** - the turn so far names no sensitive category (a card number, a password, ...), and no sensitive value is being typed or entered on a screen.
- **The session has them** - `duplex.backchannel` is `auto` (on unless the caller is on a phone line) or `true`, and the intensity is not `off`. A persona's `backchannel_clips` chooses the sounds.

How often depends on the language and the intensity. The pack's `backchannel.timing` holds the language's `medium` numbers (English: `{"gap_ms": 6000, "skip_every": 3, "min_voiced_ms": 1500}`, about one sound every 10 to 20 seconds of the caller's speech, as listeners give them; a pack without it takes English's), and the intensity scales them: the persona's `backchannel_intensity`, `medium` when the persona leaves it unset (a caller on a phone line hears none under `auto` whatever the persona says). `duplex.backchannel.intensity` lowers it for the session. In English:

| Intensity | Caller's speech in the turn first | Since the last one | Most in one turn | Pauses passed over |
|-----------|-----------------------------------|--------------------|------------------|--------------------|
| `low` | 2,142 ms (`min_voiced_ms` × 10/7) | 12 s (`gap_ms` × 2) | 1 | every second (`skip_every` × 2/5, at least 2) |
| `medium` | 1,500 ms | 6 s | no limit | every third (`skip_every`; 0 passes none over) |
| `high` | 1,071 ms (× 5/7) | 4.32 s (× 18/25) | no limit | every sixth (× 2) |
| `off` | none play | | | |

"Since the last one" counts from the last listening sound and from the end of the agent's last line, cut or not: a caller who has just stopped the agent ("wait a second") hears no listening sound in the pause after it.

**Every sound is checked before it is used.** Once its leading and trailing silence (10 ms frames under -45 dBFS) is trimmed, a clip must be at most 600 ms long and not silent. When the session's speech-to-text answers once per upload (a request-response recogniser, cheap to run on a clip), it also listens to each clip, which must not hear more words than the clip's text has: this catches a voice that spells "mhm" out ("M.H.M."). A streaming recogniser is not run on clips. Audio that is not 16-bit PCM is used unchecked.

- **A clip that fails** is replaced by the pack's fallback word (`backchannel.fallback`, a clip id of the group; English `okay`), made and checked the same way. When no clip passes, the session makes no listening sounds and says so once: `interaction_updated` with `degraded: ["backchannel_unavailable"]`.
- **Recorded clips** - the operator may record the sounds of a voice: `interaction.clips_dir` holds `<provider>/<voice>/<language>/<clip id>.wav` (the session's `tts_config.provider`, its `voice_id` or `default`, the pack's language code, the clip id of the group, for example `openai/alloy/en/mhm.wav`). A recording replaces the rendered clip of that id; it is mixed to mono, resampled to the session's `tts_config.sample_rate` and checked like a rendered one (a recording that fails is rendered instead). Sessions whose audio is not PCM render every clip.
- **No sound before the bank is ready** - a listening sound plays only once every clip of the session is checked. Listening sounds turned on mid-session (`interaction_update` with `duplex.backchannel`) are made then. A session keeps its voice and language for its whole length, so its bank is made once.

A listening sound yields as soon as the caller speaks again or their turn ends, so it never plays into the agent's reply: one that has not started is dropped, one that plays fades out over 40 ms (the client still plays what it holds of the 150 ms lead).

## When Services Fail

A call depends on the recogniser, the front model, the background (an LLM or the orchestrator) and the voice. When one of them fails or stalls, the agent says so in short pre-made lines in the session's own voice, as a person whose computer froze would ("Sorry, my systems are acting up. Bear with me a moment."), and when it stays down it says goodbye and the call ends. The lines are not a way of understanding the caller: they only say, honestly, that something is wrong, and never name a vendor.

**The lines** are the pack's `failure` group (English: `docs/duplex-agent/front-model/phrase_banks.en.json`), each with an id (`clip`) and a kind (`subsituation`): three `stall` lines, three `hearing` lines (the recogniser), `exit`, `exit_follow_up` and `back`. A persona's `banks.failure` replaces the lines of the kinds it gives; `failure.lines` replaces the words of lines by id.

**Made before they are needed.** At session start, with the listening sounds, each line is taken from, in this order: the operator's recording `interaction.clips_dir/<provider>/<voice>/<language>/failure/<line id>.wav`; a rendering of the same words in the same voice that this process made before, or that is kept under `.../failure/cache/<line id>-<digest>.wav` (written by the first session in that voice; without `clips_dir` only the process keeps them); else it is rendered in the session's voice. Each is checked: not silent, at most 12 seconds once its leading and trailing silence is trimmed. A line that fails its check, or that cannot be rendered because the voice is down, is the server's default set's: the same lines made once at server start in `interaction.failure_voice` (or the operator's recordings of that voice), resampled to the session's rate. Each of those renders waits until no session is open (at most 60 seconds): on a speech server the calls share, they held up the first answers of a gateway's first session. `ready.interaction.failure.lines` says what the session starts with: `session` (every line in its own voice), `default` (the default set until the session's own are rendered) or `none` (the lines are rendered now and there is no default set). A session whose audio is not PCM16 renders its lines every time and has no default set. The lines are played by the playback pump as listening sounds are, at speech level: nothing is synthesised, no model and no network is needed when they play.

**The health watcher** is fed by the code paths that already report failures, never by what the caller said:

| Service | Fails when | `degraded` | Line | Ends the call |
|---|---|---|---|---|
| Recogniser | it reports an error and the next result does not come within `failure.stall_after_ms`, or (a streaming recogniser) 3 seconds of the caller's speech get no result | `recogniser_unavailable` | `hearing` | `failure.max_wait_s` after the first line |
| Front model (run by the gateway) | a caller turn waits for it while its server is down; the turn is asked again once the model is back | `front_unavailable` | `stall` | not back within the supervisor's restart window: interaction mode ends ([The Front Model's Server](#the-front-models-server)), or, on a session with no plain conversation to go on as, the call |
| Background | a run of the session's background gives no first sign of life within `failure.stall_after_ms` while the caller waits for a task: its first token for the session's LLM, an orchestrator, a voice agent, a DAG and a streamed OpenAI Responses backend; the backend's answer to the request for a webhook, an A2A agent, an MCP task tool and a polled Responses backend (each works on the task on its own once it has taken it) | `background_stalled` | `stall` | `failure.max_wait_s` after the first line; the tasks follow `tasks.session_end` |
| Voice | a line of the agent's gets no audio within `failure.stall_after_ms`, or its synthesis fails and the next one does not succeed within that time | `voice_unavailable` | `stall` (pre-made, so it still plays) | `failure.max_wait_s` after the first line |

An agent of an orchestrator plays no line (its task fails with a notice, chapter 8), and a connection lost to the client plays nothing (nobody hears it; [Tasks After the Call](#tasks-after-the-call) applies). A line the voice could not give (its synthesis failed, or gave no completion within 10 seconds) is never apologised for as a failed task: the client gets an `error` with code `interaction_tts_failed` once in a run of such failures (a line heard to its end ends the run), and the caller hears the voice's own `stall` line from the watcher above. A question it carried is asked again. Live (launch demo take 22, 28 October): Deepgram refused one flush over its rate limit (`EXCESSIVE_FLUSH`), the gateway's streaming client then paired each later completion with the utterance before it, every line played and failed on the floor's watchdog, and each failure said "Sorry, I couldn't get that done just now.", which failed in turn: it was said every 13 seconds for six minutes. The streaming client now sends a refused flush again (after 1 second, doubled for each refusal in a row, at most 8) and completes the utterances each flush covered.

**On a speech-to-speech session** (`/realtime`, and a room's realtime voice, see [Speech-to-Speech Providers](#speech-to-speech-providers)) the provider is the voice, the recogniser and the front at once, so its failures are one service, `voice` (`degraded`: `voice_unavailable`). The watcher is fed by the provider's errors (a warning is not one), by a caller's turn it does not answer (no audio, words, function call or end of a response within `failure.stall_after_ms` after the caller stopped speaking: the provider's speech events, with manual turns the gateway's analyser, else the provider's transcript of the caller), and by its connection: back after a reconnect is well again, lost for good (the provider's supervisor gave up) is the exit at once. The lines are the server's default set (`interaction.failure_voice`; the provider's own voice cannot render them), resampled to the provider's output rate and played into the session's output audio as the provider's audio goes out (binary frames on `/realtime`, the room's audio track), at a gap: the caller silent for half a second and none of the provider's audio playing. Stall lines are spaced, rotated and capped, the back line and the exit line follow the same rules as above, each line comes with `interaction_updated` (`failure`, `degraded`), the session's history gets the note, and after the exit line the client gets `session_failed` (`service: "voice"`) and the gateway closes the socket (on a room's session with code 1011). Without a default set no line plays and the session still ends with `session_failed`. A provider that does not answer a caller's turn on purpose (a backchannel it ignores) gets a stall line all the same. Not on the `/v1/realtime` relay (its audio is the vendor's own events).

- **Stall** - at the next slot: the caller has been silent for half a second (by the voice activity detection, whether or not the turn has ended: a recogniser that is down ends no turn) and none of the agent's audio plays. A line that has no audio yet (a session's first seconds, with no default set) waits for it. Further stall lines come at most every 8 seconds and at most three in one outage, rotated so that none repeats. A caller who starts to speak over one fades it out.
- **Back** - once every service is well again, the `back` line ("Thanks for waiting, I'm back.") plays if a stall line was heard: right behind the stall line when that still plays, ahead of the answer. When the agent's own line plays first (the voice came back with it), the back line is not said.
- **Exit** - `failure.max_wait_s` after the first stall line with the service still down, or at once when the front is gone for good on a session with nothing to go on as, the exit line plays (it waits only for the caller to be silent): `exit_follow_up` ("... I'll get back to you once they're back.") only when the session has a way to get back to the caller (`tasks.push_url`, `failure.follow_up`, or a verified caller with caller memory), else `exit` ("... Please call back a little later."). Once it has played, the client gets `session_failed` with the live tasks and why, the same body with the session's `stream_id` (and no `t_ms`) is pushed to `tasks.push_url` signed as [The Push](#the-push) is (`Idempotency-Key: <stream_id>:session_failed`), the tasks follow `tasks.session_end` as at a hang-up, and the gateway closes the socket with code 1011. Transferring the caller to a person instead (chapter 9's `human`) is not built.
- **The client and the history** - each line comes with `interaction_updated` naming it in `failure` (`line`, `kind`, `service`, `text`) and listing what is degraded, and with `audio_segment` of kind `failure` on the `front` lane; it is not an `assistant_transcript`. The background's history gets a note: `[the background failed; the agent said: Sorry, my systems are acting up. Bear with me a moment.]`, `[the background is back; ...]`, `[the voice stayed down; ...]`.

## What the Caller Heard

What the caller heard of the agent decides several things: a "yes" binds only after the read-back was heard, "say that again" repeats the line the caller heard last, and a background is told how much of its answer was heard. The gateway estimates it from the audio it delivered. A client that knows what it actually played (it buffers, pauses, or plays on another device) reports it, at most four times a second:

```json
{"type": "playback_position", "utterance_id": "u_41", "played_ms": 1320}
```

`utterance_id` is the one of `audio_segment` and `assistant_transcript`. From the first report on, what the client reports is what the caller heard:

- **Heard in full** - an utterance whose audio the gateway delivered counts as heard when the client reports it played to within 300 ms of its end, at the time of that report. Until then its `assistant_transcript` stays `heard: "none"` and a confirmation it reads back is not yet heard.
- **Heard in part** - when the client reports a later utterance, or the agent is cut, an utterance it did not play to the end was heard as far as it reported (`heard: "partial"`), or not at all.
- **Say that again** - repeats the line the client last reported playing, the line it stopped in.
- **A client that stops reporting** - 2 seconds after its last report, the gateway's estimate stands again for what it holds.

## Personas

A persona is what the front sounds like: its name and organisation, its phrase banks and template wording, its tone, its listening sounds. Four are packaged (see `front.persona`). A persona can also be given as an object in the shape of `docs/duplex-agent/front-model/persona.schema.json`; the gateway reads `id`, `name`, `org`, `role`, `channel`, `language`, `tone`, `formality`, `max_words`, `answer_words`, `backend_capabilities`, `delegate_when`, `do_not_delegate_when`, `forbidden_topics`, `social_scope`, `backchannel_intensity`, `backchannel_clips`, `interruption_notes`, `sensitive.extra_categories`, `banks`, `template_overrides` and `protected_terms`.

Such a persona is checked like the packaged ones before it is used: its id is 1 to 64 letters, digits, `_`, `.` or `-` (not `default`); `name`, `org` and `role` are 1 to 80 characters; every bank line belongs to a known group and passes the fact guard (no claim that something is done, no prediction of an outcome, no time promise, no promise of a channel, no role label), an acknowledgement is at most 24 characters, a template's rewording keeps the template's slots, and `backchannel_clips` names clips of the backchannel bank.

- **From the operator or the agent's author** - `front.persona` as an object in the server's `default` or `agent_default` block, an alias definition or an agent entry. A persona that fails the checks gives `interaction_value_ignored` and the default persona.
- **From a tenant** - with `interaction.tenant_personas` on, `PUT /v1/interaction/personas/{id}` registers a persona under the request's authenticated id. The body is the persona object (its `id` is the path's). The answer is `200` with `{"id", "version"}`, `422` with `{"error"}` naming what failed, `409` when the tenant already keeps 20 personas, or `404` when the switch is off. Each `PUT` adds a version; the newest five are kept. Concurrent `PUT`s each get a version of their own, and the cap of 20 holds: the check and the write are one step (a script in the task Redis, one lock in a process without it). A session of the same tenant selects it with `front.persona: "<id>"` (the newest version) or `"<id>@<version>"`; a tenant's persona is looked up only for an id no packaged persona has. With `interaction.task_redis_url` the personas are kept in that Redis, for every gateway process.
- **Reading and removing** - `GET /v1/interaction/personas/{id}` answers `200` with `{"id", "version", "versions", "persona"}`: the newest version (or the one `{id}` names as `id@version`), the numbers of the versions kept, oldest first, and the persona object of that version. `DELETE /v1/interaction/personas/{id}` removes every version and answers `204`. Both answer `404` when the switch is off or the tenant has no such persona or version. A session that runs a removed persona keeps it to its end; a later session that names it gets the default persona.
- **Never from a session** - a session's own block may only name a persona; an object there gives `interaction_override_refused`.

## Caller Memory

Caller memory is off unless the server has `interaction.caller_memory_key`. It keeps up to ten short facts about a returning caller, newest first, for 90 days, and gives the first three to the front model's call header and the background's caller context at the start of each call. It never keeps numbers, codes, addresses, amounts or links: account details come from the background.

- **Who the caller is** - the operator's backend signs the caller's identity and the client passes it in `front.caller.identity_token`: `v1.<payload>.<mac>`, where `payload` is the unpadded base64url of `{"sub": "<caller id>", "tenant": "<authenticated id>", "exp": <unix seconds>}` and `mac` the unpadded base64url of HMAC-SHA256 over `v1.<payload>` keyed with `caller_memory_key`. A token is valid for at most five minutes. A token that is forged, expired, for another tenant, or sent to a server with no key gives `config_warning` `caller_identity_rejected` (or `caller_memory_unavailable`), and the call runs without memory.
- **Writing it** - `PUT /v1/interaction/memory/{subject}` with `{"facts": ["prefers aisle seats", "uses a wheelchair"]}` replaces what is kept about that caller of the request's tenant, the most important first; an empty list forgets the caller. At most 10 facts of 1 to 80 characters, with no digit, `@`, currency sign or link (`422` otherwise); `404` when memory is off; `204` when kept.
- **The background writes it too** - after a call whose token was valid, a session whose background is an LLM (its `conversation_config` or `interaction.tasks.llm`) asks that model once, on its own, what is worth keeping about the caller: it is given the facts the call started with and the call as the caller heard it, and writes at most three lasting facts in the caller's own terms. Those that pass the rules above are put in front of what is kept, none twice (whatever the case), and the oldest beyond ten are dropped. Nothing is written when what is kept cannot be read, or the model gives nothing within 30 seconds. A voice agent, a DAG and the operator's backends write nothing: their platform or the operator writes with `PUT`.
- **Reading it** - `GET /v1/interaction/memory/{subject}` answers `200` with `{"facts": [...]}`, everything kept about that caller of the request's tenant, newest first (`[]` for none); `404` when memory is off.
- **Where it is kept** - under a keyed hash of the tenant and the caller, in `interaction.task_redis_url` when set (else in the process). The read at call start waits at most 150 ms.

## Echo

When the caller's device plays the agent and its microphone picks that up, the agent's own voice comes back on the caller's channel. Three defences keep it from interrupting the agent or from being taken for a request.

| Defence | Setting | What it does |
|---------|---------|--------------|
| Transcript filter | always on | A transcript of three or more words, 60% of which the agent said in the last 5 seconds, is not a caller turn. Over the agent, one or two words that its line playing (or ended in the last 1.5 seconds) has in a row are its echo too (a spoken number counts as its digits: "10" is the agent's "ten"); in a turn of its own a short reply ("Aisle.") is the caller's. Words taken for the echo are a wait whatever the front reads in them: they never stop, hold or change the call (live S4, r16-verify: the front read the interim "our kitchen" over "Our kitchen is open ..." as a control and it cut the agent). |
| Correlation gate | `duplex.echo.correlation_gate`, default `true` | The gateway keeps the audio it delivered and finds where it returns in the caller's audio (up to 1 second later). Voiced audio that this explains, by its waveform or by being no louder than the echo, does not count as the caller starting to speak: the agent is not lowered, paused or cut for it. |
| Echo canceller | `duplex.echo.aec`, default `auto` | WebRTC's echo canceller removes the returning audio from what the gateway analyses and from what the speech-to-text hears; sound that it removed is not the caller. `auto` turns it on for a caller on a phone line (a SIP participant of a LiveKit room, a socket client with `phone_line: true` or 8 kHz audio), for a client that says it cancels no echo itself (`client_aec: false`), and once echo was heard in `auto_enable_after_echo_episodes` stretches (2) within 30 seconds. Set `on` for a client that plays the agent through a loudspeaker. A browser cancels echo itself and needs `off` or `auto`. |

- **A caller who speaks over the echo still interrupts.** The gate lets a voice through that is at least 3 dB louder than the echo. A quieter caller is heard once the agent stops.
- **The first second.** The gate needs about 100 ms of echo to find it, and nothing is lowered meanwhile. A line's soft first word is enough: the search needs one chunk's worth of sound (32 ms above -50 dBFS) in its 256 ms window, not that much on average over it (live S4: with the synthesiser's soft "While ..." the second voiced chunk's window was below the whole window's floor, the echo was found a chunk later, and the two chunks before it ducked the agent for 340 to 380 ms). The canceller alone is slower: with the gate off, the agent may be lowered or cut on its own echo at the start of a line.
- **Words that come with the echo.** Without the canceller the speech-to-text hears the caller's audio as it arrives, echo included. While the gateway hears echo (and for `tail_ms` after), words that arrive with no sound of the caller's own open a turn that is dropped as the agent's, however short it is. An interruption is judged on the words that are not the agent's.
- **The speech-to-text with the canceller.** While the canceller runs, the speech-to-text gets its output (resampled to the session's input rate) in place of the audio as it came: the echo it removed is not transcribed. In a room that output replaces the audio after the room's noise filter. A canceller turned on during the call (`auto_enable_after_echo_episodes`) feeds the speech-to-text from then on. When the analyser stops, or cannot keep up (a full queue), the speech-to-text gets the audio as it came again.
- **A phone line with the canceller off** (`duplex.echo.aec: "off"`). A sound over the agent does not lower it. The agent is lowered and stopped when the caller's first words arrive.

The `duplex.echo` settings are fixed when the session starts: an `interaction_update` that names `duplex.echo` is refused with reason `not_mid_session`. With both defences off (`correlation_gate: false`, `aec: "off"`) the gateway keeps no copy of the audio it delivers.

## LiveKit Rooms and Phone Calls

A session whose `config` carries a `livekit` block runs interaction mode on the room's audio. A SIP call reaches the gateway as a participant of such a room. With `interaction.speech.realtime` the room's voice is a speech-to-speech provider instead of the cascade (see [Speech-to-Speech Providers](#speech-to-speech-providers)).

```json
{
  "type": "config",
  "stt_config": { "provider": "deepgram", "model": "nova-3", "language": "en", "sample_rate": 16000, "channels": 1, "punctuation": true, "encoding": "linear16" },
  "tts_config": { "provider": "openai", "model": "tts-1", "voice_id": "your-voice-id", "audio_format": "pcm", "sample_rate": 24000 },
  "conversation_config": { "base_url": "http://127.0.0.1:18742/v1", "model": "qwen3b-q4_k_m", "api_key": "local-dummy" },
  "livekit": { "room_name": "support-call-1042" },
  "interaction": true
}
```

- **One caller** - the session hears one participant: the first one whose audio track the gateway receives. With `livekit.listen_participants` set, it is the first of the listed ones. Nobody else's audio reaches the speech-to-text, and only the caller's leaving ends the session. A session without interaction mode still hears every participant.
- **Events in the room** - every event of [Events (Server → Client)](#events-server--client) that goes to the socket is also published in the room, as the same JSON, on the data topic `waav.interaction`. A phone caller has no screen and gets nothing.
- **Phone lines** - a caller whose participant kind is SIP is on a phone line. The echo canceller is on for it unless `duplex.echo.aec` is `off` (see [Echo](#echo)).
- **Audio** - the agent's audio is sent to the room 40 ms ahead of its playout time (150 ms on a socket). The caller's audio is analysed as it arrives, before the room's noise filter; the speech-to-text gets it after the filter (with the echo canceller on, the canceller's output instead).
- **What was heard** - a frame of the agent's counts as heard 80 ms after its playout time by a room's caller, and 150 ms after it by a phone line or a socket client: a "yes" binds only after the read-back was heard.
- **Listening sounds** - a caller on a phone line hears none unless `duplex.backchannel` is `true` (see [Listening Sounds](#listening-sounds)).

### Keypad Answers on a Phone Line

With `"hitl": {"channels": ["voice", "dtmf"]}` (add `client` to keep the screen for other clients), a caller on a phone line answers on the keypad. The keys are the SIP DTMF events LiveKit reports for the session's caller; anybody else's keys are ignored, and a session whose caller is not on a phone line ignores keys altogether.

- **Confirmations** - after the question the caller hears "You can also press 1 for yes, or 2 for no." Once the question has begun to play, `1` accepts and `2` declines, as a clear spoken "yes" or "no" would; `task_answer_received` has `by: "dtmf"`. Any other key does nothing. Spoken answers still count.
- **Sensitive values** - a value question that names a sensitive category (a card number, a PIN, a one-time code) is asked as "For your security, please type your card number on your keypad, then press the pound key." The caller types the digits and ends with `#`; `*` starts again. The digits go to the background as the answer, and `task_answer_received` has `by: "dtmf"`, `value: null` and `value_redacted: true`. A value said aloud is not taken: the caller hears "Please don't say that out loud. Use your keypad instead." Forms and sign-in links still need a screen.
- **A pause ends the value** - a typed value with no key for `policy.hitl_key_gap_ms` (5 seconds by default) after the last one is answered with the keys so far, as if `#` had been pressed. The question's own `policy.hitl_answer_timeout_ms` still applies when no key is pressed at all.
- **Choices by number** - after a choice the caller hears "You can also press 1 for Mumbai, or 2 for Pune." (the first nine options); once the question has begun to play, key `n` picks the `n`-th option (`task_answer_received` `by: "dtmf"`, the option as `value`). A key with no option does nothing.
- **The call's recording** - a room session with recording on (`livekit.enable_recording`) stops its recording while a sensitive value is typed on the keypad, and starts a new one when the question closes, at `<prefix>/<auth_id>/<stream_id>-part2/audio.ogg` (then `-part3`, ...): a LiveKit egress cannot be paused, so a call with typed values is recorded in parts. A confirmation answered with a key does not stop it. A session that ends while the value is typed has no part after it.

## Tasks After the Call

A live task does not stop because its caller hung up or lost the connection: `tasks.session_end` says which tasks run on, and `tasks.orphan_max_s` (30 minutes by default) how long.

- **`auto`** (the default) - a task runs on when it may change something (`side_effects`: the session has a tool, an agent or a backend that changes things), or when its result has a reader: a push address (`tasks.push_url`), or the caller of a lost connection, who may come back. A task whose only reader is that caller runs on for the grace (`tasks.reconnect_grace_s`) and is stopped then. Any other task is `cancelled` by `system` when the session ends.
- **`continue_all`** - every live task runs on, a queued one too (it starts when a running one ends).
- **`cancel_all`** - every task is `cancelled` by `system` when the session ends, as before this setting.
- **A call on the wire** - whatever the setting, a side-effecting call that the caller confirmed has been sent and cannot be taken back: it gets 30 seconds to answer, and the background then gets 30 seconds (or the rest of `orphan_max_s`, when the task runs on) to word its answer. A call that does not answer in time ends the task as `unknown` with `effects: "unknown"`.
- **Nobody to ask** - a task that runs on cannot ask the caller anything: its open question is closed as unanswered (`task_answer_received` with `outcome: "timeout"` and `by: "session_end"`), and a further call that needs a confirmation is refused.
- **Stopped** - a task still running when `orphan_max_s` is over, or at the end of the grace for one only the caller could read, ends `cancelled` by `system` with the effects it has (`unknown` when a call was on the wire).
- **The result is kept** - for ten minutes after the task ended, for `GET /v1/tasks/{task_id}` (see [Listing Tasks](#listing-tasks)).

### Coming Back

A connection that is lost is not a hang-up. The session ended without a close frame from the client (the socket broke, the idle timeout closed it, or the server shut down), so the caller may come back:

- **How** - a new `/ws` session of the same authenticated caller that sends the same `stream_id` in its `config` and runs interaction mode. With authentication off, the `stream_id` alone names the caller. Whoever holds both gets the outcomes, so a client that wants this sends a `stream_id` nobody can guess.
- **By when** - within `tasks.reconnect_grace_s` (60 seconds by default) of the lost connection. A caller who is back in time also gets an outcome that comes later.
- **What it gets** - the outcome of each task that went on, when it is known: `task_result` (or `task_cancelled`) with the task's own `task_id` and `task_ref`, and the agent says it. A completed task's answer is spoken word for word (`assistant_transcript` with `source: "background"` and the `task_id`); for any other outcome the agent says the line it would have said in the call.
- **Once** - the first connection that comes back takes the session's outcomes. A second one gets nothing, and nothing is pushed.
- **Task refs** - a `task_ref` is not used twice under one `stream_id`: a new task of the new connection continues the count (`t2` after `t1`).
- **With a resume key** - a session with `tasks.resume_key` is come back to with that key instead of its `stream_id`: a new session of the same owner with the same key, on any `stream_id`, within the grace, gets the outcomes as above, and the updates of an orchestrator's children wait for a slot as in the call. A clean close (a hang-up) is then come back to as well: the caller may call back. Task refs start again on the new `stream_id`; `task_id` tells the tasks apart.

A session the client closed itself (a close frame) has nobody to come back: its outcomes go straight to the push address.

### The Push

With `tasks.push_url` set, the outcome of a task that ended after its session is sent there when no connection came back for it: as soon as the task ends after a clean close, and not before the grace is over after a lost connection.

```text
POST <tasks.push_url>
Content-Type: application/json
X-WaaV-Timestamp: <unix seconds>
X-WaaV-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>" keyed with tool_secret>
Idempotency-Key: <task_id>

{"type": "task_result", "task_id": "task_5b1e9c0d", "task_ref": "t1", "revision": 1,
 "state": "completed", "status": "completed", "cancelling": false,
 "summary": "Your table for two is booked for seven.", "effects": ["booked a table for 2"],
 "spoken": "none", "streamed": true, "superseded": false, "stream_id": "call-1042"}
```

- **Body** - the `task_result` or `task_cancelled` event as the client would have received it, without `t_ms` and with the session's `stream_id`. A completed task's also has `update`: the short spoken update of its result next to the full `summary` (the front model's line, within 400 ms and with the checks of an update, else the template "Your request to ... is done: <the first sentence of the result>").
- **Signature** - as for a tool call (see [Tools](#tools)); absent when the server has no `tool_secret`.
- **Retries** - a 2xx ends it. A 4xx is taken as a refusal and is not retried. Anything else is tried again after 2 and after 10 seconds, with the same `Idempotency-Key`; after the third failure the result is only in the task list.
- **Who may set the address** - the operator: the server's `default` or `agent_default` block, an alias definition, or the agent entry. A session may set its own only where the operator allows it (`interaction.allow_client_push`, env `WAAV_INTERACTION_ALLOW_CLIENT_PUSH`; never in Bud mode): it then names `tasks.push_url` and `tasks.push_secret` (16 to 256 characters, never echoed or logged) together, and its pushes (the results, and `session_failed`) are signed with that secret, so the client can check them; the server's `tool_secret` never signs a client's address, and a client's secret never signs the operator's. One without the other is dropped with `interaction_value_ignored`, and the operator's address stays; without the switch either gives `interaction_override_refused`. A session's own address is kept in its gateway process only: a task swept from a process that died (below) is not pushed there, since no other process holds its secret.

### Several Gateway Processes

Without `interaction.task_redis_url` each gateway process keeps its own tasks: a caller who comes back must reach the same process, and `GET /v1/tasks` shows the tasks of the process that answers. With it, the processes share one Redis:

- **Listing** - `GET /v1/tasks` and `GET /v1/tasks/{task_id}` read the Redis, so any process answers for a task that another one runs, and `GET /v1/tasks/events` on any process streams the task events of every process's sessions (Redis pub/sub; an event published while a process was cut off from the Redis does not reach the others).
- **Coming back** - a caller who comes back on another process gets the outcome there: the process that ran the task publishes it and the one with the new session receives it.
- **A process that dies** - each process renews a lease every 10 seconds. One whose lease is 30 seconds old is suspected; when it has still not renewed it 15 seconds later (the next two renewals of the others), it is dead, and another process then ends the tasks it left running: a task that could change something (`side_effects`) becomes `unknown` with `effects: "unknown"`, because a call may have been on the wire, and its `summary` names what it had committed before; any other task becomes `failed` with its effects as they were. The outcome then goes to the caller who is back, or to the push address, as above.
- **A process that was only cut off** - a process that reaches the Redis again after its lease ran out writes its running tasks there again at once, which ends the suspicion; if it was swept meanwhile, the tasks read as running again (an outcome already delivered or pushed is not taken back).
- **Callbacks** - a webhook's callback, an A2A agent's push or the operator's answer to a person hand-off (`human_<hex>`, see [A Person on the Webhook](#a-person-on-the-webhook)) may reach any process (a load balancer in front of them). One that reaches a process with no run of that task is handed, as it came, to the process whose record of the task (or of the hand-off, kept while it waits plus 60 s) names it, while that process holds its lease: the route answers `202`, and the owner checks the signature or the token as its own (no secret is kept in the Redis; a push's token goes on the channel only as its SHA-256, which the owner compares with its own token's; a refused one is logged there, `interaction callback from another gateway process refused`). One with no proof at all (neither `X-A2A-Notification-Token` nor both `X-WaaV-Timestamp` and `X-WaaV-Signature`) is answered `401` before the Redis is asked. No live record, or an owner that is gone: `404`. The Redis did not answer or did not take it: `503` with `Retry-After: 2`.
- **What is stored** - each task as `GET /v1/tasks` shows it, its result, and the operator's push address. A running task is kept for a day at most, a finished one for ten minutes. A Redis that cannot be reached at startup leaves the tasks in the process, with a warning in the log; a write that fails later is logged and dropped.
- **A Redis that does not keep up** - the writes wait in the process in order, at most 4,096: past that the oldest task event is dropped (metric `waav_degraded_total{component="interaction",reason="task_event_dropped"}`), and with no event among them the oldest write (`task_redis_write_dropped`, and a warning in the log).

## Listing Tasks

`GET /v1/tasks` lists the tasks of the caller's sessions: the live ones, and finished ones for ten minutes. The optional query parameter `stream_id` limits the list to one session. A request without an authenticated id gets only the session it names, and an empty list without `stream_id`.

```json
{
  "tasks": [{
    "id": "task_5b1e9c0d", "task_ref": "t1", "revision": 1, "title": "your table booking",
    "state": "working", "cancelling": false, "effects": "none_committed",
    "open_question": null, "side_effects": true, "started_at": 4180,
    "parent_id": null, "agent": null, "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
  }]
}
```

A follow-up (see [Follow-ups](#follow-ups)) also has `follows`: the `task_id` of the finished task it continues; every task event carries it too.

`GET /v1/tasks/events` streams the caller's task events as server-sent events from the moment of the request, by the same rule: `task_created`, `task_progress`, `task_question`, `task_answer_received`, `task_output`, `task_result` and `task_cancelled`, each as an event named after its `type` whose data is the event as the session's client got it with the session's `stream_id`. Optional filters: `stream_id`, `task_id`, `parent_id` (a request's children). Tasks that run on after their call are included. A reader that falls behind gets a `lagged` event with the number it missed. Without a task Redis the stream carries the tasks of the process that answers; with one (see [Several Gateway Processes](#several-gateway-processes)) it carries those of every process of the deployment: each process publishes its sessions' task events on the Redis channel `waav:ix:task-events` and passes the other processes' on to its own readers, each event once. A process publishes them only while another process has a reader: a process names itself on `waav:ix:task-readers` when its first reader comes and every 10 seconds while it has one, and the others publish for 30 seconds after they last heard it. A process that starts after a reader came elsewhere publishes from that reader's next renewal on (at most 10 seconds later).

```text
event: task_output
data: {"type":"task_output","task_id":"task_9f2c","task_ref":"t2","revision":1,"state":"completed","text":"Booked AI 101 on Friday at 9:40.","data":{"flight":"AI 101"},"artifacts":[{"url":"https://air.example.com/t/AI101"}],"effects":"none_committed","t_ms":21400,"parent_id":"task_5b1e","agent":"browser","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","stream_id":"call-1042"}
```

`GET /v1/tasks/{task_id}` returns one task in the same shape, with the `stream_id` of its session and its `result`: `null` while it runs, then its `state`, its `summary` (the answer of a completed task, otherwise what went wrong) and its `effects`. The same rule decides who may read it: a request without an authenticated id must name the task's session with `stream_id`. A task the caller may not read is answered with 404, like one that does not exist.

```json
{
  "id": "task_5b1e9c0d", "task_ref": "t1", "revision": 1, "title": "your table booking",
  "state": "completed", "cancelling": false, "effects": ["booked a table for 2"],
  "open_question": null, "side_effects": true, "started_at": 4180, "stream_id": "call-1042",
  "result": { "state": "completed", "summary": "Your table for two is booked for seven.", "effects": ["booked a table for 2"] }
}
```

## Language Packs

The words of the mode (the phrase banks, the templates such as the confirmation's read-back, the sensitive categories, the lexicon rows the front model is shown as examples of the caller's words, and the function words a copy span writes in lower case) form a pack. English is built in. The operator adds a language as data, without a new build: three files in the directory of `interaction.packs_dir`, named after the language's code.

```
packs/
  guard_lexicon.hi.json
  phrase_banks.hi.json
  templates.hi.json
```

The files have the shape of the English ones (`docs/duplex-agent/front-model/*.en.json`). A pack is loaded only when all three parse, every bank group and every template this build speaks is there, the patterns are regular expressions, and every line passes the same check as the English lines (no claim that something was done, no promised time, no prompt label). A pack that fails is left out with a line in the log saying why.

- **Which sessions** - a session whose `stt_config.language` has the pack's code as its primary subtag (`hi`, `hi-IN`) runs the mode on that pack: its persona's lines, templates and rules are the pack's. The persona is the pack's default one; a persona of the session's tenant is compiled against the pack of its own `language`.
- **The front** - the front model's instructions stay in English; on another pack its prompt names the pack's language ("Speak Hindi only", "The caller speaks Hindi; read their words in Hindi") and shows up to four words of each of the pack's lexicon rows (stop, repeat, cancel, status, amendment, request, continuer and side-talk cues) as examples of their acts. The lists are examples, never a match that decides (chapter 9), so the front model must read the language: use a multilingual one. A pack with one of those rows empty is refused interaction mode (`interaction_refused`, reason `front_unavailable`, naming the row). The narrator writes a task's update, and its answer from a stored result, in the pack's language.
- **Another language** - the recogniser's language field must start with the pack's code; the words' language is the front model's reading (`wait` `foreign`, see [Another Language](#another-language)), not a word list.
- **Listening sounds** - the `backchannel` group's lines are the words, `fallback` names the clip that replaces one failing its checks, and `timing` holds the language's numbers (see [Listening Sounds](#listening-sounds)). A pack whose fallback is not a clip of the group, or whose timing passes over every pause or has no gap, is left out.
- **When services fail** - the `failure` group needs a line of each kind (`stall`, `hearing`, `exit`, `exit_follow_up`, `back`), each with its id in `clip` (see [When Services Fail](#when-services-fail)). A pack made before this group existed is left out until it has one.
- **Matching in any script** - phrases match as whole words after lower-casing; letters and digits of every script count and accents are kept (`réservé` is not `réserve`). In a script written without spaces (Chinese, Japanese, Thai, Lao, Khmer, Myanmar, Tibetan) each letter is a word, so a phrase matches as a run of characters; the rules that count words (a short answer is at most three words, a request needs content words of three letters or more) then count characters, and a repeated request is not recognised in such a script. A phrase with no letter or digit in it matches nothing.
- **What stays English** - the checks of a background's answer (links, long numbers, prompt labels, requests for a secret in its own words) and the regime B and C sessions.

No pack other than English ships: a Hindi pack waits for review by native speakers. The live test (LP1) writes a small Spanish pack of its own into its run's log folder and loads it from there: machine-written and unreviewed, it is test data and never part of the gateway's packs.

## Deepgram

What the gateway does with Deepgram, with interaction mode on or off.

- **Flux** - `stt_config.model` `flux-general-en` streams on `/v2/listen`, Deepgram's speech-to-text with its own turn model. Each turn arrives as interim `stt_result`s of the whole turn so far and one final that is also speech-final (Flux `EndOfTurn`). Flux takes no language (English only) and none of the `/v1` features; `stt_config.extras` may set its `eot_threshold`, `eager_eot_threshold` and `eot_timeout_ms`. In interaction mode Flux's `EagerEndOfTurn` is the eager end of turn (`duplex.eager`; Smart Turn then guesses none) and its `TurnResumed` withdraws it; when the gateway ends a turn early (the silence ceiling, `audio_end`) it sends Flux `ForceEndTurn`. Eager mode stays off until it is measured: Flux sends `EagerEndOfTurn` only when `eager_eot_threshold` is set. Flux refuses `KeepAlive`, so the socket stays open on the session's continuous audio.
- **Language codes** - each model gets a code it takes, from Deepgram's model list less the codes its streaming endpoint refuses (`nb`, nova-3's `vi-VN`, nova-2's `ms-MY`): the caller's own code when the model lists it (`fr` on nova-3 is sent as `fr`, `hi-Latn` on nova-general as `hi-Latn`), else the region code when listed (`fr-FR`), else the language subtag (`vi-VN` on nova-3 is sent as `vi`). Norwegian is `no` (`nb` and `nb-NO` are sent as `no`). A model the list does not know gets the region code, as before.
- **File-only models** - Deepgram's `whisper-*` models transcribe files only (`POST /transcribe/batch`). A `/ws` audio session with one gets an `error` that says so and names what to use instead; it is not dialled (Deepgram refused the stream with 405). A session that asked for interaction mode first gets `interaction_surface_unavailable` with `reason: stt_file_only`.
- **Detected language** - with `language: "multi"`, nova-3 names the language it heard, and so does `flux-general-multi` (its turn's `languages`); `stt_result` carries it as `detected_language` (also the language interaction mode checks a turn against).
- **End of turn** - in interaction mode, when the gateway's own turn logic ends a turn whose words are still interim (Smart Turn is sure and the session's `endpointing_ms` has passed, or the silence ceiling), it sends Deepgram `Finalize`; Deepgram's answer is the segment's final (Deepgram's own endpointing held some English sentences 4-5 s). An empty answer (the final had come already) is not passed on, and a late final that repeats the words of a turn already ended is not a second turn.
- **Voice Agent** (`/realtime` provider `deepgram`) - the `config` chooses the agent's parts: `model` is the think model and `think_provider` its vendor (`open_ai`, `anthropic`, `google`, `groq`, `nvidia`; when unset it is taken from the name: `claude-*` Anthropic, `gemini-*` Google, `openai/gpt-oss-*` Groq, `nvidia/*` NVIDIA, any other OpenAI); `transcription_model` the listen model (nova-3 by default; `flux-general-en`); `language` the agent's language (its language subtag; `auto` is `multi`); `voice` the speak voice (an Aura voice); `region` `us` (default) or `eu` (`api.eu.deepgram.com`; a server endpoint override wins, any other value fails the session). A function call's answer names its function, as Deepgram requires. The session's functions are sent with the `deepgram_tools` fix (see [Provider Fixes](#provider-fixes)) and always in interaction mode. A Flux listen model gets no `agent.language` (Deepgram refuses it with `INVALID_SETTINGS`). A Deepgram `Warning` reaches the client as `warning` with `code: provider_warning` and `detail.provider_code` (Deepgram's code), not as an `error`. When the agent ignores an injected line because it is in a reply of its own (`INJECT_AGENT_MESSAGE_DURING_AGENT_SPEECH`), the line goes out again once that reply ended: the client's typed `text` with the mode off, the gateway's own line in interaction mode. Settings Deepgram refuses (`INVALID_SETTINGS`) end the session with Deepgram's reason (an `error`, then `connection_lost` naming it) instead of a reconnect.
- **Circuit breakers** - a speech-to-speech session has a breaker of its own per vendor and model (`deepgram-realtime/<think model>`; at most 256 model breakers, then a new model shares `deepgram-realtime`), so a think model Deepgram keeps refusing never stops its other models nor the vendor's speech-to-text and text-to-speech sessions. A configuration the vendor refused (Deepgram's `INVALID_SETTINGS`, a close whose reason names a 4xx status other than 401/403/407/429, such as ElevenLabs' unknown agent) never counts against a breaker: it is the client's to fix.
- **Latency** - the gateway's speech-to-text, text-to-speech and speech-to-speech WebSockets send without Nagle's delay (`TCP_NODELAY`): the text-to-speech `Flush` that follows `Speak` used to wait for Deepgram's delayed acknowledgement, +340 ms first audio.

## ElevenLabs, Cartesia and `POST /speak`

These hold with interaction mode on or off.

- **`POST /speak`** streams the audio as it is synthesised (chunked, no `Content-Length`); a request with `audio_format: "wav"` is answered whole, with `Content-Length`, as before. Its `tts_config` takes `features` and `extras` as a `/ws` session's does (before they were ignored): a provider with a `features` mapping gets them (ElevenLabs' `streaming`, `seed`, voice settings; Deepgram's `streaming` is its WebSocket voice). An error before the first audio is answered with its status as before; one after it ends the response early.
- **Streaming TTS fallback** - `tts_config.features.streaming: true` on a provider with no streaming variant in the gateway (every provider but Deepgram and ElevenLabs) is synthesised over HTTP as before, and the session now gets `config_warning` `tts_streaming_unsupported_or_degraded` (`detail.feature: "streaming"`).
- **ElevenLabs streaming** - with `tts_config.features.streaming: true` in a `/ws` session's config or a `POST /speak` request (with interaction mode on or off) ElevenLabs synthesises on its HTTP streaming endpoint, `/v1/text-to-speech/{voice_id}/stream`, with the same query and body as the convert endpoint: the audio comes as it is made instead of when the whole line is done, and no `tts_streaming_unsupported_or_degraded` is sent. `ELEVENLABS_TTS_URL` in the server's environment (never a session's) sends the requests to a proxy or a stand-in instead of `https://api.elevenlabs.io/v1/text-to-speech`. Live (2026-10-19, `eleven_flash_v2_5`, one line of 47 characters): the first audio reached the client 443 ms after `speak`.
- **Rate limits** - a vendor's 429 reaches the client as `Rate limited: <the vendor's message>`, with `(retry after N s)` only when the vendor sent `Retry-After`. `POST /speak` answers it as 429 (with `Retry-After` when the vendor gave one), a voice or request the vendor refused as 400, a key it refused as 401 or 403, a vendor 5xx as 502, always with the vendor's message (all of these were 500).
- **Account concurrency** - `WAAV_TTS_ACCOUNT_CONCURRENCY` (server environment, e.g. `cartesia=2,elevenlabs=5`) is the most synthesis requests a vendor account takes at once, across every session and route of the replica: a request over it waits its turn (at most its request timeout, else 30 s, then 503 with `Retry-After: 1`) instead of drawing the vendor's 429. Unset vendors are not limited. A line cleared by a cut gives its place up at once: its request is dropped, not waited out. Cartesia's account here allows 2: a burst of six `POST /speak` was answered six times 200 with `cartesia=2`, and one in three got the 429 without it.
- **Refused handshakes** - a speech-to-text WebSocket the vendor refuses with a client error (`401`, `403` and other 4xx but 408 and 429: a bad key) is not redialled and does not count against the vendor's shared breaker; the session's `error` names the vendor's answer (Cartesia's was a "Connection timeout" after redialling for 10 s).
- **Vendor warnings** - a speech-to-speech vendor's warning (Deepgram `Warning`) is logged, not sent as an `error`, on `/v1/realtime` (the GA protocol has no warning event) and in a DAG realtime node (the node goes on); `/realtime` sends it as `warning` (above).
- **`GET /voices`** - a vendor whose list could not be read is named in the `x-voices-failed` header (`vendor: reason; ...`); when every configured vendor failed the answer is 502 with each vendor's reason (it was an empty 200).
- **ElevenLabs** - `POST /transcribe/batch` with an empty `api_key` uses the server's key (it answered "API key is required"); Scribe speech-to-text models get no "language ignored" warning (they take `language_code`), while the English-only `eleven_turbo_v2` / `eleven_flash_v2` now do. `/realtime` takes the aliases `11labs`, `elevenlabs-convai` and `elevenlabs_convai` (and `deepgram-agent`, `gemini-live`, `fixie`, `yandexgpt`). An agent ElevenLabs does not have ends the session with its reason (`Refused by the provider: Agent ... not found: 404`), with no reconnect and nothing counted against the breaker.
- **Cartesia** - the speech-to-text key travels in the `X-API-Key` handshake header, never in the URL; a short-lived `access_token` (extras) still rides in the query, as Cartesia documents.

**Per session** - a `/realtime` `config` may switch the fixes for its own session with `provider_fixes`, a fix name to `true` or `false`:

## The Front Model's Server

With `interaction.front_model.command` the gateway runs the front model's `llama-server` itself. Without it the operator runs the server and the gateway only uses `front_model.url`.

```yaml
interaction:
  enabled: true
  front_model:
    url: "http://127.0.0.1:18741"
    command: ["/opt/llama/llama-server", "-m", "/models/Qwen3.5-2B-Q4_K_M.gguf",
              "--host", "127.0.0.1", "--port", "18741", "-np", "2", "-c", "8192", "--no-webui"]
```

**Two slots or more.** At each session's warm-up the gateway reads the server's slot count (`GET /props`, `total_slots`). With two or more (`-np 2`; give each slot room for the system prompt, about 3,000 tokens, so `-c 8192` for two) each live session holds a lane, the lowest free one: lane `k` sends the front's decisions about the caller's words over the agent, its readings of a reply or a repeated request and its narrator's lines to slot `2k + 1`, and its turns' decisions and warm-up to slot `2k` (both modulo the slot count, `id_slot`), so the sessions spread over every slot and, with two slots per session, each keeps its interims' slot to itself (on two slots every session uses slots 0 and 1, as one session does). The decisions' slot is warmed at the session's start, and the interims' slot after it only while the caller is quiet and no turn has been decided yet: a warm-up read beside the first turn's decision shares the server's batches with it (live, 20 October: on the loaded GPU the interims' slot's 3,250 tokens, read in 1.6 s beside the first decision, took it past its 1.5 s budget, and the caller's first request got "Sorry, I didn't catch that."). Otherwise the next agent line primes that slot; a turn's decision also drops a warm-up still under way (the server may finish reading it). The prompt of such a decision (all but the words) is put into slot 1's cache at the start of each agent line, while the agent speaks: the caller's first words over it are read with only themselves and what follows them left to process, and a turn's decision never evicts that prompt. A reading or a narration has a short prompt of its own: on the decisions' slot it waited until the turn's line was generated and then evicted the persona's prompt from that slot's cache (live D2, 20 October: the repeat reading launched 1.2 s after it was asked and missed its 1.5 s budget in 3 of 6 runs; on the interims' slot it answered in 254 to 642 ms in 3 of 3), so it goes to the interims' slot, whose prompt is primed again at the next agent line. An agent line that starts while a reading or a narration is still out is primed once they are back: primed first, the whole prompt was read again ahead of them (their short prompt had taken the slot's cache), and the front's answer to a follow-up question from a stored result missed its 1.5 s budget every time that happened in the runs of 20 October (MA3: 4 of 4; the question then became a task). With one slot the priming waits for the caller's first sound over the agent (it would delay the turn's decisions), as before. **Client-rendered interims** (r5, 21 October): with two slots or more, the priming asks the server to render the interim's prompt with its own chat template (`POST /apply-template`, the caller's words replaced by a mark), cuts it where the words go, has the head tokenised (`POST /tokenize`) and puts the head and four tokens more into the interims' slot on `POST /completion` (the server keeps a state checkpoint four tokens before a prompt's end, so it keeps one exactly where the words go). An interim whose prompt is the primed one (same agent lines, same clock, same tasks) is then sent to `/completion` as the head's tokens followed by its words and the rest as text: the server renders, tokenises and parses nothing of the 3,400-token prompt and reads only the words and what follows them. Any other interim (a new line began, a reading or a narration took the slot's cache, a server without those endpoints) goes to the chat endpoint as before. While a spoken question is open, the agent's lines prime its answer's reading instead (the agent's question and the labels, the caller's words left out), and the reading of the caller's answer is sent the same way (live MA2: the reading took 290 to 357 ms of the agent's 5 s on the chat endpoint). Measured on the shared GB10 (Qwen3.5-2B, one server, the captured S1 prompts, same tokens either way): the act 57 to 131 ms after the request (median 72 to 77) client-rendered, 83 to 269 ms (median 124 to 195) on the chat endpoint, which also kept two state checkpoints of 19 MB per request. A second llama-server only for the interims was measured too and dropped: on the chat endpoint it named its act in 81 to 328 ms (median 139 to 225) against 90 to 305 ms (median 189 to 211) on the shared server's second slot, and 106 to 371 ms against 164 to 1,647 ms with a decision running on the other server or slot. **A dropped interim may run on** (r6, 21 October): over-speech decisions are streamed, and the gateway drops one as soon as newer words make it moot; llama-server stops it when it sees the connection gone, but when the newer request reaches the slot first the dropped one can run to its end and the newer one waits behind it (live S1: "stop talking" had no first byte in 474 ms behind the dropped "zop talk", 316 ms after the drop; on an own server 3 of 12 and 1 of 3 such pairs waited over 300 ms). Sending the newer interim to the lane's decisions' slot instead was built and measured, and not kept: on an own server it removed that tail at the median's cost, but live the turn's decision that follows needs that slot, and in the same hour 4 of its 8 "Stop talking." cues (four runs) were cut more than 800 ms after their words, 1 of 6 with the earlier build (three runs). A lane's narrations take turns on its slot, each with its own budget from its turn: two updates narrated together waited on the server one behind the other and the second ran out of its budget there (live MA1, 4 of the 8 empty narrations of the r5-verify runs). **Not built, measured 24 October (r12):** a newer interim right after one dropped at its act waits on the same slot while llama-server releases the dropped request. On an own 2B server with three slots (decisions, two primed interim slots; S1's captured prompts, 15 rounds each) the newer "stop talking" had its first token after: a free primed slot 63 ms (median; p90 97) alone and 203 ms (p90 283) beside a generating gpt-oss-20b; the same slot after the drop (today) 168 (275) alone and 391 (550, max 897) beside it; the other primed slot, alternating, 86 (131) alone and 366 (423, max 427) beside it; the same slot with `n_predict` 8 and no drop (the dropped one ends itself; the stop's kind came within 8 tokens 15 of 15) 301 (563) and 817 (1,249). A short `n_predict` is slower; alternation halves the wait alone but takes 25 ms off the median on the loaded GPU (its gain is the tail), and needs a third slot per session. Live S1 A/B on 24 October (a build that alternated on a three-slot front, against today's two slots; three runs each, five cues a run): the stop cues' interims waited 18 to 88 ms for the server (one 156, one 214) with it against 185 to 780 ms in 9 of 13 without (13 to 78 ms in the others), but the server took longer per request (to 735 ms) and the cut after the cue's words was no better: Parakeet median 166 ms (4 of 14 within 100 ms, max 413) against 126 (2 of 15, max 1,289), Whisper 250 (3 of 14, max 1,001) against 213 (4 of 13, max 1,153); S1 failed all twelve runs either way. Neither is in the gateway.

- **Start** - when the server starts, with the program and arguments as given and an environment of `PATH`, `LD_LIBRARY_PATH`, `CUDA_VISIBLE_DEVICES` and `HOME` only (no `LLAMA_ARG_*`). Its output is discarded. On Linux it is stopped by the system if the gateway dies.
- **On a private socket** - with `front_model.url: "unix:"` (env `WAAV_INTERACTION_FRONT_URL=unix:`) the server listens on a UNIX socket, not on loopback: at start the gateway makes a run directory for this boot, `$WAAV_RUN_DIR/front-<boot>/` (default `<temp dir>/waav-run`; mode 0700) with a fresh key file `front.key` (0600), adds `--host <dir>/front.sock --api-key-file <dir>/front.key` to the command (a socket path has at most 107 bytes: a longer `WAAV_RUN_DIR` is refused at start and the log says so), and sends every request of the front over that socket with that key (nothing else: no `api_key`, no environment). It writes its own pid in `front.pid` when it makes the directory (`0 <gateway pid>`), and the child's pid before its own once the child runs.
- **Earlier gateways' children** - before it starts the server, the gateway looks through `$WAAV_RUN_DIR/front-*`: where the gateway named in `front.pid` is gone and the child still runs the command's program (`/proc/<pid>/cmdline`), the child gets `SIGTERM`, then `SIGKILL` after 2 seconds, and the directory is removed (also one whose child is gone). A directory of a gateway that still runs is left alone.
- **Ready** - when `<url>/health` (or the socket's) answers 200 and one whole decision has come back (the canary: the default persona's prompt, the act grammar, the stream and its parse, at most 20 s; the log's `front model ready` has its `canary_ms`), polled every 250 ms for up to 120 seconds, then every 5 seconds; a canary that fails is tried again at the next check. Until then interaction mode is refused at session start; a session that lost the model lists `front_unavailable` in `degraded`, decides nothing new (the acoustic duck still lowers the agent's voice when the caller speaks), takes the model up again once it is ready, and ends interaction mode (`config_warning` `interaction_ended`, as a plain conversation where it has one) when it is not back within 150 seconds (the longest backoff and the longest load of one restart).
- **Restart** - when it exits, fails three health checks in a row, or is not ready in 120 seconds: after 0.5, 1, 2, 4 ... up to 30 seconds (back to 0.5 once it was ready). After more than 10 restarts in 10 minutes it is left stopped and interaction mode is refused or ends until the gateway restarts.
- **Stop** - after the sessions have ended at shutdown: `SIGTERM`, then `SIGKILL` after 2 seconds.
- **Licence** - a model file whose name contains `lfm` (Liquid's LFM models) is started only with `front_model.licence` set to `lfm_open_eligible` or `liquid_commercial` and a `LICENSE` file in the same directory; otherwise it is not started and the log says why. An operator-run server is checked too: when its `GET /props` names a model (`model_path`, `model_alias`) whose file name contains `lfm` and the licence is not stated, it is not the front (interaction mode is refused, `front_unavailable`, and the log says `interaction front model server refused`).
- **No fallback** - a server that cannot start on the GPU is not restarted on the CPU (product owner, 2026-10-16: no fallbacks for the front).

## Limits

- **English unless a pack is added** - the built-in phrase banks, templates and word lists are English. A session in a language with no pack (see [Language Packs](#language-packs)) runs without the mode, and a caller who switches language is stepped down (see [Another Language](#another-language)).
- **`/ws` and voice agents on `/v1/realtime`** - voice-agent sessions that answer in text only or take manual turns are refused with `interaction_surface_unavailable`, and a DAG that produces audio with `interaction_dag_audio_output`. A `/realtime` or relay session runs the mode only as [Speech-to-Speech Providers](#speech-to-speech-providers) says.
- **A voice agent on a file-only recogniser** - since release 1.0.0 a voice agent with automatic turn detection on a speech-to-text model that transcribes uploaded files (for example a local Whisper) is refused with `stt_live_unsupported`, interaction mode or not, although the mode ends and flushes each turn itself. Serve it with segmented speech-to-text or a streaming model; an operator who keeps the buffering path sets `WAAV_STT_FILE_ONLY_REFUSAL=off`, and the session then gets the `stt_buffered_until_commit` warning before `ready`.
- **No confirmation on a voice-agent or DAG session** - `task_question` (`bud.task.question`) comes only from the gateway's own tools, which such a session does not have. A Bud agent's run that needs a person's approval still fails with the approval notice: approvals by voice, an agent's per-tool `confirmation_templates` and background runs of an agent need work in the agent platform that is not there yet (the agent runs its tools without stopping for the gateway).
- **Operator backends** - a webhook's callback or an A2A agent's push that reaches another gateway process is handed to the one that runs the task only through a task Redis (see [Several Gateway Processes](#several-gateway-processes)); without one it must reach the process that runs it (another one answers `404`). An MCP server must speak the 2026-07-28 revision over HTTP. When the session ends, a task on a backend with `side_effects: none` is stopped and the backend is told. One on a backend with `side_effects: possible` goes on like a task whose tool call is on the wire (see [Tasks After the Call](#tasks-after-the-call)): the backend has 30 seconds to report and then 30 more to finish, and is told to stop after that.
- **Tasks live in memory** - nothing is stored on disk; with `interaction.task_redis_url` the tasks are also in that Redis. A session's tasks end with it, except one whose tool call is on the wire (see [Tasks After the Call](#tasks-after-the-call)). The gateway sets no limit on how many tasks run or wait: an operator who needs one sets `tasks.limits` and the entries' `max_concurrent` (a voice-agent or DAG session runs 1 task at a time). The tenant limit counts the sessions of one gateway process. A session keeps its live tasks and its last 32 ended requests (with their children); an older ended one leaves its board and can no longer be followed up (`GET /v1/tasks` still lists it for its ten minutes).
- **Coming back is for a connection the gateway saw end** - a client that loses its network and reconnects before the gateway has noticed starts a second session next to the first, which still runs. A lookup that was running when the connection was lost is cancelled, not continued. On `/v1/realtime` a session's end is always a clean one.
- **A restart loses what only the process knew** - without a task Redis a deploy drops the tasks and results of the process. With one, the tasks a stopped process left running are ended as described, not continued by another process.
- **Echo and the speech-to-text** - the gate works on the audio the gateway analyses; only the canceller also cleans what the speech-to-text hears. Without the canceller the speech-to-text still hears the echo, so a caller's words said in one breath with the agent's echo can be dropped with it. The gate cannot tell a caller less than 3 dB louder than the echo from the echo. An echo that returns later than `duplex.echo.max_bulk_delay_ms` (1 second) after its playout time is not found.
- **A session's first seconds** - each session loads its voice activity and Smart Turn models when it starts (0.3 to 1 second, up to 4.5 seconds for the first session of a gateway on a loaded machine). `ready` waits until they are loaded, at most 2 seconds (also on a room's realtime voice with manual turns); a session whose models take longer is ready all the same, and the caller's audio from that time is kept and worked through once they are loaded, so a caller who speaks at once is heard, a little late; the silence before that speech is not reported (the speech-to-text already holds the audio that follows it).
- **A room's first seconds** - the noise filter of a LiveKit session starts its workers with the first audio frame. Until they run, the caller's audio reaches the speech-to-text late (about 10 seconds in a debug build); the turn-taking hears it on time.
- **The model front is required** - every caller turn is the front model's to decide. A decision that does not come in `front.total_budget_ms` is not guessed: the caller is asked to say it again. After three misses in a row, or when the model server is not reachable, `interaction_updated` lists `front_unavailable` in `degraded` and nothing new is decided until it is back; the mode ends if it is not back within 150 seconds. When the gateway runs the server itself (`front_model.command`), the session takes the model up again once the server was restarted and is ready, and an `interaction_updated` without `front_unavailable` says so.
- **A stop waits for the front model** - the agent's voice is ducked at the caller's first sound (10 dB down within 0.1 to 0.35 s live), but it is cut only when the front has read the words. At that first sound the gateway already puts the decision's prompt (all but the words) into the front server's cache, and an interim's words are sent as a message of their own, so the front reads only them; once the front names an act that is not a wait, the rest of its line is not read and the server stops generating, so the turn's own decision does not wait behind it. Live on a shared GB10 with Qwen3.5-2B and a local streaming recogniser (interim results every 350 ms), the front named its act 79 to 349 ms after an interim was asked, and the agent was cut 443 to 1,169 ms after the first voiced frame of "Stop talking." or "Wait a second." ## Live End-to-End Test

`tests/live_testing/scripts/interaction_live_e2e.py` streams recorded caller speech to `/ws` in real time and checks events and audio against thresholds. It exits non-zero when one fails. It needs `websockets` and `numpy`.

```bash
cd gateway/tests/live_testing/scripts

# Request-response recogniser (the default, --stt request)
python3 interaction_live_e2e.py --start-stack

# Streaming recogniser with interim results
python3 interaction_live_e2e.py --start-stack --stt streaming

# Selected scenarios only
python3 interaction_live_e2e.py --only L0,L2
```

It expects these local services:

- **The debug gateway** on port 3401 (`--gateway-port`), built with `cargo build --features dag-routing,turn-ensemble,noise-filter,openapi` and run with `WAAV_INTERACTION_ENABLED=1`, `WAAV_INTERACTION_ALLOW_CLIENT_TOOLS=1`, `WAAV_INTERACTION_FRONT_URL`, `WAAV_INTERACTION_TOOL_SECRET` (equal to `--tool-secret`) and debug logging for `waav_gateway::core::interaction`.

### Against Deepgram

`tests/live_testing/scripts/deepgram_matrix.py` runs the same checks against a gateway that holds a real Deepgram key (`DEEPGRAM_API_KEY` in the gateway's environment; the script reads it from its own only for its direct calls to Deepgram). Read its header for the parts. Every item is priced before it runs and charged to a spend ledger shared across runs; `--budget-usd` stops a part before the ledger would pass it, and `--estimate-only` prints the estimate without running anything.

python3 deepgram_matrix.py --base-url http://127.0.0.1:3412 --data <matrix dir> --results <dir> --parts E

python3 deepgram_matrix.py ... --parts B --pairs enhanced-general:fr,general:de --multi-languages de,es --file-models whisper-large --limit-file-pairs 1
# The codes Deepgram refused before (caller codes listed for the model), Flux multi's detected language; no batch pairs
