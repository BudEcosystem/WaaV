## Cross-provider audit — do the Deepgram/ElevenLabs bug classes recur elsewhere?

After the live Deepgram/ElevenLabs work, three reusable bug classes were audited across **all 32 STT + 37 TTS providers** (3 parallel read-only audits, each finding then verified against the real code + provider docs). Findings and fixes (#29 group):

**Class A — configured model/voice silently dropped (the ElevenLabs #26 pattern: a `from_base`/`from_standard` that `..Default::default()`s over the provider's real model/voice field).** Confirmed and FIXED on the live path:
- **AssemblyAI STT** — `from_base` chose `speech_model` from language only, ignoring `base.model`. Now honors an explicit model (falls back to language). 
- **Rev AI STT** — `from_base` dropped `config.model` → the `transcriber` (machine/machine_v2/human) was ignored. Now mapped.
- **LMNT TTS** — `from_base` hardcoded `model = "blizzard"`, ignoring `base.model`. Now honored.
- **IBM Watson STT** — `from_base` derived model from language only; an explicit model (e.g. `en-US_Telephony`) was overridden. Now honored verbatim via `IbmModel::Custom`.
- **Viettel STT** — `from_base` hardcoded `asr_model: None`. Now maps `config.model`.
- **AWS Polly TTS** and **IBM Watson TTS** — `from_standard` (the W1 keystone path) dropped `voice_id`/`model` → `voice`/`engine`; the live `new()` path was already correct, but the standardized path silently ignored them. Now mapped (via `from_str_or_default`, so unknown values degrade gracefully).
- **NOT changed (deliberate): Cartesia STT, Gladia STT** — single-model providers (`ink-whisper` / `solaria-1`). Because the *shared* `STTConfig` default model is Deepgram-specific (`"nova-3"`), forwarding an arbitrary `base.model` to a single-model provider would only risk an invalid-model rejection. Left with a comment to map it once they expose multiple models.
- Each fix is locked by a positive "honors explicit model" unit test + a language/default fallback test. In production the WS path yields `model=""` when unspecified (fix #25), so every provider correctly falls back to its own default; the `"nova-3"` leak only affects direct `STTConfig::default()` construction.

**Class B — unencoded dynamic values in URLs (the Deepgram #27 pattern).** Audited every raw query/path assembly across stt/tts/realtime. The only values that are genuinely *free text* (and thus can contain spaces) were Deepgram's keyterm/keywords/tag — already fixed (#27); the residual `redact` value there is now encoded too. Everywhere else, raw-concatenated query values are **constrained identifiers** — model ids (`saarika:v2.5`), locales (`en-US`), GUIDs, enum-derived names — which carry no spaces/delimiters (and whose `:` is valid in a query and must stay literal). Sarvam/Azure were briefly encoded then reverted for exactly this reason. All other providers use auto-encoding APIs (reqwest `.query`, `Url::query_pairs_mut`, multipart, JSON bodies) or gRPC. **No additional genuine instances.**

**Class C — TTS output format silently overridden (the ElevenLabs #23 pattern).** Audited all 37 TTS providers. **No other HIGH tier-403-style defect exists** — the commercial providers (Cartesia, Azure, Google, Polly, IBM, OpenAI, Hume, LMNT, PlayHT, Deepgram) all map to valid wire formats with safe defaults and honor explicit values. LOW-severity items documented (not fixed): Viettel/Zalo TTS label MP3 bytes as `"wav"` and ignore `audio_format` on the flat path; Gnani hardcodes `pcm16`; Tencent/Cereproc/Bhashini coerce the implicit `linear16` default to a WAV container.
