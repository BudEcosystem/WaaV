# WaaV SDK / API / Standardization Plan

> Governing design from the Phase-1 analysis workflow (w2b0reiy4): full code analysis of WaaV SDKs/API/features + live-probe against the running gateway (:3009) + Pipecat + cross-provider research. Live-proven findings.

## Current state
## CURRENT STATE (verified live + source)

THREE client surfaces only: WS `/ws` (cascade; one big JSON `config` envelope = stt_config/tts_config/livekit/dag_config/conversation_config), WS `/realtime` (S2S; DIFFERENT event vocab — transcript/session_created/response_done vs /ws ready/stt_result/tts_playback_complete), and a small REST set (verified registered routes: /speak, /voices, /voices/clone, /dag/{templates,validate}, /livekit/*, /recording/{id}, /sip/transfer, /realtime, /ws). Note the wire is FLAT: there is NO top-level turn_detection/noise/reasoning/recording — turn_detection nests in stt_config (config.rs:345), reasoning+latency_filler nest in conversation_config (config.rs:140-217), recording = livekit.enable_recording, noise reduction is LiveKit-ingress-only on /ws and a field only on /realtime.

STANDARDIZATION — bimodal maturity, all claims verified:
- MATURE: EMOTION. core/emotion/{types,mapper,mappers/{azure,elevenlabs,hume,fallback}}.rs — 40-variant canonical Emotion enum + 15 DeliveryStyle + EmotionIntensity, Mapper trait + per-provider registry + graceful-degrade warnings + 1:1 Python mirror. This is the proven template.
- REAL but partial: STT/TTS FEATURES. core/stt/standard.rs SttFeatures + ProviderExtras(open Map) + 34 from_standard impls; core/tts/standard.rs TtsFeatures + 73 from_standard impls. Carried across dispatch via create_stt_standard/create_tts_standard; degrades LOUDLY (warn+metric). But many providers fall back to flat base; only deepgram has TTS WS-streaming.
- MISSING entirely (verified by grep returning ZERO hits across the whole gateway): canonical LANGUAGE (config.rs:304 `pub language: String` passed verbatim — live-proved: gateway accepted `us-en` with no normalization, failed only at provider connect); model ALIAS/PROXY resolver; canonical VOICE descriptor; canonical AudioFormat enum; cascade-path tools/modalities (only RealtimeConfig has them); voice-cloning is REST-only and not session-inline; translation (doc-comment only); batched/async STT.

LIVE PROOF (python3 /tmp/waav_arch_probe.py → ws://127.0.0.1:3009/ws): sent config with language `us-en` + nested stt features{diarization,keyterms,redaction} + turn_detection + full conversation_config{reasoning_effort:minimal, reasoning_model:o3, latency_filler:auto, mute_strategy, barge_in_min_words} + a `bogus_top_level_key`. Gateway ACCEPTED all of it (the bogus key silently dropped — no deny_unknown_fields anywhere; verified grep) and only errored on a deepgram-TTS required `model` field. This proves: (a) the rich config surface is FULLY wired gateway-side, (b) language is never canonicalized, (c) unknown keys vanish silently. livez/readyz=200.

HEADLINE PROBLEM: the gateway is a deep, mostly-good server-side standardizer, but all 3 SDKs are a thin, partly-WRONG, years-stale subset (10 STT/12 TTS/2 S2S vs 27/32/12). The flagship conversation+reasoning loop is 0% SDK-reachable; advanced features are sent as flat keys that silently drop; TS transcripts come back EMPTY. The standardization promise ("client code never changes when switching models") is FALSE today because language/voice/format/model are raw per-provider strings.

## Standardization design
## WHERE IT LIVES: GATEWAY-SIDE mapper, mirrored (not reimplemented) in SDKs

Decision: every canonical→native mapping lives at the gateway dispatch boundary so ALL THREE SDKs + raw WS callers benefit automatically. SDKs carry only the canonical VALUE SPACE (enums/types) for typed DX and codegen, never the mapping logic. This is the lesson of the existing emotion system (the one axis done right) and the inverse of Pipecat (which duplicates per-service InputParams + LANGUAGE_MAP in every client).

## THE TEMPLATE: replicate the emotion architecture for the 5 unstandardized axes
core/emotion/ already proves the full pattern end-to-end: canonical enum → Mapper trait → per-provider registry → graceful no-op warning → SDK mirror. EXTEND this exact chassis; do NOT invent parallel systems. The additive SttFeatures/TtsFeatures + ProviderExtras escape-hatch is the second proven keystone — new canonical blocks ride alongside it with the SAME degrade-loudly contract (warn + waav_degraded_total).

1) LANGUAGE (highest leverage — unblocks the entire 'switch models without client edits' goal). New gateway/src/core/lang/: `CanonicalLanguage` = BCP-47 region-qualified (en-US, es-ES, hi-IN, cmn-CN for Mandarin), accepting bare ISO-639-1 (en) as shorthand. `resolve(&str)->CanonicalLanguage` absorbs EVERY alias spelling ONCE (us-en, eng, en_US, 'english', zh-CN↔cmn-CN, or-IN↔Sarvam od-IN, nb/no, yue/zh-HK) — port waav-infer components/standardize.rs resolve_alias/NotationMap. `to_provider_language(canonical, provider, model)->Result<String>` with per-provider override table for quirks (ElevenLabs ISO-639-1-only downgrade; iFlytek zh_cn underscore; Baidu numeric model 1537 + 'zh' lang split; Google cmn-CN; Sarvam od-IN; AWS EN_US enum) + a canonical `auto` token mapping to each provider's detection mechanism (Deepgram detect_language flag / AssemblyAI multilingual speech_model / Gemini native / OpenAI source-auto) or a warn-and-default. CALL IT at the config→provider boundary (replace the raw concat at deepgram.rs:460 etc.) so NO provider code ever sees a raw client string. On unsupported lang→provider, emit a config_warning (like MappedEmotion.warnings), never a hard 400. DELETE the ad-hoc per-provider alias matches (speechmatics en|english|en-us|en-gb, reverie, tencent).

2) EMOTION/STYLE (widen + backfill the mature base). Keep the 40-variant canonical model. Resolve the Emotion-vs-DeliveryStyle overlap (Cheerful/Serious/Soft live in both): Emotion=affective-state, DeliveryStyle=delivery-mechanism (whispering/shouting→DeliveryStyle). Widen superset with researched Azure-DragonHD + Cartesia styles (amazed, amused, intrigued, flirtatious; scenario styles newscast/customerservice/advertisement_upbeat/sports_commentary). FIX under-mapped providers: replace FallbackEmotionMapper::cartesia()/openai() with real mappers (Cartesia emotion-array name:level; OpenAI gpt-4o-mini-tts + gpt-realtime synthesize an `instructions` string from emotion+intensity+style+description). Add an `instruction_text` slot AND an `inline_tags/text_prefix` slot to MappedEmotion so the abstraction can carry (a) natural-language instructions for Hume/OpenAI/Nova-Sonic/Gemini-Live and (b) inline bracket tags for ElevenLabs v3 [excited] / Azure DragonHD — the current struct models only ssml_style/speed/voice-settings and cannot express text-injection. Unify the double-path: TtsFeatures.emotion(String) folds into structured EmotionConfig (one input, defined precedence). Route S2S emotion via session/system instruction (set supports_free_description appropriately in the support descriptor).

3) VOICE + VOICE-CLONING. Canonical `VoiceDescriptor {gender, accent/locale, style, age, name_hint}` resolved server-side to a provider voice_id (backed by the existing unified /voices catalog, voices.rs), with raw voice_id kept as an escape hatch — so 'female, American, warm, en' maps to aura-asteria-en / 21m00Tcm4TlvDq8ikWAM / en-US-JennyNeural with no client edit. NEW canonical VoiceClone block as a SEPARATE REST op (not a per-turn TTS feature): {samples, name(req), mode: instant|professional, description?, labels{language,accent,gender,age}?, base_voice_id?, remove_background_noise?, consent{verified,statement}?} → {voice_id, status: ready|verifying|training|queued, requires_verification?}. instant→ElevenLabs/Cartesia/PlayHT/LMNT/Speechify; professional→ElevenLabs-PVC/Resemble as an async poll/webhook job; expose Hume save-prior-generation as a distinct save_generation_as_voice op. Returned voice_id is directly usable as TTSConfig.voice_id, and SDKs add poll-until-ready.

4) TRANSLATION (new, reuses CanonicalLanguage). Three canonical shapes: (a) STT side-channel translation:{target_languages:[CanonicalLanguage], partials?} → emit translations[]{lang,text} (Speechmatics/Gladia/AssemblyAI); (b) translate_to_english:bool fast-path (Whisper /translations); (c) S2S dub:{source_lang?, target_languages, voice_id?}. Add a canonical translate DAG node so STT→translate→TTS language pairs are uniform.

5) AUDIO FORMAT. Single canonical AudioFormat {container, encoding, sample_rate, bit_rate} on the public STT/TTS/realtime config; derive the legacy encoding/audio_format/sample_rate from it (kills cache-key ambiguity, e.g. opus-in-ogg vs raw opus). Per-provider mapper to native (Cartesia output_format / OpenAI response_format / Deepgram encoding+sample_rate).

6) PARAMS/VALUES inside features. Make keyterms lossless: Vec<String> → [{phrase, boost?}] (Deepgram intensifier / Google boost / AssemblyAI boost_param). Redaction: freeform Vec<String> → canonical category enum {pii,phi,pci,numbers,names,locations,...} + substitution mode {mask,hash,tag}, expanded per provider. Lift tools:[ToolDefinition]+tool_choice+modalities onto cascade ConversationConfig (already on RealtimeConfig) so function-calling is uniform across both paths.

7) BATCHED/ASYNC STT (new). batch:{audio:url|bytes, callback_url?, callback_method?} that REUSES SttFeatures verbatim + batch-only knobs (paragraphs,utterances,summarize,topics,intents,chunking_strategy,logprobs,prompt) → job {job_id,status,result}. CRITICAL: the batch dispatcher must ENABLE the streaming-only-gap features (alternatives/detect_language/summarize) that streaming from_standard intentionally drops — they ARE batch-capable on Deepgram.

## ENFORCEMENT (prevent regression)
- Add `#[serde(deny_unknown_fields)]` to the gateway WS config structs (or a config_warning for unknown keys) so the flat-key bug fails LOUDLY, not silently. Keep serde lenient ONLY where forward-compat needs it, gated by an opt-in `validate` round-trip.
- Add a compile-time tripwire test per new block (mirror stt/standard.rs shared_research_semantics) so a future research pass that discovers a new shared semantic fails the build until the canonical field is added.
- Surface ProviderEmotionSupport + a new ProviderLanguageSupport (+ feature support matrix) via a /capabilities REST endpoint so degrade is OBSERVABLE, not silent, and SDKs stop hardcoding stale capability dicts.

MIGRATION: all additive + backward-compatible. Existing raw `language: String`, raw voice_id, raw encoding all keep working (resolve() treats an already-canonical/native value as identity). No client breaks; clients OPT INTO canonical values and gain provider-portability.

## SDK DX design
## ONE config shape per SDK = a 1:1 CODEGEN MIRROR of the gateway /ws config (stt_config/tts_config/livekit/dag_config/conversation_config), generated in CI from docs/openapi.yaml (utoipa ToSchema already derives on IncomingMessage/config structs). This structurally prevents 'feature exists server-side but unreachable from SDK' — the single highest-leverage SDK fix and the root cause of nearly every bug above. Mirror the canonical enums (language, emotion, voice, format) + a single `extras: dict` long-tail passthrough.

## BEGINNER SURFACE — minimal-lines helpers on top of the full config (beat Pipecat's ~95-line client wiring by keeping the DAG/loop server-side):

TTS (1 call):  `await bud.speak("Hello", tts={"provider":"deepgram","voice":"female-warm-en"})`
STT (3 lines): `async with bud.transcribe(stt={"provider":"deepgram"}) as s:  s.send(pcm);  async for r in s: print(r.transcript)`
TALK / AGENT (the flagship — reasoning+barge-in+filler in ~5 lines, IMPOSSIBLE today):
```
async with bud.agent(
    stt={"provider":"deepgram","language":"en-US"},
    tts={"provider":"elevenlabs","voice":"female-warm-en","emotion":"friendly"},
    llm={"model":"qwen2.5","base_url":"...","reasoning_effort":"minimal",
         "reasoning_model":"o3", "latency_filler":"auto"},
    turn={"eager_eot": True}, interrupt=True,
) as call:
    async for ev in call:  # transcript | bot_text | audio | warning events, one unified stream
        ...
```
The helper serializes conversation_config + nests turn_detection into stt_config + applies sane defaults (allow_interruption, strip_markdown, barge-in). A beginner gets the entire reasoning/barge-in/latency-filler stack for free.

REALTIME/S2S (gateway-native, provider-agnostic):
`async with bud.realtime(provider="openai", voice="alloy", instructions="...") as rt: ...` — speaks /realtime's protocol (config/create_response/commit_audio/clear_audio/function_result/update_session), wired into BudClient. Keep direct-to-provider BudRealtime only as an explicit escape hatch (or delete).

DAG (inline or template/alias):
`await bud.agent(dag="support-bot")` (alias/template) OR `dag={"definition": {...}}` (inline) — reuses the typed DAG helpers (already well-covered in Python types.py:1203+, currently dead in TS — wire them into configToWire).

## FEATURE EXPOSURE — flat SDK kwargs routed to their correct nested wire home (the SDK hides the asymmetry the gateway-api report flagged):
- reasoning → llm={reasoning_effort, reasoning_model, latency_filler, reasoning_route, reasoning_budget_ms} → conversation_config
- turn-detect → turn={eager_eot, threshold} → stt_config.turn_detection
- VAD/noise → noise=True / vad={...} → (currently LiveKit-ingress; see roadmap P4 to add a real /ws PCM noise field) — until then the SDK must NOT expose dead toggles; gate or omit.
- streaming → stt/tts features.streaming
- advanced STT/TTS → stt={"features": {...}} / tts={"features": {...}} (canonical SttFeatures/TtsFeatures vocabulary) + `extras` passthrough
- recording → record=True → livekit.enable_recording

## CAPABILITY NEGOTIATION + TYPED DEGRADATION (Pipecat has none):
- SDK asserts protocol_version=='1.0' on ready; warns/raises on mismatch (gateway already emits it).
- SDK parses gateway config_warning advisories (reasoning_model_on_voice_path, reasoning_effort_clamped, emotion_ignored_for_provider, language_unsupported) and surfaces them as typed warnings in the event stream → a beginner learns 'emotion=excited was ignored by Deepgram' instead of a silent no-op.
- Replace the stale hardcoded *_PROVIDER_CAPABILITIES dicts with a live `bud.capabilities(provider)` backed by the gateway /capabilities endpoint.

## HARDENING: typed RateLimitError + jittered backoff honoring 429/Retry-After on WS connect (every live test starved on this); native WS ping frames (drop JSON ping); real round-trip e2e through the SDK deserializer asserting non-empty transcript + real ready fields + barge-in via 'clear'; env-configurable WAAV_GATEWAY_URL (default :3009); fix health 'ok' assertion. tsc --noEmit as a CI gate.

## WIDGET: one-attribute beginner form — `<bud-widget data-llm-model="qwen2.5" data-llm-base-url="..." data-stt-provider="deepgram" data-tts-voice="female-warm-en">` drives the full conversation loop (today the widget cannot make the bot talk back at all). Move turn_detection into stt_config.turn_detection, stop sending realtime_config on /ws, fix port to 3009, AudioWorklet recorder, negotiate real TTS output rate.

## PHILOSOPHY (improve on Pipecat): keep WaaV's typed-canonical-superset + single `extras` escape-hatch (strictly better than Pipecat's per-service InputParams duplication + raw kwargs) — ONE config shape across all providers for the 80% standardized surface, full power-user access for the long tail, validated server-side. WaaV leapfrogs Pipecat which has NO canonical emotion/cloning/translation/alias at all.

## Proxy / alias model-name design
## DESIGN: server-side ALIAS REGISTRY (a named profile → resolved config), resolved at config time. This is the cleaner alternative to literal placeholder model strings, and a genuine differentiator (Pipecat hardcodes service classes and CANNOT do this).

WHY an alias registry, not a placeholder model string: a voice session is not just a model — it's {STT provider+model+language, TTS provider+voice+emotion, conversation/reasoning settings, OR a whole DAG}. A single fake model name can't carry that. An alias maps a logical name to the FULL resolved bundle and lets ops re-point it (swap providers, A/B, kill-switch, cost-tier) with ZERO client redeploy.

## SHAPE
A server-config (and optionally a REST-CRUD) registry:
```
[aliases.support-bot]
kind = "agent"                 # stt | tts | realtime | agent | dag
stt   = { provider="deepgram", model="nova-3", language="en-US" }
tts   = { provider="elevenlabs", voice="female-warm-en", emotion="friendly" }
llm   = { model="qwen2.5", reasoning_effort="minimal", reasoning_model="o3" }
# OR, instead of the above: dag_template = "voice-assistant"
```
Resolution: a single client field. Reuse the EXISTING `model` / provider string by prefixing (`provider="@support-bot"` or `model="@support-bot"`), OR add a dedicated top-level `alias: Option<String>` on the /ws + /realtime config (cleaner, no string-prefix overloading). On config, the gateway resolves the alias to a concrete config BEFORE provider construction; an explicit config always overrides/merges (alias = defaults).

## EXACT GATEWAY TOUCHPOINTS
1. New gateway/src/core/alias/ (mirror the DAGTemplateRegistry pattern — the same indirection primitive already exists for whole DAGs): `AliasRegistry { resolve(name)->ResolvedConfig }`, loaded from config.yaml at startup; optionally hot-reloadable.
2. handlers/ws/config_handler.rs — at config-message handling, BEFORE create_stt_standard/create_tts_standard/conversation wiring: if `config.alias` (or a `@`-prefixed provider/model) is present, look it up and splice the resolved stt_config/tts_config/conversation_config/dag_config in (client-provided fields win on conflict). This is the same place the existing dag_config.template already resolves.
3. Echo the resolved concrete config back in the ready/config-ack (so a developer can SEE what 'support-bot' became, and so SDK capability negotiation works against the resolved providers).
4. SECURITY: keep alias DEFINITIONS server-config-only (like the SSRF-guarded realtime_endpoint_override at core/net.rs/readiness.rs) so a client can NAME an alias but never INJECT a backend URL/credential. This is the key safety property: indirection without client-controlled endpoints.

## RELATIONSHIP TO EXISTING MACHINERY
This GENERALIZES two primitives WaaV already has — dag_config.template (named whole-DAG) and ProviderExtras.endpoint_override (host swap, SSRF-guarded) — into ONE 'alias' field that works at single-provider AND DAG AND agent granularity. It is lighter than forcing every client into DAG mode (the gateway-standardization + research-features reports both flagged that DAG-template-only indirection is too heavy for a simple model swap).

## SDK SURFACE
`bud.agent(alias="support-bot")` or `bud.speak(text, alias="news-voice")`. The alias does NOT replace the canonical layer — it composes with it: the alias resolves to provider+model, then the canonical language/emotion/voice mappers run against whatever it resolved to. So 'repoint support-bot from elevenlabs to cartesia' is a one-line server config change, and the client's `emotion="friendly"` / `language="en-US"` keep working because the canonical mappers handle the new provider's native vocabulary automatically.

### gateway-standardization
_WaaV has ONE genuinely-mature cross-provider standardization axis — EMOTION — implemented as a full canonical-enum → provider-native mapper system (22 emotions + 15 delivery styles + intensity), with a provider-keyed mapper registry, graceful-degradation warnings, and a 1:1 mirror in the Python SDK. Everything else is partially or not standardized. Voice CLONING is well-standardized (unified request/response across ElevenLabs/Hume/LMNT) but voice SELECTION is raw per-provider. - MODEL NAME: no canonical model-class aliases ('fast-stt','accurate-multilingual-tts'); only empty-string='provider default'. No alias/proxy resolution on the model field — only whole-DAG templates.

### pipecat
_Pipecat (github.com/pipecat-ai/pipecat) and WaaV sit at opposite ends. Pipecat is a CLIENT-SIDE Python pipeline framework: you compose typed Frames through Processors (transport→STT→LLM→TTS→aggregators) in ~95 lines, and provider differences are handled by per-service `InputParams(BaseModel)` + per-service `LANGUAGE_MAP`/`language_to_service_language()` over ONE canonical `Language` StrEnum (transcriptions/language.py). It STANDARDIZES language (single enum, ~hundreds of BCP-47 members) but does NOT standardize emotion/style/voice-cloning — those are raw per-service kwargs (ElevenLabs `style`/`stability`/`similarity_boost`; emotion via LLM-emitted inline tags). WaaV is the inverse: the gateway is a SERVER-SIDE standardizer with canonical `SttFeatures`/`TtsFeatures` structs + `ProviderExtras` escape hatch (gateway/src/core/{stt,tts}/standard.rs), a canonical 22-`Emotion`/15-`DeliveryStyle` system with per-provider mappers (core/emotion/), and 27+32+12 providers — a far richer SUPERSET than Pipecat. BUT three things are broken/missing that this design effort must fix: (1) NO canonical language resolver — language is a raw `String` at every boundary, normalized ad-hoc and inconsistently per provider (speechmatics matches `en|english|en-us|en-gb`, reverie matches `en|english|en-in|en-us|en-gb`, tencent matches `english|en|en-us`); the live gateway accepted bogus `us-en` with zero normalization and only failed at provider connect. (2) The SDKs are a thin, drifted subset of the gateway: the Python SDK's `_send_config()` (ws/session.py:409-493) sends only stt/tts/livekit/dag and SILENTLY DROPS `conversation_config` — so the flagship reasoning/eager-EoT/latency-filler/barge-in loop (ConversationWebSocketConfig, ~30 fields) is UNREACHABLE from the SDK; turn_detection/noise/VAD `audio_features` are marked "client-side" and never serialized to the wire. (3) README/types advertise surfaces that don't exist in code (bud.voice, bud.recordings, bud.sip, bud.sync). WaaV should keep its server-side standardization (it beats Pipecat), add a Pipecat-style canonical Language enum at the gateway boundary, make the SDK a faithful 1:1 of the gateway config (especially conversation/reasoning), and add a real PROXY/alias mechanism (none exists today)._
- No canonical language layer in the gateway: `language: String` everywhere; ~10+ providers each hardcode their own inconsistent alias lists (en/english/en-us/en-gb/en-in vary by provider). A user switching providers can get different behavior for the SAME language string. This is the single largest standardization hole and directly contradicts the stated goal.
- SDK cannot reach the gateway's flagship features: conversation_config (reasoning_effort, reasoning_model, eager_eot, latency_filler, allow_interruption, barge_in_min_words, reasoning_route/budget) is never serialized by the Python/TS SDKs. The headline 'reasoning-LLM optimization' is gateway-only, invisible to SDK users.
- SDK AudioFeatures (turn_detection/noise/VAD) are marked 'client-side' and dropped — the gateway expects turn_detection nested in stt_config and noise/reasoning inside conversation/stt configs; the SDK's standardized objects never map onto the actual wire schema.
- No proxy/placeholder/alias resolution exists in either SDK or gateway. `provider` is a literal string; there is no server-side table to remap an alias to a DAG/provider/model without client changes.
- Doc/code drift: Python README documents bud.voice, bud.recordings, bud.sip, bud.sync that are absent from client.py; VoiceCloneRequest type exists with no client method. Beginners following the README hit AttributeErrors.
- Emotion standardization is real but lossy/silent: many providers (Deepgram, OpenAI, Kokoro, LMNT) have no emotion support; the mapper emits warnings server-side but the SDK has no typed way to surface 'this emotion was ignored for this provider' to the caller (capability negotiation is absent from the SDK).
- No capability/discovery API surfaced to the SDK: the gateway knows per-provider feature support (SttFeatures/TtsFeatures + emotion support matrix), but the SDK hardcodes a stale STT/TTS_PROVIDER_CAPABILITIES dict in types.py (10 STT/12 TTS) that does NOT match the gateway's 27/32 providers.
- Config boundary lacks validation feedback: permissive serde silently accepts unknown fields and bogus languages; failures surface only at provider connect with provider-specific messages (e.g. 'Deepgram API key not configured'), not as standardized client-side errors.
- Provider count drift: SDK enums list 10 STT + 12 TTS + 2 realtime; gateway/context states 27 STT + 32 TTS + 12 realtime/S2S. The SDK is years behind the gateway's provider fleet.

### research-lang-emotion
_WaaV today has TWO opposite maturity levels. EMOTION is already well-standardized: gateway/src/core/emotion/ defines a canonical superset (22 Emotion variants + 15 DeliveryStyle + numeric/named EmotionIntensity + free-form `description`) with a Mapper trait, per-provider mappers (Azure SSML express-as, ElevenLabs voice-settings, Hume natural-language), a ProviderEmotionSupport capability descriptor, and graceful no-op warnings — a strong base that just needs the superset widened and the provider matrix filled in (Cartesia/OpenAI/PlayHT/LMNT are wrongly marked 'no emotion support'). LANGUAGE, by contrast, has ZERO standardization: handlers/ws/config.rs:304 carries a raw `pub language: String` passed straight through, and each of the 27+ STT / 32+ TTS providers validates it against its own native notation (Deepgram BCP-47 `en-US`, ElevenLabs ISO-639-1 `en`, Sarvam `od-IN`/`en-IN` non-standard, iFlytek underscore `zh_cn`, Baidu numeric model `1537`/`zh`, Google `cmn-CN`, IBM `en-US_BroadbandModel`, AWS Transcribe `EN_US` enum). Web research confirms the real values for all 14 requested providers. Recommendation: introduce a canonical BCP-47 language scheme + a NotationMap mapper (port the existing waav-infer components/standardize.rs `resolve_alias`/`NotationMap` pattern into the gateway) so a dev writes ONE code and the gateway maps per provider+model; and for emotion, keep the existing canonical model, widen it (add Cartesia/Azure-DragonHD styles), and fix the under-mapped providers._
- LANGUAGE: no canonical scheme or mapper exists in the gateway at all — `language: String` (config.rs:304) is passed verbatim to every provider; switching provider while keeping the same client code WILL break (e.g. 'en-US' rejected by ElevenLabs which wants 'en'; 'or-IN' rejected by Sarvam which wants non-standard 'od-IN'; 'zh-CN' rejected by iFlytek which wants 'zh_cn'; Baidu wants numeric model '1537').
- LANGUAGE: no auto-detect canonical value — providers differ (Deepgram detect_language flag, AssemblyAI universal-streaming-multilingual speech_model, Gemini native-audio auto, OpenAI source auto). No canonical 'auto'/'multi' token is defined or mapped.
- LANGUAGE: region/script handling undefined — canonical needs a documented fallback chain (en-US -> en when provider only accepts ISO-639-1; cmn-CN<->zh-CN<->zh aliasing for Mandarin; or-IN->od-IN Sarvam quirk; nb/no Norwegian; yue/zh-HK Cantonese).
- EMOTION: superset is narrower than the union — missing high-value Azure/DragonHD + Cartesia styles now researchable (e.g. amazed, amused, intrigued, sarcastic-as-first-class, whispering/shouting are styles not just DeliveryStyle, newscast/customerservice/advertisement_upbeat scenario-styles, flirtatious). DeliveryStyle and Emotion overlap awkwardly (Cheerful/Serious/Soft live in BOTH enums).
- EMOTION: provider matrix is stale/incomplete — Cartesia (mappers/mod.rs:74) and OpenAI (mod.rs:82) wrongly no-op; no mappers exist for AWS Polly domain styles, PlayHT emotion enum, Google (now Chirp3/Gemini affective), LMNT, Sarvam, or any realtime S2S (gpt-realtime/Hume EVI/Gemini Live/Nova Sonic) — realtime emotion routing through `instructions`/system-prompt is unaddressed.
- EMOTION: ElevenLabs v3 inline audio-tag mechanism ([excited][whispers]) and Azure DragonHD bracket markers are a different injection point (text-embedded, not a settings field) than ElevenLabs v2 stability — the mapper abstraction (MappedEmotion has ssml_style/speed/voice-settings but no 'text_prefix'/'inline_tag' slot) cannot yet express tag-injection.
- EMOTION: no canonical handling for free-form `description` precedence vs structured emotion across the instruction-based providers (Hume/OpenAI/Nova/Gemini) — currently only Hume mapper consumes description; OpenAI/Cartesia/realtime should synthesize an instruction string from the canonical (emotion+intensity+style+description+context).
- No single source-of-truth capability endpoint: a client cannot query 'what languages/emotions does provider X support' — ProviderEmotionSupport exists in Rust but is not surfaced via REST/SDK; there is no language-support equivalent at all.

### research-features
_WaaV ALREADY has a mature, additive standardization layer for the realtime/streaming path — `SttFeatures`/`TtsFeatures` (typed canonical knobs) + `ProviderExtras` (open passthrough) crossing the dispatch boundary via `create_stt_standard`/`create_tts_standard`, with a per-provider `from_standard` mapper that degrades capability gaps LOUDLY (warn + metric) rather than failing. Emotion is also fully standardized (EmotionConfig → per-provider mapper). The live gateway accepted a full `features`+`extras` config end-to-end (only failed on missing Deepgram key). BUT the design goal's three headline asks are GENUINELY MISSING and have NO interface today: (1) VOICE CLONING — zero clone API surface; (2) TRANSLATION — only mentioned in doc-comments (gladia); (3) BATCHED/ASYNC transcription — no standardized batch call. Two more structural gaps: there is NO canonical-language mapper in the gateway (raw `language` string is passed straight through — config_handler.rs has zero language handling, unlike the Infer side's standardize.rs), and function-calling/`tools`+`modalities` are standardized ONLY on the realtime path (RealtimeConfig), NOT on the cascade `conversation` path (ConversationConfig exposes neither). The SDKs lag the gateway by years: Python lists 10 STT/12 TTS providers (gateway has 27/32) and surfaces none of `features`/`extras`/clone/translate/batch. The recommendation is to EXTEND the existing additive `features`/`extras` pattern with four new canonical capability blocks (VoiceClone, Translation, Batch/AsyncJob, plus AudioFormat+tools on the cascade) rather than invent a parallel system, and to backfill the SDKs from the OpenAPI schema._
- No voice-clone interface at all (instant + professional). Need a canonical VoiceClone block: voice_clone:{ samples:[bytes|url], name(req), mode: instant|professional (canonical 2-tier), description?, labels:{language,accent,gender,age}?, language?, base_voice_id?, remove_background_noise?, consent:{verified:bool, statement?}? }. Returns canonical {voice_id, status: ready|verifying|training|queued, requires_verification?}. Map: instant→ElevenLabs /voices/add, Cartesia /voices/clone(stability), PlayHT /cloned-voices/instant, LMNT create-voice, Speechify /voices; professional→ElevenLabs PVC 6-step async, Resemble professional (dataset length). DEGRADE: providers without a tier reject with capability error; Hume's generation_id-based save is a DIFFERENT shape (save-prior-generation, not from-audio) — expose as a separate `save_generation_as_voice` op.
- No standardized translation. Need a canonical Translation block split by capability: (a) stt translation side-channel translation:{ target_languages:[canon], partials?:bool } → emit canonical translations[]{lang,text} (Speechmatics translation_config, Gladia translation_config.target_languages, AssemblyAI Speech Understanding); (b) translate-to-English single-pass flag translate_to_english:bool → Whisper /audio/translations; (c) S2S dubbing dub:{ source_lang?, target_languages:[canon], voice_id? }. DEGRADE: a provider with neither rejects/falls back to transcribe-only with a warning.
- No batched/async transcription call. Need a canonical Batch envelope batch:{ audio: url|bytes, callback_url?, callback_method?: POST|PUT } that REUSES the existing SttFeatures verbatim (diarization,word_timestamps,redaction,keyterms,sentiment,entity_detection,summarize,topics,intents,language_detection,alternatives,multichannel) plus batch-only extras (paragraphs, utterances, chunking_strategy, logprobs, prompt). Submit→poll(job_id)/webhook envelope. Map: Deepgram pre-recorded, AssemblyAI POST /v2/transcript, OpenAI batch transcribe. Note `alternatives`/`detect_language`/`summarize`/`topics`/`intents` are batch-capable on Deepgram even though they're streaming gaps — the batch dispatcher must NOT inherit the streaming from_standard's unmapped-on-streaming exclusions.
- No canonical-language mapper in the gateway: en-US vs us-en vs eng vs cmn-Hans-CN go straight to providers. Need a canonical Language type + per-provider language_to_provider() (port Pipecat's enum+mapper, and reuse the Infer-side standardize.rs resolve_alias approach) so client code never changes the language string when switching providers.
- Function-calling/tools + output modalities are NOT on the cascade conversation path. ConversationConfig has no tools/tool_choice/modalities; only RealtimeConfig does. A beginner can't supply tool definitions to the cascade DAG via the WS `conversation` config — needs the same tools:[ToolDefinition]/tool_choice/modalities canonical block on both paths.
- Audio format is split across base.encoding + base.audio_format + features.sample_rate with no single canonical {container, encoding, sample_rate, bit_rate} object — providers model it inconsistently (Cartesia output_format{container,encoding,sample_rate}; OpenAI response_format mp3|opus|aac|flac|wav|pcm; Deepgram encoding+sample_rate). Risk of cache-key collisions and ambiguous mapping (e.g. opus-in-ogg vs raw opus).
- Keyword boosting has no per-term BOOST WEIGHT in SttFeatures.keyterms (plain Vec<String>). Deepgram keywords support term:intensifier, Google speechContexts.boost, AssemblyAI word_boost+boost_param(low|default|high). Need keyterms:[{phrase, boost?}] to be lossless.
- Redaction categories aren't a closed canonical enum — `redaction: Vec<String>` is freeform. Deepgram groups (pci|pii|phi|numbers, 50+ entities) vs AssemblyAI redact_pii_policies (person_name|credit_card_number|location|medical_condition|...) diverge; need a canonical category set + per-provider expansion + a redaction substitution mode (mask char vs hash vs entity-tag).
- SDKs (python 10/12, typescript) don't surface features/extras/clone/translate/batch and list a tiny stale provider subset — they cannot exercise the standardization that already exists server-side. They should be regenerated/backfilled from the OpenAPI schema (utoipa is already wired: ProviderExtras has a hand-written ToSchema).
- No alias/proxy resolver: there's endpoint-override + DAG-template machinery but nothing that resolves a canonical `model:"my-backend-alias"` to a server-side DAG/provider/model triple changeable without client edits.
