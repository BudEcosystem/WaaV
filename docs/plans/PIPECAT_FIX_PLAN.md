## 0. How to read this plan

### 0.1 This is the *second wave*, layered on a now-realtime cascade — not a rewrite
WaaV's own `MASTER_PLAN.md` (extreme-TDD, mostly **shipped** per `AUDIT_REPORT.md` + the implementation-progress record) already closed the **realtime-critical** overlaps with Pipecat: streaming WebSocket TTS (Deepgram Aura, `core/tts/websocket.rs` + the defaulted `speak_with_context` on `core/tts/base.rs:333`), Smart-Turn **v3** (`core/smart_turn/detector.rs:30-33`, the identical `smart-turn-v3.2-cpu.onnx` Pipecat ships), eager-EoT with history staging (`core/llm/mod.rs:655-833` `complete_staged`/`commit_turn`, `conversation/mod.rs:85,136` `EagerTurn`), sentence-boundary aggregation in the pump, monotonic timing, the single-owner speech-final critical section, SIGTERM drain, and per-class WS backpressure.

Every item is reconciled against what is already done (§0.3) so nothing is re-planned.

### 0.2 The organizing principle: WaaV's own goals, met in full
Per `REALTIME_ROADMAP.md`, WaaV's goals are concrete and this plan is sequenced to satisfy them, using Pipecat's mechanisms as the *means*:

- **G1 — Realtime latency.** end-of-speech → first-audio **300–500 ms**, ideally toward **200 ms**. (Measured baseline through the production binary: ~7.5 s, 99.7% provider-dominated; gateway glue ~10–20 ms.)
- **G2 — Dual architecture.** Offer *both* an optimized cascade (STT→LLM→TTS, controllable/auditable/tool-capable) *and* a speech-to-speech path, **routed per use-case** — WaaV's stated differentiator. Pipecat's "S2S = a service emitting the same downstream frames" is the clean way to make S2S a drop-in DAG node (roadmap P4).
- **G3 — Barge-in stop < 60 ms.** Pipecat's ≤40 ms output chunking + WaaV's existing `clear_buffer()` is the means; must be *measured and enforced* via the live profiler.
- **G4 — Standardized, one API per provider.** Every capability available to all relevant providers through the standard `StandardSTTConfig`/`StandardTTSConfig` + base-trait path; new capability lands as **defaulted trait methods** (the `speak_with_context` pattern) so the 67-provider fleet and ~135+ call sites don't churn.

- **G6 — High accuracy & correctness.** Turn-taking semantics correct across the fleet; no context corruption; exactly-one-completed-turn identity; multilingual correctness (the EN→Hindi DAG is a live fixture).

## 1. Per-gap engineering plan — Cluster A: Turn-taking & Interruption

**Reconciliation / keystone:** WaaV's turn-taking is **correct but monolithic** — a hardcoded pipeline (`stt_result.rs` dual/triple-timer speech-final machine → `conversation/mod.rs` barge-in + eager-EoT) **duplicated across two unconnected consumers** (`ConversationOrchestrator` and the DAG path at `config_handler.rs:1681`). Pipecat factors the identical concerns into three orthogonal composable strategy families (start/stop/mute) on one controller. The load-bearing move (**A-G0**) is a provider-agnostic **`ControllerSignal` stream + a `TurnController` running pluggable start/stop/mute strategy traits**, fed by the one STT callback all ~33 providers funnel through (`BaseSTT::on_result`, base.rs:528) + the smart-turn fire-site (`manager.rs:490`). The controller adds *policy* around the existing `TurnDecisionEngine` (which stays the smart-turn detector — §6.2 A4), it does not replace it. **Dropped as already-adequate (do NOT rebuild):** WaaV's interruption ordering / no-double-fire / monotonic-time guarantees are already enforced by the fire-generation claim protocol (`stt_result.rs:399-449`) + `InterruptionState` (`state.rs:60-87`); the centralized `clear_tts` + `CancellationToken` barge-in is PARITY with Pipecat's task-cancel; the eager-EoT *staging* primitive is already shipped (`complete_staged`/`commit_turn`). This cluster generalizes those into the strategy API and adds two genuine correctness fixes.

**Dependency graph:** `A-G0` (spine) is the keystone — nothing ships without it. `A-G1` (the missing `is_finalized` STT flag) is a small standalone fleet change that **must precede A-G2**. `A-G6` (uninterruptible chunk) is orthogonal, parallelizable. Ship order: **A-G0 → A-G1 → A-G2 → A-G3 → {A-G5, A-G4, A-G7}**; `A-G6` parallel; `A-G8` depends on the B-cluster universal-LLM-context and is optional. Tiering: **A-G0, A-G1, A-G2, A-G3 = T0/T1 (critical path); A-G4 = T1; A-G5, A-G6, A-G7 = T2; A-G8 = T3.**

### A-G0 — Pluggable turn-strategy abstraction (T0, the keystone)

> **v2 corrections (§6.2 A4–A12, §6.1 X3/X5, verified first-hand):** (1) WaaV **already has** a live `turn_decision::{TurnSignal, TurnDecisionEngine}` ensemble (`engine.rs:51`, owned by `SmartTurnProcessor`) — so rename the new type **`ControllerSignal`** and have the `TurnController` **consume** the engine's turn-completion output (the engine stays the detector; the controller owns start/stop/mute *policy*); "no abstraction" was wrong. (2) **Actor-bug guardrail (load-bearing):** transcript egress (interim + provider-final) MUST stay a synchronous side-effect on `on_stt_result`, byte-identical to today; the controller is fed *alongside* egress and emits only turn-decision events, never transcript delivery (else it re-creates MASTER_PLAN crit#1's killed bug). (3) `BotStarted`=first egress audio chunk (`manager.rs:928`), `BotStopped`=playback drain — **not** `on_complete` (= generation completion, fires while audio still plays). (4) Move the whole `begin_turn` (id+token) into the controller; feed its `turn_id` into the profiler `TurnTrace`. (5) Timer seam: the controller owns a tokio timer per armed stop-strategy, feeding a synthetic `ControllerSignal::Timer` back under the generation claim. (6) Bar is **ordering + exactly-once**, not "byte-identical". Read the text below through these.

**(a) Mechanics + delta.** Pipecat's `UserTurnController` (`turns/user_turn_controller.py:32`) holds `_user_speaking`/`_user_turn` + a stop-timeout watchdog (:95-99), runs every start then every stop strategy breaking on `ProcessFrameResult.STOP` (:166-174); `_trigger_user_turn_start` is guarded `if self._user_turn: return` (:266, no double-start); stop strategies emit **two** events — `inference_triggered` vs `stopped` (`base_user_turn_stop_strategy.py:118-139`) enabling speculate-vs-finalize via `deferred()`; resets all strategies on each boundary (:273-307). Every signal source is normalized to a Frame *before* any strategy, so strategies are provider-agnostic. WaaV today: **no abstraction** (grep-confirmed) — stop logic in `stt_result.rs:77-102` (`is_speech_final`→fire; `is_final`→600ms detection + 1500ms hard timer); start/barge-in in `conversation/mod.rs:507-523` (**any** non-empty interim → `handle_barge_in`, no word gate); smart-turn in `manager.rs:463-512` (only consumer = eager-EoT); the DAG re-implements the stop trigger inline (`config_handler.rs:1681`). (NB §6.2 A4: this is **no pluggable *strategy* trait**; a fixed `turn_decision::TurnDecisionEngine` ensemble *does* exist and stays.) **Delta:** one `TurnController` consuming a normalized `ControllerSignal` stream, running `Vec<Box<dyn UserTurnStartStrategy/StopStrategy/MuteStrategy>>`, emitting `TurnEvent`s; WaaV's eager-EoT + timers become strategies *around* the engine.

**(b) Impact/correctness.** Sites: `config_handler.rs:413-435` (conversation STT cb), `:1654-1738` (DAG STT cb), `:391-406` (smart-turn cb) all route through the controller; `stt_result.rs` timers are *not deleted* — they become the engine behind `SpeechTimeoutUserTurnStopStrategy` (A-G2), preserving the fire-generation claim; `manager.rs:739-823` `on_stt_result` keeps its `can_interrupt()` fast-path + observer anchors, now feeding `controller.feed_signal`. **Invariants:** no double-start/stop (`AtomicBool turn_active` + the existing fire-generation claim); turn-id monotonicity (move `next_turn_id` from `conversation/mod.rs:134` into the controller); barge-in latency unchanged (a start verdict is a pure `split().count()`, `clear_tts().await` is the same call); interruption ordering (controller calls the same `clear_tts`, which self-guards on `can_interrupt()`). **Failure modes prevented:** strategy panic on hot path → trait method is **infallible**, returns a verdict; strategy holding a lock across `.await` → **the trait method is sync** (`fn on_signal(&mut self,&ControllerSignal)->Verdict`), *all* I/O happens in the controller after the verdict (the single most important hot-path constraint); two consumers diverging again → the controller is the **only** turn brain, both paths subscribe to `TurnEvent`s. **Optimal:** a session-owned `TurnController` holding the three strategy vectors behind a `parking_lot::Mutex` (taken microseconds, never across `.await`) + the stop-timeout watchdog; `VoiceManager` gains `set_turn_controller` and feeds it from STT result, smart-turn result, and **new** bot-speaking signals derived from TTS start/complete callbacks (these don't exist today — which is also why A-G5/A-G7 are currently impossible).

The session registers a `TurnEventCallback`: conversation maps `Stopped→run_turn`, `Started{interrupt}→handle_barge_in`, `ResetAggregation→clear turn buffer`; DAG maps `Stopped→executor.execute_from(post_stt_node,…)`. ## 2. Per-gap engineering plan — Cluster B: LLM, Context & Conversation Flows

**Reconciliation / tiering:** WaaV's `core/llm/mod.rs` is a well-built but **structurally OpenAI-Chat-Completions-only** client — the on-the-wire `ChatMessage`/`ToolCall`/`ToolDefinition` types *are* the OpenAI request schema (`core/llm/mod.rs:110-239`); the only transport is `POST {base_url}/chat/completions` (`:593-596`); grep for `v1/messages`/`generateContent`/`tool_use`/`function_response`/`input_schema` returns **zero** hits in `gateway/src`. So "Anthropic/Gemini support" today = "hope it's OpenAI-compatible," false for native Claude/Gemini tool-calling and system placement. Exactly **three** construction sites: `conversation/mod.rs:172`, `compiler.rs:382`, `nodes/llm.rs:223` — a small, well-defined integration surface. Eager-EoT/staging is **already done** (`complete_staged`/`commit_turn`, reconciliation §0.3) and is preserved unchanged; this cluster adds the *vendor-portability and orchestration* layer on top.

**Dependency chain (the build order):** Gap B1 (universal context + adapter) is foundational and goes first/alone. Then B2 (S2S) and B4 (tool orchestration) in parallel (both need only B1). Then B5 (commit-partial, small, rides B4's history machinery). Then B3 (flows, consumes B4). Then B6 (summarization, lowest). Tiering: **B1 = T0; B2, B3 = T1; B4, B5 = T2; B6 = T3.**

### B1 — Universal LLM context + per-vendor adapter (T0, foundational)

### C-G1+2 — Unified sentence aggregator w/ lookahead + decimal/abbrev disambiguation (T0)

> **v2 correction (§6.4 C1/C5/C6):** pin the `is_real_boundary` contract — **push the triggering char into `buf` before the boundary check** (Pipecat order) and read **both** the char before `.` *and* the lookahead char, or `"3.14"` splits at `"3."` (the test the gap exists to pass); add **char-streaming-granularity** tests. ### D-G1 — Reconnect audio-replay buffer (T1)

> **v2 correction (§6.5 D1, verified first-hand):** the v1 "the one real bug / mid-utterance loss via `finalize_stt`" framing is **overstated** — `finalize_stt` runs only *after* the client signals end-of-input (`audio_handler.rs:290-303`), so no concurrent `send_audio`; and the Deepgram mpsc(32) already buffers internal reconnects. The chaos mocks must be redesigned to track audio→transcript (today they emit finals on a timer); the live-kill test is the real oracle. Read below through this.

**(a) Mechanics + delta.** Pipecat `STTService` (`stt_service.py:170-655`): `_can_reconnect`/`_need_reconnect`/`_reconnecting` flags + `_reconnect_audio_buffer`. While `_reconnecting`, `process_audio_frame` **appends the frame to the buffer and does NOT send** (:349-363); after a successful reconnect it **replays every buffered frame in order** (:605-655). Reconnect is **deferred while the user speaks** (`_can_reconnect=False` on VADUserStarted, fires on UserStopped, :516-544). WaaV today: audio rides `ws_rx` mpsc to the inner loop (`deepgram.rs:855`); when the loop breaks to reconnect, the consumer is gone until re-dial, and `finalize_stt` (`manager.rs:1327-1353`) does `disconnect → sleep(50ms) → connect` during which `send_audio` errors or silently drops — **words are lost mid-utterance.** No `_can_reconnect`, no replay buffer. **Delta:** add (1) a VAD-state gate deferring a mid-utterance reconnect to end-of-turn, and (2) a bounded replay buffer in the **STT base** that captures `send_audio` during a reconnect and replays it in order — standardized so all 31 streaming STTs inherit it.

**(b) Impact/correctness.** Sites: `core/stt/base.rs` (new state + default methods), `core/stt/deepgram.rs` (signal begin/end-reconnect + route audio through the buffer), `manager.rs:1327` (`finalize_stt` must stop dropping audio), `callbacks.rs` (wire VAD→STT). **Invariants:** (i) no audio loss across a reconnect (union of pre-gap + replayed == full stream); (ii) `send_audio` during reconnecting buffers, never errors-to-caller; (iii) **bounded memory** — cap at ~30s, drop-oldest + `waav_stt_reconnect_buffer_dropped_total` (a 30s outage already kills the session, so this is a safety valve); (iv) no reconnect mid-utterance unless forced. **Failure modes:** unbounded buffer → cap; double-count replay → only buffer after the drop, and the featured-restored session is fresh so replayed audio is the only audio it's seen; `_can_reconnect` never re-enabled (no UserStopped ever) → a **max-defer timeout (~5s)** forces the reconnect. **Optimal:** a reusable `SttReconnectBuffer` struct + default trait methods in the base.

**(c)/(d) Integration + tests.** API (`core/stt/base.rs`):

### E-G2 — Output chunk-size knob / barge-in tightness (T2, do first)

> **v2 correction (§6.6 E1/E4):** v1 misread the LiveKit SDK — the 4th `NativeAudioSource::new` arg is **`queue_size_ms`** (WaaV passes 240/160/80 ms of buffering, mis-named `samples_per_frame`), **not** 10ms framing. LiveKit barge-in is tight because `clear_buffer()` flushes the queue, not because of framing; do **not** wire `audio_out_chunk_ms` into `queue_size_ms`. The `OutputChunker` is needed **only** for the **WS** egress path (`processor.rs:269`), which is a separate code path from `callbacks.rs::on_audio` — place it there, not at the LiveKit-side callback. Read below through this.

**(a) Mechanics + delta — honest near-parity.** Pipecat slices output to 10ms×`audio_out_10ms_chunks` (default 40ms, `base_output.py:134`); barge-in residual is bounded because the consumer pulls one chunk at a time and the queue is replaced on interruption; LiveKit adds `clear_queue()` on `InterruptionFrame`. WaaV today: TTS audio is forwarded **verbatim, no re-chunking** (`callbacks.rs:46-58`) — **but** for LiveKit the `NativeAudioSource` is built with `samples_per_frame = (sr*10)/1000` (`audio.rs:34`) so the **SDK internally re-frames to 10ms and `clear_buffer()` flushes it** (`audio.rs:192,216`) — i.e. WaaV's LiveKit barge-in is **already ~10ms-bounded, at-or-ahead of Pipecat's 40ms default**. The **genuine gap is raw-WS egress** — `WSResponse::Binary(data)` is sent whole (`processor.rs:269`), no SDK to re-frame, so a clear can't truncate a frame already on the socket — **plus a uniform config knob** so both transports expose the same tightness (G3/G4 standardization).

**(b)/(c)/(d).** `core/audio/output_chunker.rs` `OutputChunker{buf:BytesMut, chunk_bytes}` with `push(bytes)->Vec<Bytes>` (drain full chunks, carry <1-chunk remainder — Pipecat's prefix-drop) + `flush_remainder()`, at the common choke point `callbacks.rs::on_audio`; config `audio_out_chunk_ms`(default **20**, tighter than Pipecat since WaaV already clears) fed into WS chunking + LiveKit `samples_per_frame`. **Invariants:** no audio dropped/duplicated (carry remainder); barge-in clears within one chunk (WS clear also drops the chunker remainder); chunk_bytes even (never split a PCM sample → clicks); WS clients needing exact framing (Genesys/Vonage 20ms) → pad to exact size. **Tests:** chunker drains `[32,32,32]` + carries 29, `flush_remainder()→[29]`; odd input carries the trailing byte; 640B@20ms/16k mono → one `Binary(640)`+384 carried, clear drops the carry; LiveKit source built with the configured frame size. **Live:** barge-in residual < one chunk (≈20ms) on both transports. **Effort:** ~1 d.

### E-G3 — LiveKit per-participant resubscribe cleanup + event surface (T2, confirmed leak)

**(a) Mechanics + delta.** Pipecat keys streams by participant sid, **closes the old stream before registering the new** on every resubscribe (`livekit/transport.py:511-567`, 2s bounded close) → exactly one producer per participant; `on_first_participant_joined` fires once. WaaV today (**leak confirmed**): `TrackSubscribed` spawns a per-track task pushed into a **flat `Vec<JoinHandle>`** (`events.rs:155,218`) with only passive `retain(!is_finished())`; the prior task for the same participant is **not cancelled on resubscribe** (relies on the SDK closing the old stream); `TrackUnsubscribed` (:231) and `ParticipantConnected` (:242) **only log**; **no first-participant detection, no greeting hook anywhere** (grep-confirmed). The facade re-drives subscription for already-present tracks, so subscribe can fire >once/track → real transient-accumulation under mute/unmute storms. **Delta:** (1) `HashMap<ParticipantIdentity, JoinHandle>`, close-old-before-register, abort-on-unsubscribe (2s bounded); (2) a `participant_connected_callback` + a once-only first-participant flag → enables greeting-on-join.

**(b)/(c)/(d).** Sites: `events.rs:105/231/242`, `mod.rs:84` (field), `callbacks.rs:83` (new callback). **Invariants:** exactly one producer per participant (idempotent pop-close-before-insert); no duplicated inbound audio (the leak's symptom — two tasks feeding the audio callback); first-participant fires once (flag reset only at count 0); tolerate transient `capture_frame` errors during barge-in. **Tests:** subscribe→subscribe(same id) → one live handle, old aborted; unsubscribe → zero; two participants → first-participant callback once, both leave → resets. **Live:** mute/unmute 20× → no inbound-audio duplication, bounded task count; greeting delayed until `on_first_participant_joined`. **Effort:** ~1 d.

### E-G4 — Eval harness + LLM-as-judge (T3, high engineering value, not product-gated)

**(a) Mechanics + delta.** Pipecat `evals/`: a YAML `Scenario`/`Turn`/`Expectation` DSL (`scenario.py`) with per-turn **`within_ms` latency budgets anchored at user-send** (`harness.py:894`); `EvalJudge` (`judge.py`) wraps any OpenAI-compatible LLM, NL criteria, **STT-homophone-tolerant** prompt ("'for'/'four'→4; never fail solely for a transcription error"), three-way `yes`/`no`/`continue`, sha256-cached by `(criterion, conversation)`; `EvalSuite` runs bots in parallel. WaaV today: a strong **in-process driver** (`conversation_loop.rs` — scriptable mock LLM/STT/TTS, `MockTts.spoken`) + the latency substrate (`turn_profile.rs` `TurnTrace`, the `within_ms` oracle) + `serde_yaml`, but **no scenario DSL/runner/judge** (grep-confirmed; team-scoped per PIPECAT_ANALYSIS §8.5). **Delta:** `Scenario`/`Turn`/`Expect` serde types + YAML loader; a runner over `ConversationOrchestrator` capturing `MockTts.spoken` + `TurnTrace`, applying `text_contains`/`eval`/`within_ms` per turn; an `EvalJudge` reusing `core/llm::LlmClient` with the homophone prompt + sha256 cache.

**(b)/(c)/(d).** Test-only (`tests/eval/` or `#[cfg(feature="eval")]`); reuses conversation/llm/observability. **Invariants:** judge cache deterministic (sort_keys JSON, exact sha256 port); `within_ms` anchored **once per turn** not per-expectation; `continue` monotonic (only the judge fails; a missing `text_contains` → `continue` + keep accumulating segments). **Failure modes:** judge nondeterminism → cache + `temperature 0` + "only `yes` passes"; CI mode (mock LLM, deterministic) vs live mode (`#[ignore]`+`key()`-gated, WaaV convention). Scenario format sketch + Rust types per the cluster report (`#[serde(default)]` idiom). **Steps:** `EvalJudge` (TDD: homophone criterion → `yes`; identical `(criterion,convo)` → 1 inference) → `Scenario` serde + loader → runner over the orchestrator → surface `TurnTrace` from `on_stt_result` so `within_ms` asserts real per-stage latency → optional parallel `EvalSuite`. **Live:** a real scenario vs a real LLM, judge `gpt-4o-mini`, assert verdict + `response_latency_ns()` SLO. **Effort:** ~3 d (+0.5 to consolidate `conversation_loop.rs`/`latency_harness.rs` scaffold into `tests/common/`).

### E-G1 — Voicemail / CallStateDetector (T3, outbound-gated)

> **v2 correction (§6.6 E2/E3):** the v1 "natively hostable in the DAG, no `ParallelPipeline` needed" claim is **false for streaming voicemail** — WaaV's Split/Join is **batch-only**, and the streaming executor bails to batch on any Join (`executor.rs:150-152`), producing whole TTS at the end with nothing to incrementally gate. Streaming TTS and a concurrent Join are mutually exclusive in one graph. Re-scope to **cascade-orchestrator-only** with the `OutputGate` at the **TTS audio-callback seam** (`voice_manager/callbacks.rs:47`, *not* the nonexistent `ConversationOrchestrator::flush()` method), or extend the streaming executor for a bounded concurrent side-branch without a topological Join. Read below through this.

**(a) Mechanics + delta.** Pipecat `VoicemailDetector` = a `ParallelPipeline` (conversation branch + classifier-LLM branch) with three `EventNotifier`s + a **`TTSGate`** that buffers TTS frames in order until a verdict, then **releases in order** (human) or **clears** (voicemail) (`voicemail_detector.py:397-662`); a response-delay timer waits for the greeting to finish before leaving a message. WaaV: **no such code**, **but** the DAG has the parallel substrate (Split/Join above) and the cascade path has centralized barge-in (`handle_barge_in`/`clear_tts`). **Delta (native hosting, not a ParallelPipeline port):** a reusable **`OutputGate`** (buffer→release-or-clear) shared by (i) DAG users — a `CallStateClassifierNode` as a Split branch writing a verdict to `ctx.metadata["call_state"]`, with the TTS endpoint gating on it — and (ii) the cascade — a `CallStateDetector` hook on `ConversationOrchestrator` whose `flush()` routes through the gate while a parallel classifier task (spawned like `trigger_eager_turn`) sets the verdict.

**(b)/(c)/(d).** `core/extensions/call_state/`: `OutputGate{buffered:Mutex<Vec<TtsUnit>>, state:AtomicU8}` with `submit`/`release`/`clear`; the classifier uses a **separate `LlmClient`/session** so it never pollutes real history; **add a safety-timeout force-release as "human"** (Pipecat buffers indefinitely on classifier failure — WaaV must not). **Invariants:** no audio before classification (gate starts buffering); exactly one of release/clear (verdict latch); ordering preserved on release; no deadlock (gate is append-only, never blocks the producer; safety timeout backstops a hung classifier); no history pollution (separate session). **Tests:** `OutputGate` submit-while-buffering stores, `release` returns in order, `clear` drops; classifier "VOICEMAIL" → gate cleared + turn cancelled + `clear_tts`; "CONVERSATION" → released in order; no-verdict-within-timeout → released as human; response-delay fires once after silence ≥ delay. **Live:** outbound call to voicemail → bot waits for the beep, leaves a message; human → buffered greeting plays in order, no audible delay. **Effort:** ~3–4 d. **Gated:** outbound calling.

### E-G5 — Call recording, multi-stream sync (T3, compliance-gated; partially exists)

**(a) Mechanics + delta.** Pipecat `AudioBufferProcessor`: byte-aligned user/bot buffers via **sync-before-extend** (pad the lagging buffer before appending, guarded by speaking flags), **wall-clock silence injection** on >0.2s gaps, stereo (user-L/bot-R) or mono mix, per-turn segments with ≤1s pre-roll. WaaV today: recording = **LiveKit Egress room-composite → single mono OGG to S3** (`room_handler.rs:436-485`); `handlers/recording.rs` is download-only — **no in-process mixing, no stereo split, no per-turn events** (but the in-process PCM is available: user via `events.rs:195`, bot via `callbacks.rs:46`). **Delta:** an in-process **`RecordingSink`** trait (standardized: LiveKit + WS both feed it) + a `SyncRecorder` porting the sync-before-extend alignment.

**(b)/(c)/(d).** `core/recording/sink.rs`: `RecordingSink{on_user_audio, on_bot_audio, on_user_turn_end, on_bot_turn_end, finalize→RecordingOutput}`; `SyncRecorder` with per-side buffers + monotonic last-write timestamps + two C-G5 stream resamplers + `channels:{MonoMix|StereoUserLeftBotRight}`. **Invariants (alignment is the whole point):** both buffers represent the same wall-clock instant (port sync-before-extend exactly, incl. the speaking-flag crackle guards + timestamp-advance-after-sync); 16-bit alignment; mono clips (not averages); stereo truncates to shorter; bounded memory (flush-on-threshold / stream to object store). **Tests:** equal-length aligned buffers; gap → silence injected into the lagging side; stereo interleave `[L0,R0,…]`; mono additive+clip ±32767; per-turn pre-roll trimmed to 1s. **Live:** 2-turn call → stereo WAV, left=user-only, right=bot-only, time-aligned (cross-correlate vs known STT/TTS timing). **Effort:** ~2–3 d. **Dep:** C-G5 resampler. **Gated:** compliance/QA.

### E-G6 — IVR + DTMF (T3, telephony-gated)

Pipecat: an inbound **`DtmfAggregator`** (digits → `"DTMF: 123"` `TranscriptionFrame` into the normal STT→LLM context, first-digit barge-in, terminator/idle flush, **tone-before-transcript** ordering) + outbound **IVR** (`<dtmf>N</dtmf>` tag generation + mode-switch).
